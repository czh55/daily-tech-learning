一句话概括。本文解决的核心问题是：当标签页堆积到拖垮内存与 CPU 时，如何用「收纳，得到队列，得到消化，得到归档」四步 GTD 式流程，把不敢关的标签变成可逐条处理的阅读队列，同时做到零账号、零上传、全本地存储。

接下来，第一部分，核心概念关系。

关系脉络如下：收纳 Stash，一键收走标签，然后展示 Queue，按日期+域名分组，然后消化 Consume，侧边栏逐条处理，然后归档 Archive，已消费自动归档

接下来，第二部分，认知纠偏。

认知纠偏

TabQueue 不是书签管理器或稍后读服务——它管理的是「当前打开的标签页」而非「文章收藏」，擅长 GitHub issue、技术文档、论坛帖子等 Pocket 类工具不擅长的场景。

接下来，第三部分，反驳。

反驳

对立视角：「标签多说明信息量大，关不掉是生产力象征，收纳反而打断工作流」

80 个后台标签各自跑 WebSocket 和定时器，16GB 内存触发 swap 时你损失的是整机响应速度——收纳不是丢掉信息，而是把认知负荷从标题栏搬到可按域名消化的队列里。

接下来，第四部分，【概念拆解卡】TabQueue 是什么。

在讲什么问题，重度信息消费者每天开几十个「回头再看」标签，导致内存飙到 10GB+、CPU 空转、切换卡顿，甚至崩溃后标签全丢。

核心机制，Chrome/Edge 扩展，把当前窗口所有标签一键收纳进本地队列，按日期和域名两级树形展示，在 Side Panel 中像刷收件箱一样逐条打开、标记已消费或删除。

关键理解，借鉴 GTD 收件盘——收纳时零整理成本，消化时才按结构浏览，读完自动归档，收件盘永远清爽。

典型场景，早上 HN/GitHub/Twitter 各开一堆标签，下班前一键收纳，周末打开侧边栏按 Reddit、GitHub 分组消化。

边界说明，仅支持 Chromium 内核（Chrome/Edge/Brave ≥114）；未上架 Web Store，需手动加载解压扩展；Firefox/Safari 因 API 差异尚未支持。

「TabQueue 把你不敢关的标签页，变成一个有序的阅读队列。」——作者一句话概括

接下来，第五部分，【方法/工具卡】3 分钟上手 TabQueue。

核心思路：开发者模式加载解压扩展 ，得到 快捷键收纳 ，得到 Side Panel 消化队列。

操作步骤，① 访问 tonybai.com/tabqueue 下载 ZIP 并解压；② 打开 chrome://extensions 或 edge://extensions，开启开发者模式，加载解压文件夹；③ Pin 工具栏图标；④ 打开待读标签，按 Ctrl+Shift+S（Mac: Cmd+Shift+S）或点击「收纳当前窗口」；⑤ 点击「打开队列」在右侧 Side Panel 逐条处理。

选型条件，标签页囤积、需要按域名分组、要求数据不出本机时选 TabQueue；需要跨设备云同步或纯文章收藏时选 Pocket/Raindrop。

「那一刻你会感觉到一种久违的清爽——标签没了，浏览器安静了，风扇也停了。」

避坑：收纳前会预览并自动跳过重复标签和浏览器内部页面；手滑标记已消费或删除后 5 秒内可通过底部 Toast 撤销。

接下来，第六部分，【跨概念对比表】TabQueue vs 常见方案。

管理对象，打开中的标签页，当前窗口标签，文章 URL，任意 URL

分组方式，日期 + 域名树形，扁平列表，标签/收藏，文件夹（需手动）

隐私，100% 本地，零网络，本地为主，需注册账号，本地

一句话结论，标签队列 + GTD，一键收纳但难消化，文章稍后读，标签页坟墓

接下来，第七部分，【决策/选型表】什么场景用什么工具。

80+ 标签拖垮笔记本，TabQueue 一键收纳，释放渲染进程，立刻降内存，继续堆标签，每标签独立进程，10GB+ 内存常见

GitHub issue / 文档待读，TabQueue，管理标签页而非文章，Pocket，Pocket 偏重文章，不擅长 issue

跨设备稍后读，Pocket / Raindrop，云同步，TabQueue，刻意不做上传，隐私优先

建个人知识库，Raindrop / Obsidian 集成，结构化收藏，TabQueue 单独使用，TabQueue 定位是消化队列非知识库

接下来，第八部分，【避坑清单卡】使用 TabQueue 的注意点。

坑名，未 Pin 扩展图标导致收纳不便

原因，扩展默认藏在拼图菜单里，高频操作需要多一次点击。

解法，安装后在扩展管理页点击 Pin 固定到工具栏。

严重程度，可忽略——可用 Ctrl+Shift+S 快捷键绕过。

坑名：期待 Chrome Web Store 一键安装——目前需手动加载 ZIP，因审核周期长且个人项目投入产出比低。

坑名：同一 URL 多渠道分享产生重复——TabQueue 已内置 utm/fbclid/gclid 等 20+ 追踪参数归一化，一般无需担心。

接下来，第九部分，【心法/原则卡】隐私优先的设计底线。

原则，阅读列表是你自己的事——数据绝不离开本机。

为什么重要，队列里可能有内网文档、未公开 issue、敏感调研链接，上传云端等于主动泄露。

怎么落地，全部存在 chrome.storage.local；扩展零网络请求、无 GA、无遥测、无账号；可随时 JSON 导出备份。

适用边界，需要多设备同步时必须自行导出/导入 JSON，或配合 Trello/Todoist/Obsidian 集成转发单条。

「我不知道你存了什么——这是隐私优先的底线。」

接下来，第十部分，总结与行动。

结论

TabQueue 用 GTD 式「收纳，得到队列，得到消化，得到归档」解决标签页囤积导致的内存、CPU 与焦虑问题。

按日期和域名两级分组 + URL 智能去重（20+ 追踪参数归一化），消化体验像刷收件箱。

100% 本地存储、零网络、无账号，可选 Trello/Todoist/Obsidian 集成。
