一句话概括。本文解决的核心问题是：当编译器架构债务逼出 487 天从零重写时，Roc 团队为何从 Rust 迁到 Zig、丢掉借用检查器后内存损坏 bug 为何反而更少，以及「没有更好的语言，只有更贴合工程约束的语言」该如何用实测数据论证。

接下来，第一部分，核心概念关系。

关系脉络如下：Bun，Zig，得到Rust · 11天 · AI搬运，然后Roc 编译器，Rust，得到Zig · 487天 · 架构重写

接下来，第二部分，认知纠偏。

认知纠偏

Rust 版 21 个内存损坏 bug 多于 Zig 版 10 个，并不代表 Rust 更不安全——这 21 个全部出在「编译器生成的机器码」而非编译器自身逻辑，恰恰证明借用检查器保护了编译器本体。

接下来，第三部分，反驳。

反驳

对立视角：「编译器就该用 Rust，487 天人工重写 Zig 是逆潮流」

当 30 万行里 1200 处 unsafe 已成常态、arena 分阶段内存与 SoA 缓存是核心架构时，借用检查器护不住索引越界这类真正高频风险——继续 Rust 只是抱着「更安全」的心理安慰，增量编译仍慢一个数量级。

接下来，第四部分，【概念拆解卡】重写的真正导火索。

在讲什么问题，多态去函数化（polymorphic defunctionalization）长期出诡异 bug，OCaml 原型证明问题在编译器多阶段架构，修它等于重写大半个编译器。

核心机制，闭包捕获变量时零堆分配——做对可解锁内联级性能，做错则 bug 反复；团队选择 scratch-rewrite 而非忒修斯之船式修补。

关键理解，起点不是「嫌弃 Rust」，而是架构债务到期；语言迁移是顺带决策。

典型场景，多个贡献者不约而同要重写核心模块时，不如一次性彻底重构。

边界说明，Bun 的 AI 直接搬运在 Roc 行不通——他们要的是新架构而非忠实移植。

「要修好它，几乎等于要重写大半个编译器。」——Richard Feldman

接下来，第五部分，【决策/选型表】为何选 Zig 而非继续 Rust。

构建速度，预期明显更快，cargo 增量编译随代码量恶化

内存控制，分配器到处传递，契合 arena + SoA，生态默认全局单分配器 + Drop 隐式释放

生态相关性，独立 LLVM bitcode 序列化器等现成代码，编译器冷门需求库更少

unsafe 占比，1200 处/30 万行，Zig 对不安全代码兜底更多，unsafe 无法被当成「少数例外」隔离审查

接下来，第六部分，【跨概念对比表】内存损坏 bug 统计解读。

内存损坏 bug，21，10，绝对数不能直接比安全性

损坏位置，全在生成机器码，2 个 UAF 在错误信息渲染，借用检查器护住了编译器本体

非内存 bug，2575，421，架构重写顺带减少逻辑 bug

若用 Rust 借用检查，—，2 个 UAF 可编译期拦截，对 18 个月整体影响微乎其微

接下来，第七部分，【方法/工具卡】编译速度与增量构建实测。

核心思路：Zig -fincremental 目标是把改动反馈压到毫秒级，但需等稳定版修复 0.16.0 的增量失效 bug。

关键数据：Rust 1.97 增量 3.4 秒 vs Zig 0.17 预发布版增量 0.035 秒（约 100 倍）；Rust 1.85，得到1.97 同期优化也把 10 秒砍到 3.4 秒。

操作启示：评估迁移收益时同时看「语言切换」与「工具链自身进化」两条曲线，避免静态快照误判。

零解析缓存：数据结构用 32 位索引 + SoA 布局，磁盘数据可原样 mmap 进内存，第二次 roc check 近乎 memcpy 速度——代价是索引查错数组类似 UAF，借用检查器管不着。

避坑：0.16.0 稳定版 -fincremental 失效，需 0.17 预发布或等下一稳定版。

接下来，第八部分，【避坑清单卡】语言迁移中的误判。

坑名，把「Rust 版内存 bug 更多」当成 Rust 失败

原因，编译器 bug 分「编译器自身」与「生成代码」两类，混淆统计会得出错误结论。

解法，用 issue 标注区分 bug 归属，再谈语言工具链价值。

严重程度，致命——错误归因会导致错误的技术战略。

坑名：用 Bun 的结论套 Roc——Bun 痛在 JS GC 与手动内存混用，Roc 根本不碰追踪式 GC。

坑名：期待 Drop universally 好用——对 arena 分模块管理，Drop 反而是 Rust 生态里的痛点。

接下来，第九部分，【心法/原则卡】生态适配而非语言优劣。

原则，Rust 生态为 Bun 那种写法优化，Zig 生态为 Roc 这种写法优化——没有谁更先进。

为什么重要，Drop vs defer、全局分配器 vs 传递分配器，同一特性在不同项目里命运相反。

怎么落地，重写前先写清架构约束清单（arena 数量、unsafe 比例、LLVM 耦合方式），再选语言而非反过来。

适用边界，Feldman 仍怀念 Rust 的测试自动内存管理、多态、私有字段、向后兼容——Zig 不是全面替代。

「没有更好的语言，只有更适合具体工程约束的语言。」

接下来，第十部分，总结与行动。

结论

Roc 重写起因是多态去函数化架构债务，487 天 scratch-rewrite，非 AI 搬运式移植。

选 Zig 基于构建速度、分配器粒度、LLVM 生态复用、高 unsafe 占比四因素。

内存损坏统计需区分编译器本体 vs 生成代码；Zig 版 UAF 仅 2 个且在错误渲染，借用检查器本可拦截。

Zig 增量 35ms vs Rust 3.4s；零解析磁盘缓存是意外架构红利。

Bun（Zig，得到Rust）与 Roc（Rust，得到Zig）用同一论据得出相反结论，均合理。

看到「X 语言重写成 Y」新闻时，先问：他们要解决的到底是什么架构问题？

评估编译器类项目时，统计 unsafe 占比与 bug 归属，别只看 headline 数字。

对比增量构建时，同时跟踪目标语言与源语言工具链的 release 进化。

若考虑索引式磁盘缓存，提前设计索引-数组配对的安全策略，别指望借用检查器兜底。
