欢迎收听每日技术学习语音讲解。本期主题，Rust 官方发文：AI 可以审代码，但不能写代码。标签包括rust-lang/rust、LLM 政策、开源治理、披露义务。本次讲解预计时长 约 9 到 10 分钟，共 10 个部分。好，我们开始。

一句话概括。本文解决的核心问题是：当 AI 让「漂亮 PR」不再等于「作者真懂代码」、评审资源被进一步挤压时，Rust 核心仓库如何用成文政策划定「可辅助思考、不可代为创作」的边界，并对不同角色给出可执行规则。

接下来，第一部分，核心概念关系。

关系脉络如下：三类恶化问题，信号失效 · 评审过载 · 机械搬运，然后允许辅助，问 · 析 · 检 · 评，然后禁止创造，生成合入代码，然后披露 + 更高门槛，测试 · 非关键路径

接下来，第二部分，认知纠偏。

认知纠偏

常见误解：Rust「封杀 AI」或「全面拥抱 AI」。政策既不禁令也不友好——主语是单个核心仓库；允许 LLM 辅助评审与分析，但对生成代码设比人类更高的准入标准。

接下来，第三部分，反驳。

反驳

对立视角：AI 原生贡献者 · 「工具中立、效率优先」派

把 LLM 生成代码拒之门外，评审员仍要审 1281 个 PR——政策保护的是旧时代「精致即理解」的仪式感，却可能把愿意用 AI 加速修复的新贡献者挡在门外，评审瓶颈并不会因此消失。

接下来，第四部分，【概念拆解卡】rust-lang/rust LLM 政策边界。

在讲什么问题，1281 个开放 PR 背景下，LLM 让写代码变容易但评审判断「方向对不对、值不值得做」的能力无法被代码替代，精致产出不再证明理解与长期投入。

核心机制，编译器、libs、types、rustdoc、bootstrap 五团队联合采纳 forge 政策——公开 LLM 文本必须披露；生成代码须预先沟通、非关键路径、完善测试；健全性改动强烈劝阻 LLM。

关键理解，评审默认前提是「跟想把事情做好的真人对话」；机械把评审意见喂给 LLM 再贴回，破坏信任且浪费所有人时间。

典型场景，用 LLM 翻译邮件、找糟糕报错、分析 RFC 遗漏——属尊重社区运作的正面用法。

边界说明，不适用于 rust-lang 其他仓库；不属于四类受影响人群者无需改变工作方式。

原文：「可以用 LLM 来提问、分析、提炼、精炼、检查、建议、评审，但不能用来创造。」

接下来，第五部分，【跨概念对比表】Go / Zig / Linux Kernel / Rust 立场。

生成代码，严格限制 + 更高标准，不接受 AI 为共同作者，行为准则禁止一切 LLM 内容，工具中立，看怎么用

披露，公开 LLM 文本硬性披露，强调人负全责，禁令式，文档指引辅助使用

治理风格，政策留修改接口、无独裁者，邮件列表争论版权责任，一刀切禁止，相对宽松

共同关切，工具可加速产出，理解与责任必须落在具体的人身上

接下来，第六部分，【决策/选型表】不同角色如何应对。

落地建议：合入前对照 forge 政策「允许」章节与 rustc-dev-guide LLM 指引；PR 模板将询问是否 LLM 生成，减少争议。

Issue 报告者用 LLM，披露并标出 LLM 生成段落，禁止未标注公开 LLM 评论，未标注粘贴 LLM 输出，评审员无义务阅读未披露内容

提交 LLM 生成代码，预先沟通 + 完善测试 + 披露，门槛高于人类提交，无测试豁免，关键路径/健全性改动用 LLM，即使专家也被强烈劝阻

评审员，不合规可直接关闭并引导至 LLM 频道，是否 LLM 生成由作者声明，非风格指控，凭「读起来像 AI」当面指控，风格不能作为证据

私下自用，不公开发布则无需披露，政策针对公开协作场景，把私下生成当公开提交不说明，隐瞒 AI 参与违反规则

接下来，第七部分，【避坑清单卡】社区信号与评审陷阱。

坑名，把「打磨精致的 PR」当加入信号

原因，LLM 让精美 PR 不再代表心血、理解或长期留存意愿；Agent 场景甚至可能无持续跟进的人。

原文说法：团队通常不愿轻易关闭 PR，因代表别人心血——这一假设已被 LLM 动摇。

解法，评审重心放在方向、演变规划与作者是否理解代码，而非 diff 本身。

严重程度，致命——误判信号会浪费双向巨量时间。

另一坑：因对方使用 LLM 而骚扰——无论是否违规，Rust 行为准则在任何互动中都必须遵守。

接下来，第八部分，【心法/原则卡】政策而非禁令的治理哲学。

原则，无共识时先画清界线、用真实数据检验——跟踪 AI 贡献是否有价值、贡献者是否学习与留下。

为什么重要，项目无「仁慈独裁者」；内部对 AI 价值与危害分歧巨大，但共享「专家深度 + 包容欢迎」双重价值。

怎么落地，接受政策比各自猜测更好；「大家都有点不满意」倒逼持续改进治理；考虑成立 LLM 政策子团队降低改规成本。

适用边界，部分条款难「抓现行」是刻意设计——画界线而非抓每一次违规；回应时才考虑动机。

接下来，第九部分，总结与行动。

结论

政策主语是 rust-lang/rust 核心仓库，非 Rust 整体官方立场；影响评审者、LLM 代码提交者、LLM 辅助 issue 者与公开引用 LLM 输出者。

动因是三类恶化：精致产出≠理解、写容易评更难、机械复制粘贴浪费时间与信任。

核心红线：可辅助问析检评，不可创造；公开 LLM 文本必须披露，生成代码门槛高于人类。

用公开成文规则替代私密频道与潜规则，让新人可查阅、评审可引用。

横向看 Go/Zig/Kernel 风格各异，共同关切是责任必须落在具体的人。

贡献 rust-lang/rust 前阅读 forge.rust-lang.org/policies/llm-usage.html。

任何公开评论/PR/issue 中的 LLM 内容一律标注来源与生成段落。

拟合入 LLM 代码前先沟通路径与测试计划，避开健全性关键改动。

评审时关注作者理解与方向，勿仅凭代码风格指控 AI。

不合规 PR 可关闭并引导至官方 LLM 辅助交流频道。

总结：

行动清单：

关键认知转变：开源协作里「代码漂亮」从信任信号降级为可疑信号；治理重点从审 diff 转向审人与方向，披露与更高标准是为保住「真人对话」前提。
