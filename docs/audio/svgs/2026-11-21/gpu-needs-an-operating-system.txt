一句话概括。本文解决的核心问题是：大模型推理时 Tensor Core 大量闲置并非「卡不够强」，而是 Decode 访存受限且缺乏微秒级抢占与多维资源治理；OpenInfer 提出 GPU OS（Slack 预算、可暂停 Kernel、准入控制），实验在 Kimi K2 前台下约回收 24% 算力、延迟仅增 1.6%——但真实训练/评估后台仍受显存与缓存竞争制约。

接下来，第一部分，核心概念关系。

关系脉络如下：Prompt Prefill，然后矩阵密集，然后逐 Token Decode，然后读权重等待，然后Tensor Core 空转

接下来，第二部分，认知纠偏。

认知纠偏

误解：买更多 GPU 就能填满算力。原文强调小 Batch Decode 是 Memory-bound，且现有 MIG/Green Context/Stream Priority 不能微秒抢占——后台 Kernel 可能让前台延迟放大 10 倍（极端实验 1ms 后台 ，得到 AMD MI300X 上或等 200ms）。

接下来，第三部分，反驳。

反驳

对立视角：「多买 GPU 比改软件栈便宜」

当 Tensor Core 活跃个位数、卡价与电费已封顶时，线性加卡无法消解 Decode 访存天花板；且缺抢占的粗暴共置会直接把 p99 打穿。论文表明在约束内可挖约四分之一算力——忽视 OS 层等于长期为闲置 SM 付租金。

接下来，第四部分，【概念拆解卡】Slack：前台性能余量即后台预算。

在讲什么：如何在保证在线 SLO 的前提下塞进后台任务？

关键理解，若推理基准 40ms、允许延迟涨 6%，则 Slack = 42.4 − 40 = 2.4ms；GPU OS 在此预算内调度后台，而非固定分区静态切卡。

关系：类比 CPU 时间片，但 GPU 需同时治理 SM、显存带宽、L2、设备内存、PCIe/NVLink、功耗。

落地：为每条在线路径定义 p99 延迟 × (1+ε) 为硬约束，后台准入由 Cost Model（L4）+ Admission（L5）裁决。

边界：Slack 过小或波动大时不应塞训练；仅适用于可预测的前台负载曲线。

原文：「在不突破预算的情况下，尽可能多地安排后台工作。」

接下来，第五部分，【跨概念对比表】MIG / Green Context / Stream Priority vs GPU OS。

粒度，固定实例分区，限制 SM 数量，队列优先级，Kernel 片段级动态分配

抢占，重分区常需重置 GPU，无真抢占，低优 Kernel 难被中断，5–20μs 级暂停恢复

带宽/缓存，部分隔离，不完全解决竞争，基本不管，Resource Governor 全栈 QoS

适用，租户硬隔离，粗力度前后台切分，简单优先级，前台 SLO + 后台填缝

接下来，第六部分，【方法/工具卡】六层 GPU OS 架构。

L0 芯片：快速暂停信号、内存优先级、动态分区硬件原语。

L1 Kernel 规范：短片段、可暂停点、状态保存、资源声明（算力/带宽/缓存）。

L2 On-GPU Scheduler：片段映射到 SM。

L3 Resource Governor：限制后台对 L2/显存/传输的干扰。

L4 Cost Model + L5 Admission：预测对前台影响，决定后台能否入场及配额。

编译器角色：Triton/CUTLASS 需自动生成多分区版本与安全暂停点——程序员手工不切现实。

接下来，第七部分，【决策/选型表】后台工作负载与回收预期。

合成寄存器 GEMM，约 23% SM，约 +5.1%，验证调度机制上限

真实 FP8 GEMM，约 9%，约 +4.7%，更接近算子，仍受缓存竞争

Resident Kernel + 16 请求，约 24%，约 +1.6%，研究型潜力，非通用训练

完整训练/评估，论文未无损验证，风险更高，需独立验证带宽隔离

接下来，第八部分，【避坑清单卡】把论文数字当生产承诺。

坑 1：只看 SM 回收率，忽略 L2/DRAM 争用 ，得到 前台 p99 仍劣化。解法：监控带宽与缓存 miss，不单看 Tensor Core%。

坑 2：后台 Kernel 不可暂停 ，得到 抢占失效。解法：强制片段化编译 + 驻留循环自调度（Resident Kernel 研究路径）。

坑 3：24% 回收来自合成任务。解法：用真实 FP8/训练 step 复现实验再定 SLO。

坑 4：L4/L5 尚未完整实现。解法：生产先用 Green Context + 严格准入，等待厂商微秒抢占与显存优先级。

接下来，第九部分，【心法/原则卡】竞争点从「卡数」到「利用率操作系统」。

原则，硬件够强后，胜败在能否让每张卡多角色、可让渡、可观测。

反面：24×7 独占推理实例 + 夜间空转训练集群 = 重复资本支出。

落地：白天在线推理保 Slack；夜间提高后台配额；新请求触发抢占链。

边界：预印本，跨模型通用性与真实训练共置仍待证；需芯片/OS/编译器/框架四方协同。

接下来，第十部分，总结与行动。

结论

推理闲置主因是 Decode 访存瓶颈，不是峰值算力不足。

现有分区/优先级机制不足以微秒抢占与全栈资源 QoS。

GPU OS 用 Slack + 可暂停 Kernel + 六层治理回收后台算力，实验约 24%@+1.6% 延迟（研究场景）。

真实训练共置仍需硬件抢占、显存优先级与成本模型成熟。

用 Nsight 等区分 Tensor Core 活跃率与整卡利用率，确认是否 Memory-bound。

为在线服务定义 Slack（如 +6% p99）并禁止无暂停长 Kernel 与前台共卡。

试点 Green Context 双区 + 合成/真实 GEMM 复现 9–23% 回收曲线。

跟踪编译器片段化与厂商微秒抢占路线图，避免自建不可维护调度 hack。

将 24% 视为机制上限警示，而非训练混布 SLA。
