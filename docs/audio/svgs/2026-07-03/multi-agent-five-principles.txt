一句话概括。本文解决的核心问题是：当复杂任务出现时，团队为何本能地堆砌多 Agent，以及从工程稳定视角判断——什么场景该用单 Agent、什么场景才值得拆多 Agent，以及若必须拆分应遵循哪五条原则。

接下来，第一部分，核心概念关系。

关系脉络如下：规则系统，规则明确优先，然后Workflow+LLM，企业首选落点，然后单 Agent，长链路决策，然后多 Agent，拆分收益明确时

接下来，第二部分，认知纠偏。

认知纠偏

常见误解：「人类靠分工搞定复杂任务，AI 也该一样」—— 人类分工解决能力分散，技术拆分解决工程控制；看着像一回事，设计差得很远。换几个 Prompt 角色名不等于真正的多 Agent。

接下来，第三部分，反驳。

反驳

对立视角：「多 Agent 架构师」/ 追求组织感的产品团队

复杂任务天然需要分工——采购、风控、审批本就是多角色协作，强行塞进单 Agent 会让上下文爆炸、无法并行，多 Agent 是工程上唯一可扩展的路径。

接下来，第四部分，【概念拆解卡】Agent 与多 Agent 的工程定义。

在讲什么问题，什么叫真正的 Agent？什么叫有价值的多 Agent？

核心机制，Agent = 以模型为决策核心、工具为执行手段、状态为粘合层的任务执行单元（目标+状态+工具+反馈闭环）。多 Agent = 同一目标下多个相对独立决策单元，通过串行/并行/分层/自由裁决协同。

关键理解，真正有价值的差异在边界：工具是否不同、权限是否不同、输入上下文是否不同、评价标准是否不同、失败模式是否不同——若都没变只是换角色名，复杂度涨了能力结构没拉开。

典型场景，单 Agent 适合中短链路需统一判断；串行多 Agent 适合规则清晰的信息链；并行适合多路检索；分层适合平台型编排。

边界说明，自由多 Agent（节点自由裁决）适合创意脑暴但评价标准难设计、成本高，不宜作为企业首选。

接下来，第五部分，【跨概念对比表】五种多 Agent 形态。

上下文连续性，高，责任集中，低，交接损耗大，中，需合并，中，调度层风险，低，难追踪

核心优势，链路易追踪，步骤边界清楚，吞吐高、并发，治理与权限分层，高不确定性输出

主要劣势，长链路上下文负担，错误易级联，合并与冲突处理难，调度层易成单点，评价难、成本高

适用场景，持续决策型任务，规则清晰处理链，多路检索/多候选，复杂任务编排平台，创意脑暴

一句话结论，默认优先选项，慎用，交接成本高，并发而非组织协作，需成熟调度层，非生产首选

接下来，第六部分，【避坑清单卡】多 Agent 为何现在普遍不太行。

坑 1 — 决策连续性断裂：后一个 Agent 看到的是「二手信息」（摘要/截断），隐性判断传几次就变味；每步合理但整体不一致。

坑 2 — 交接成本被低估：真正成本在任务拆分、状态同步、摘要生成、冲突裁决、链路排障，不在模型调用次数。

坑 3 — 复杂度涨收益没跟上：路由、上下文治理、冲突判定、监控定位——变成维持协同本身，而非推进业务。

坑 4 — 基础层不扎实就上多 Agent：任务建模、状态管理、验证闭环、边界控制没做好，多 Agent 是复杂度放大器。

严重程度，致命——采购审批案例中，分类归错则全链跑偏，各节点日志很多但根因定位极慢。

原文：「一个模糊的任务交给一个 Agent 结果可能不稳定；拆成五段交给五个 Agent，只会得到五段更难追责的不稳定结果。」

接下来，第七部分，【决策/选型表】什么项目适合 Agent / 多 Agent。

规则明确、步骤固定，规则系统 / Workflow+LLM，成本最低、落地可行性最高，直接上多 Agent，交接成本远大于收益

长链路+工具调用+可验证，单 Agent + 工具链，上下文连续，有闭环可迭代，按角色名硬拆，决策连续性断裂

上下文污染、子任务可并行，多 Agent（信息隔离/并发），拆分为隔离信息或并发执行，为「显得专业」而拆，复杂度涨、收益不明

工具/权限/评价标准明显不同，多 Agent（职责边界清晰），检索/执行/验证真正分离，同模型换 Prompt 名，假多 Agent，无系统意义

开放战略、高风险核心工程，人工主导 + Agent 辅助，评价模糊或责任不可审计，自主执行权全交 Agent，局部合理、全局危险

接下来，第八部分，【方法/工具卡】必须做多 Agent 时的 5 条原则。

原则 1 — 按系统边界拆，不按角色名拆：先看哪部分需不同权限/工具/输入视角/并行/独立验证，再定 Planner/Reviewer 等角色。

原则 2 — 高耦合决策留在一个连续执行体：全局策略、高风险动作、风格一致性、强依赖历史状态的决策、例外路径不宜过早拆散。

原则 3 — 中间态结构化，不靠自然语言转述：用 TaskState（objective、verified_facts、unresolved_questions、candidate_actions、rollback_point 等）替代长文本互传。

原则 4 — 生成与验证分离：一节点生成动作，另一节点验证结果；流程：生成，得到执行，得到验证，得到裁决，职责隔离而非角色越多越好。

原则 5 — 可观测、可追踪、可回滚：能还原谁做的决定、基于什么上下文、调了哪些工具、出错能否退回安全状态。

Claude Code 真正值得借鉴的不是「支持多 Agent」，而是 progress file、git commit 回退、端到端测试验证——决定下限的是执行系统，不是角色数量。

接下来，第九部分，【心法/原则卡】克制复杂度。

原则，更现实的建设顺序是 Workflow+LLM 打牢 ，得到 单 Agent 做深 ，得到 只在拆分收益非常明确时引入多 Agent。

为什么重要，适合 Agent 的项目有明确特征：链路长、需持续决策、有工具、有验证闭环、状态可管理、风险可约束——缺一则先补基础层。

怎么落地，采购审批案例优先方案 A（单 Agent + 事实层 facts + decide + execute + verify + persist），而非六个角色各管一角的方案 B。

适用边界，多 Agent 落地可行性评为「中」——只有拆分收益能覆盖交接与治理成本时才进入。

接下来，第十部分，总结与行动。

结论

多 Agent 不是银弹——人类分工与技术拆分的动机不同，换角色名不等于系统能力拉开。

当前多 Agent 普遍不稳的根因是决策连续性断裂、交接成本被低估、基础层不扎实。

建设顺序应为规则 ，得到 Workflow+LLM ，得到 单 Agent ，得到 多 Agent，多数企业应先落在 Workflow+LLM。

仅在上下文污染、子任务可并行、职责边界明确（工具/权限/评价不同）时考虑拆分。

若必须做多 Agent，五条原则：按边界拆、高耦合决策不拆、中间态结构化、生成验证分离、可观测可回滚。

审视当前「多 Agent」设计：工具、权限、评价标准是否真正不同，还是同模型换 Prompt 名。

为单 Agent 补齐任务建模、状态持久化、验证闭环、人工接管条件四项基础层。

Agent 间交接改用 TaskState 结构化字段，禁止仅靠自然语言摘要传递关键决策语境。

借鉴 Claude Code：进度写 progress file、动作可 git 回退、用端到端测试而非模型猜状态。

新需求立项时先问：拆分收益能否覆盖交接与治理成本？不能则保持单 Agent 或 Workflow。
