欢迎收听每日技术学习语音讲解。本期主题，企业级 AI Coding 的 Harness 工程实战：8 个 Skill 串起全链路。标签包括Harness 工程、8 Skill 全链路、OpenSpec · SDD、团队 AI 协作。本次讲解预计时长 约 11 到 12 分钟，共 11 个部分。好，我们开始。

一句话概括。本文解决的核心问题是：当开发侧已把 AI 嵌入工作流、产品测试仍停留在口头沟通与手工点点点时，如何用 8 个 Skill 把需求，得到设计，得到开发，得到测试，得到验收，得到Bug 修复的产出标准化、收拢到同一 spec 目录，让环节之间自动流转而非各自为战。

接下来，第一部分，核心概念关系。

关系脉络如下：product，然后api，然后ui，然后page，然后test，然后qa，然后review，然后bugfix

接下来，第二部分，认知纠偏。

认知纠偏

常见误解：「个人 Cursor 提效够用了」。问题不在某个环节卡住，而是环节交接面站在不同角度表达——产品 PRD、AI 代码、测试 Excel 格式术语全不一致，扯皮成本比编码更高。

接下来，第三部分，反驳。

反驳

对立视角：Vibe Coding 拥护者 · 「流程会扼杀 AI 速度」

八个 Skill 加决策点停下来的功夫，够 vibe 两轮全栈上线——企业里返工三次的需求变更和测试扯皮，才是真的速度杀手。

接下来，第四部分，【概念拆解卡】五个团队级 AI Coding 痛点。

在讲什么问题，个人提效≠团队提效；框架六步走完了，落地仍卡在交接面。

核心机制，① 非开发岗位跟不上 ② 环节衔接断裂 ③ 需求反复返工（AI 第三版开始「改不动」）④ AI 识别不了变更范围 ⑤ 经验跟人走不跟项目走。

关键理解，解法不是更多文档，是把每个环节产出固定下来并自动流转——需求评审产出、接口对接产出、测试用例产出全部标准化。

典型场景，测试拿 Excel 说「12 功能点覆盖率不到一半，还有 2 个忘了写」——开发解释十分钟测试放弃的那一刻，作者开始写 Skill。

边界说明，Skill 是基础，多 Agent 并行是加速器——顺序不能反，先跑稳 3-5 个需求再拆并行。

接下来，第五部分，【方法/工具卡】spec 单目录收拢（OpenSpec 思路）。

方法名：spec/changes/<feature>/ 单目录 · 标签：规范驱动、可追踪、Review 友好

核心思路：每个需求的全部 Skill 输出收进同一目录，.spec.yaml 追踪各 skill 状态 pending，得到completed。

操作步骤，1) 复制 .spec.template.yaml ，得到 2) 各 Skill 末尾写入 product.md/api.md/... ，得到 3) 更新 .spec.yaml 状态 ，得到 4) 完成后归档到 archive/日期-feature/

落地建议：进度不用问人，打开 .spec.yaml 就知道卡在哪；Review 时所有上下文在一个目录，不用追着问「接口文档发哪了」。

接下来，第六部分，【心法/原则卡】每个 Skill 的三条共同设计。

设计一：先读 CLAUDE.md，不可跳过。 AI 不知道的事不会主动问；不喂约束就按训练数据「通用实践」来——最早 ui Skill 没加这条，生成全用 antd 原生而非项目封装组件。

设计二：有明确决策点，停下来等人。 全自动在企业场景是灾难。product 发现功能已做过，得到停；api 字段不清，得到标 [待确认] 不猜；bugfix 信息不全，得到暂停补充。

设计三：末尾挂「常见坑速查表」。 现象，得到原因，得到处理三列；review 发现新坑就补，下一个人加载 Skill 时自动变约束。bugfix 表例：修完引入新 Bug，得到回三步检查法逐条过边界。

接下来，第七部分，【决策/选型表】SDD 工具选型：为何 OpenSpec。

存量项目增量改造，OpenSpec，propose，得到apply，得到archive 轻量；npm 30 秒安装，Spec-Kit 七阶段门控，像瀑布，对存量太重

小团队敏捷，OpenSpec + 自研 Skill，不绑 GitHub 生态；Claude/Cursor 兼容好，Superpowers 作主流程，偏工具配置层，非协作主引擎

新项目大团队合规，Spec-Kit，七阶段门控严谨，OpenSpec 单独硬扛，流程约束可能不够

多项目 Skill 分发，sync.sh 统一推送，手动拷贝两个月必分叉，每项目手改 Skill，A 项目修了防重复，B 还在踩旧坑

接下来，第八部分，【跨概念对比表】四个底座机制。

SDD 闭环，CLAUDE.md，得到生成，得到Review，得到补规范，AI 没用 CustomSkeleton，得到规范没写是规范缺失不是 AI 错，每次跑偏是发现规范漏洞的机会

不清晰就停，不许猜、不许脑补，接口字段推断错，得到联调全炸，决策点兜住 AI 不会补位处

文档驱动防幻觉，先读 Context7 官方文档，代码从训练数据瞎编，从真实文档锚定而非记忆

spec 单目录，产出不散落，三个月后找不到需求对应文档，上下文不丢失是可追踪前提

接下来，第九部分，【避坑清单卡】三条血泪铁律。

坑1 · Characterization Test：改造老模块前先记录现有代码实际输出转断言；跳过则测试全绿但上线炸——最阴险，因为你测错东西了。

坑2 · 预期值必须字面量：expect(price).toBe("1.00")，不能在被测逻辑里重算 expected——算法有 bug 时 expected 跟着错，测试永远绿。

坑3 · 每批只做 1-3 个：一次生成 20 个组件/测试，一半跑不通整批不可信；慢就是快。

禁区（不做什么）：无 PRD 凭空拆任务；引入栈外依赖；顺手重构范围外代码；用 AI「没问题」代替人手验证；为一次性操作建 Skill。

接下来，第十部分，总结与行动。

结论

团队 AI Coding 瓶颈在环节交接面，不在单点编码速度——标准化产出+spec 单目录是核心解法。

8 Skill 是真实业务摩擦长出来的：qa 补测试断层，bugfix 补「根因说不清不许动手」。

三条共同设计（读 CLAUDE.md、决策点、坑表）比具体步骤更重要，是稳定运行的底层逻辑。

OpenSpec 适合存量增量改造；Skill 跑稳后再考虑多 Agent 并行。

先只做一个 Skill——痛点最重的：需求不清做 product，UI 差做 ui，Bug 反复做 bugfix。

Markdown 放 .claude/skills/：触发条件 + 步骤（标决策点）+ 常见坑。

建 spec/changes/ 单目录，哪怕只收两三个文件，用 yaml 标进度。

第一版别追求完美，review 会告诉你漏了什么；CLAUDE.md 是约束来源，Skill 管流程。

多项目用 sync.sh 统一推送，避免手动拷贝分叉。
