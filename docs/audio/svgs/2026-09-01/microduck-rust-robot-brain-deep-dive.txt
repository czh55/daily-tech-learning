接下来，第一部分，核心概念关系。

关系脉络如下：仿真训练，mjlab + PPO，然后ONNX 策略，61 维观测热切换，然后robotd 50Hz，意图，得到安全执行，然后7 守护进程，JSON-RPC/NDJSON

接下来，第二部分，认知纠偏。

认知纠偏

常见误解：「开源机器人 = ROS 堆栈」。Microduck 刻意不用任何应用框架，七个进程用 Unix Socket JSON-RPC 协作——在 ROS 遍地的机器人圈里，这是相当硬核的工程取舍。

接下来，第三部分，反驳。

反驳

对立视角：ROS 生态拥护者 · 「不用框架是自找麻烦」

七个手写进程在团队扩张和异构传感器接入时，会重演微服务早期的集成地狱——ROS2 的成熟工具链和社区包，才是机器人软件该走的正道。

接下来，第四部分，【概念拆解卡】Microduck 产品定位。

在讲什么问题，Reachy Mini 是会交互的桌面 AI；Microduck 是「会行动的物理 AI」——核心循环是仿真训练，得到真机部署，得到观察失败，得到再训练。

核心机制，25 cm 高、约 800 g、15 舵机、摄像头+深度+双 IMU，售价 399 美元；小尺寸让「摔倒」变成可承受的学习成本而非事故。

关键理解，学习动作本身很「糟糕」——必须不断尝试、摔倒、再尝试；做小便轻，失败通常只是「一只小鸭子躺在地板上」，还能自己爬起来。

典型场景，个人开发者在家做双足运动实验；社区在出厂行为之上叠加新策略。

边界说明，出厂行为只是起点，不是能力上限；严肃工业负载或大型人形仍需要更大平台。

原文：「Reachy Mini 是『会交互的 AI』平台；Microduck 是『会行动的 AI』平台。」

接下来，第五部分，【方法/工具卡】七守护进程分工与急救通道。

方法名：纯 Rust 多进程控制面 · 标签：嵌入式、高可靠、零框架

核心思路：一块板子七个进程，Unix Socket 通信；只有 robotd 能碰电机，configd/updaterd/btd 必须在 robotd 崩溃后仍可访问。

操作步骤，1) 客户端发「意图」而非直接电机指令 ，得到 2) robotd 50Hz 安全层裁决 ，得到 3) updaterd 整体替换发布+健康门禁 ，得到 4) 失败自动回滚

落地建议：OTA 采用「完整目录 releases/<版本>/ + current 符号链接」，健康检查失败自动换回旧版；启动计数器兜底重启死循环。

robotd，电机、运动学、策略、安全，唯一碰 15 舵机+IMU 串口

configd，WiFi、身份、手柄配对，robotd 挂了仍需配网

updaterd，签名校验、切换、回滚，系统最先开发的模块

btd/padd，蓝牙/手柄透传，无状态纯传输

mediad/tofd，音视频/WebRTC、深度传感，感知与媒体栈

接下来，第六部分，【决策/选型表】通信协议为何选 Unix Socket JSON-RPC。

板内 IPC，Unix Socket + NDJSON + serde，文件权限即访问控制；SO_PEERCRED 审计，TCP 0.0.0.0，手滑可能把固件更新暴露到公网

跨 BLE/WebRTC，同一 serde 消息类型复用，类型一致，不绑 D-Bus，D-Bus 类型系统，无法直接复用到其他传输

CPU 密集任务，spawn_blocking 隔离，签名校验/解压不卡 IPC，留在 tokio worker，更新时 status 查询失去响应

对比过的方案，自研 LinesCodec 分帧，对比过 jsonrpsee/varlink/zbus/axum/tonic，随手拉大框架，依赖数失控，30 依赖已够跨通道复用

接下来，第七部分，【跨概念对比表】控制系统 vs 强化学习流水线。

语言/运行时，纯 Rust + tokio，无 GC，Python + mjlab + rsl_rl，执行要确定性，训练要迭代速度

核心输出，安全执行意图、OTA 可靠性，ONNX 策略、61 维观测契约，部署接口稳定比仿真细节更重要

精细建模，进程隔离、回滚门禁，电压控制律、齿轮间隙、域随机化，sim2real 差距大半来自执行器精度

行为切换，robotd 加载策略，走路/起身/踢球/轮滑热切换，统一观测让运行时策略可互换

接下来，第八部分，【避坑清单卡】sim2real 与部署陷阱。

坑名，仿真用理想 PD，真机电压/摩擦/间隙全不同

原因，小舵机+轻机身尺度下，执行器模型误差主导 sim2real 差距。

原文说法：「宁可牺牲仿真速度，也要把理想 PD 换成真实电压控制律。」

解法，BAM M6 执行器模型 + 域随机化；Backlash 孪生任务建模 ±1° 齿轮间隙，观测维度不变。

严重程度，致命——策略在仿真里走得漂亮，真机一上就摔。

另一坑：把 CPU 密集操作（zstd/tar/签名校验）放在异步 worker——会导致更新过程中 IPC 卡死，status 查询无响应。

接下来，第九部分，【心法/原则卡】为什么网红机器人选 Rust。

原则，资源有限板子上跑 50Hz 实时环，内存安全与无 GC 停顿是硬指标。

为什么重要，走路机器人涉及可控电机与安全；类型系统在编译期挡掉悬垂指针类错误。

怎么落地，控制平面 tokio 异步等待，CPU 密集丢 spawn_blocking；手写 JSON-RPC 控制依赖数量。

适用边界，RL 训练仍用 Python 生态——Rust 管「不能随便崩」的执行面，不替代研究迭代。

接下来，第十部分，总结与行动。

结论

Microduck 爆火背后是双栈工程：Rust 零框架控制面（七进程、JSON-RPC、OTA 回滚）+ PPO sim2real 行为面（精细执行器建模、61 维热切换）。

架构核心约束：仅 robotd 触电机；configd/updaterd/btd 构成 robotd 崩溃后的急救通道。

通信选 Unix Socket NDJSON 是安全与复用性的权衡，而非「为了 Rust 而 Rust」。

小尺寸双足降低学习动作的成本，让社区能在出厂行为上持续叠加。

克隆 github.com/pollen-robotics/microduck 与 microduck_rl，对照架构文档与 infer_policy.py 理解热切换。

在 Hugging Face Space 仿真器试驾，建立对行为策略的直觉。

若做嵌入式控制：画出「谁能碰硬件」边界，OTA 必须带健康门禁与回滚。

若做 sim2real：优先建模执行器（电压、摩擦、间隙），而非先堆网络容量。

学习系统级 Rust：从 Unix Socket 权限模型与 tokio/spawn_blocking 拆分开刀。
