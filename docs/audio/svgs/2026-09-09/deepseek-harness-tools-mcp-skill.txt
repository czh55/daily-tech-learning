欢迎收听每日技术学习语音讲解。本期主题，DeepSeek Harness 入门很简单（三）——工具 / MCP / Skill 详解。标签包括内置工具、MCP 协议、创造模式、Skill 技能包。本次讲解预计时长 约 18 到 19 分钟，共 13 个部分。好，我们开始。

一句话概括。本文解决的核心问题是：Agent 的能力边界由哪些扩展机制构成——内置 Cordis 工具、MCP 外部服务接入与 Skill 标准作业流程包如何分工协作，以及创造模式下动态生成工具的完整生命周期与持久化策略。

接下来，第一部分，核心概念关系。

关系脉络如下：LLM，推理引擎，然后Prompt，系统指令，然后Tools，可调用能力，然后Agent，智能体，然后内置 Tool，tool-fs / tool-web，然后MCP，高德地图等，然后Skill，PPT 生成等

接下来，第二部分，认知纠偏。

认知纠偏

常见误解：「工具、MCP、Skill 是同一层东西，随便挂就行」。实际上三者职责截然不同——Tool 是 Harness 内置的原子能力（读写文件、联网搜索），MCP 是连接外部服务的标准协议（像 USB 统一接口），Skill 是封装领域 SOP 的 Markdown 知识包（教 Agent「怎么做」而非「能调用什么」）。创造模式动态生成的工具更是会话级临时的，不保存就随对话消失。

接下来，第三部分，反驳。

反驳

对立视角：企业安全与合规团队 · 「创造模式动态造工具不可控，必须全面禁用」

Agent 在创造模式里随手生成 Cordis 插件、注入 API Key、调用外部 MCP——没有代码审查、没有权限白名单、没有审计日志，等于给 LLM 开了无限制的 root 权限。合规要求所有工具变更走 PR Review 和 CI 扫描，动态生成完全绕过这套门禁，生产环境绝不允许。

接下来，第四部分，【概念拆解卡】Agent = LLM + Prompt + Tools。

在讲什么问题，大模型本身只能生成文本，无法读写文件、搜索网页或执行命令——Agent 是在模型之上叠加 Prompt 约束与工具调用能力的完整智能体。

核心机制，Harness 通过 Cordis 插件系统将每个工具注册为独立插件，Agent Loop 在推理过程中根据任务需要选择并调用工具，工具返回结果再注入上下文驱动下一轮推理。

关键理解，工具越多，系统提示词中的工具定义开销越大（标准模式约 20+ 工具、~1 万 Token）——扩展能力需按场景裁剪，而非无脑全挂。

典型场景，代码开发用 tool-fs 读写项目文件；信息检索用 tool-web 搜索；任务管理用 tool-todo 追踪进度；领域流程用 tool-skill 加载 Skill 包。

边界说明，内置 Tool 由 Harness 团队维护、开箱即用；超出内置能力范围才需接入 MCP 或自定义 Cordis 插件。

原文：「Agent 的本质就是 LLM + Prompt + Tools。模型负责思考，Prompt 负责约束行为边界，Tools 负责连接真实世界。」

接下来，第五部分，【方法/工具卡】内置工具与创造模式动态插件。

方法名：Cordis 插件体系 + 创造模式自然语言造工具 · 标签：内置能力 / 动态扩展

核心思路：Harness 预置 tool-fs（文件系统）、tool-web（网页搜索）、tool-todo（任务清单）、tool-skill（技能加载）等内置工具；创造模式下 Agent 可用元工具动态生成新 Cordis 插件（如 count_words 字数统计工具），用自然语言描述需求即可。

操作步骤，1) 标准任务直接用内置工具 ，得到 2) 切换创造模式 + Full access ，得到 3) 自然语言描述新工具（「写一个统计文本字数的工具」），得到 4) Agent 生成 Cordis 插件 YAML 并热加载 ，得到 5) 当前会话即可调用 ，得到 6) 满意后保存为仓库级插件实现持久化

落地建议：动态工具默认会话级临时——关闭对话即消失；团队复用需将生成的插件文件提交到项目 .cordis/ 目录，下次启动自动加载。

避坑：创造模式生成的工具未经审查直接用于生产——动态代码可能含安全隐患，务必人工 Review 后再持久化。

接下来，第六部分，【方法/工具卡】MCP 外部服务接入。

方法名：Model Context Protocol · 标签：外部 API / 标准协议

核心思路：MCP 被比作「AI 的 USB 接口」——统一协议让 Agent 连接任意外部服务（数据库、地图、支付等），无需为每个 API 写定制集成代码。

操作步骤，1) 在创造模式中描述需求（「接入高德地图，支持地点搜索和路线规划」），得到 2) 提供 API Key ，得到 3) Agent 生成 MCP Server 配置 ，得到 4) Harness 启动 MCP 子进程并注册工具 ，得到 5) 后续对话直接调用地图能力

落地建议：API Key 通过 Harness 环境变量或加密配置注入，勿硬编码进插件文件；MCP Server 独立进程便于隔离故障与权限。

与内置 Tool 的关系：内置 Tool 覆盖通用本地能力（文件/终端/搜索），MCP 覆盖需要第三方凭据和远程 API 的垂直服务——互补而非替代。

接下来，第七部分，【方法/工具卡】Skill 标准作业流程包。

方法名：Skill 技能系统 · 标签：SOP 封装 / 领域知识

核心思路：Skill 是将特定领域的标准操作流程（SOP）封装为 Markdown 文档包，通过 tool-skill 加载后注入 Agent 上下文——教 Agent「按什么步骤、用什么模板、注意什么约束」完成任务。

操作步骤，1) 从 ModelScope Skills 社区或自建仓库获取 Skill 包（如 PPT 生成技能），得到 2) 放置到项目 skills/ 目录 ，得到 3) Agent 通过 tool-skill 发现并加载 ，得到 4) 按 Skill 中的步骤、模板和检查清单执行

原文：「如果说 Tool 是 Agent 的手脚，MCP 是 Agent 的外部设备接口，那 Skill 就是 Agent 的操作手册。」

落地建议：团队高频流程（Code Review、发布检查、文档模板）优先沉淀为 Skill；与 MCP 互补——Skill 偏「知道怎么做」，MCP 偏「能调用什么外部能力」。

接下来，第八部分，【跨概念对比表】Tool vs MCP vs Skill。

本质，Cordis 插件原子能力，外部服务标准协议，SOP 知识 Markdown 包，能力 / 接口 / 流程

维护方，Harness 官方，第三方 MCP Server，社区或团队自建，内置最稳、MCP 最灵活

典型示例，tool-fs / tool-web / tool-todo，高德地图 / 数据库 / GitHub，PPT 生成 / Code Review，各管一层

创建方式，开箱即用，配置 MCP Server + API Key，编写 Markdown SOP 文档，创造模式可动态生成 Tool/MCP

持久化，随 Harness 安装，配置文件 + 进程管理，skills/ 目录文件，动态工具需手动保存

Token 开销，工具定义计入系统提示词，同上 + MCP 工具 schema，加载时注入 Skill 全文，按需加载、避免全挂

生命周期，永久，配置后持久，文件存在即可用，创造模式工具默认会话级临时

接下来，第九部分，【决策/选型表】扩展机制选型指南。

读写项目文件/执行命令，内置 tool-fs + 终端，零配置、权限可控、Harness 原生支持，自写 MCP 包装 shell，多一层进程开销且无必要

接入地图/支付等第三方 API，MCP Server，标准协议、凭据隔离、社区有现成 Server，创造模式硬编码 API 调用，难以复用、安全风险高

团队固定工作流（PPT/Review），Skill 包，纯 Markdown、版本可控、无代码执行风险，每次 Prompt 重复描述，不一致、Token 浪费

一次性定制小工具，创造模式动态生成，自然语言秒级产出、会话内即用，写完整 Cordis 插件仓库，过度工程、开发成本高

需跨项目复用的定制工具，保存为仓库 Cordis 插件，持久化、可 Review、团队共享，仅会话级临时工具，关闭对话即丢失

接下来，第十部分，【避坑清单卡】工具扩展常见陷阱。

坑名，创造模式动态工具未 Review 直接持久化

原因，Agent 生成的 Cordis 插件可能含未授权文件访问、命令注入或硬编码密钥。

解法，动态工具先在隔离环境试用；持久化前人工审查 YAML 与关联脚本；API Key 走环境变量注入。

严重程度，致命（安全与合规）

动态工具误当永久：创造模式生成的工具默认随会话销毁——忘记保存到 .cordis/ 目录，下次对话需重新生成。

Skill 与 MCP 混用不清：把需要实时 API 调用的能力写进 Skill Markdown 而非 MCP——Agent 只能「读流程」无法「调接口」。

工具全挂 Token 爆炸：标准模式 20+ 工具 + MCP 工具 + 多个 Skill 同时加载，系统提示词膨胀导致响应变慢、成本飙升。

接下来，第十一部分，【心法/原则卡】按需扩展、先内置后外挂。

原则，扩展 Agent 能力遵循「内置 Tool 优先 ，得到 MCP 接外部服务 ，得到 Skill 沉淀流程 ，得到 创造模式补缺口」四层递进，避免一上来就动态造工具。

为什么重要，每增加一层扩展，系统提示词和运行时复杂度同步上升；内置工具经过 Harness 团队安全审计，动态生成物则完全依赖 Agent 输出质量。

怎么落地，日常开发用极简/标准预设的内置工具；确需第三方 API 时配置 MCP；团队 SOP 沉淀为 Skill；仅当三者都不覆盖时才用创造模式造工具，且必须 Review 后持久化。

适用边界，个人实验可激进使用创造模式；企业生产环境动态工具须经安全审查并纳入版本管理。

原文：「动态工具就像草稿纸上的演算——有用但 ephemeral，真正要进生产的能力必须落盘为仓库插件。」

接下来，第十二部分，总结与行动。

结论

Agent = LLM + Prompt + Tools，Harness 通过 Cordis 插件体系将工具模块化注册。

内置 Tool（tool-fs / tool-web / tool-todo / tool-skill）覆盖通用本地能力，开箱即用。

MCP 是连接外部服务的标准协议（「AI 的 USB」），创造模式可配 API Key 快速接入高德地图等。

Skill 是封装领域 SOP 的 Markdown 知识包，教 Agent 流程而非提供 API 调用能力。

创造模式可自然语言动态生成 Cordis 插件（如 count_words），但默认会话级临时，须保存为仓库插件才持久化。

扩展遵循「内置 ，得到 MCP ，得到 Skill ，得到 动态造工具」递进，按需加载控制 Token 开销。

梳理当前任务所需能力，优先用内置 tool-fs / tool-web 解决，避免过早引入 MCP。

需要第三方 API 时，在创造模式中描述需求并配置 API Key，验证 MCP Server 可用后持久化配置。

将团队高频 SOP（PPT 生成、Code Review 等）从 ModelScope Skills 或自建仓库引入 skills/ 目录。

创造模式生成定制工具后，人工 Review 插件 YAML，确认无安全隐患再提交 .cordis/ 目录。

按场景选择 Agent 预设，避免标准模式无谓背负全部工具定义的 Token 税。

行动清单：

关键认知转变：Tool、MCP、Skill 不是「越多越好」的挂件清单，而是分层递进的扩展策略——创造模式的动态工具是快速原型手段，真正进入团队工作流的能力必须经审查后落盘为持久化插件。
