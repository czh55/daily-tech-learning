一句话概括。本文解决的核心问题是：当语言迁移从「数年百万美元工程」压缩到「几周甚至一个周末」时，团队应如何设计裁判系统、规则手册与验证循环，让 AI 修的是产出代码的流程而非逐文件打补丁。

接下来，第一部分，核心概念关系。

关系脉络如下：① 规则手册，依赖地图·差距清单，然后② 压力测试，迷你迁移试航，然后③ 全量翻译，实现·审查·修复，然后④ 编译，并行修错，然后⑤ 冒烟，崩溃分类，然后⑥ 行为对齐，测试·构建守护进程

接下来，第二部分，认知纠偏。

认知纠偏

常见误解：「让 Claude 逐文件翻译就能完成迁移」——Anthropic 案例表明，真正决定成败的是规则手册、依赖地图、对抗式审查与编译器/测试套件构成的机械化验证循环，而非单次 prompt 的翻译质量。

接下来，第三部分，反驳。

反驳

对立视角：保守工程派 / 「迁移烂尾史」亲历者

16.5 万美元 token 加 19 个合并后回归，换来的只是 2%–5% 性能提升——对多数团队，冻结路线图赌行为 100% 对齐，仍比渐进重构风险高一个数量级。

接下来，第四部分，【概念拆解卡】AI 代码迁移的本质。

在讲什么问题，大规模语言迁移为何突然从「三年之痒」变成「几周可完成」？关键变量是什么？

核心机制，工程师编写迁移规则与验证循环，智能体在循环内翻译，得到编译，得到测试，得到修复，直到新代码行为与原代码对齐；失败项自动进入任务队列，队列从磁盘状态重建，天然可断点续跑。

关键理解，你不是在修代码，而是在修产出代码的那个循环（loop）——旧代码本身就是需求文档，测试套件是天然裁判，编译/测试失败自动生成下一批任务。

典型场景，Bun 百万行 Zig，得到Rust（不到两周）、Mike Krieger Python，得到16.5 万行 TypeScript（一个周末）、Anthropic 一个月内迁移 10 个代码包。

边界说明，适合有客观验证标准（测试/编译/行为 diff）的迁移；无裁判时需先让 Claude 造一致性核查工具；Bun 迁移后仍有约 4% unsafe 代码，合并后曾发现 19 个回归——100% 行为一致是目标而非默认。

原文：当验证标准是客观的，模型可以连续几天对着一个「标准答案」死磕，而不需要人来仲裁质量。

接下来，第五部分，【方法/工具卡】六步迁移法实操流程。

方法名：Anthropic 六步迁移法 Claude Code

核心思路：规则先行、压力试航、全量并行翻译、编译/冒烟/行为三层机械化验证，人力集中在前期规则与审查设计。

操作步骤，① 建规则手册（先于差距清单）+ 依赖地图 + 差距清单，用怀疑论审查者审计 ② 3 文件迷你迁移压力测试规则（产出全部丢弃）③ 批处理全量翻译，实现用小模型、审查用大模型，不确定处标 // TODO(port) ④ 编排脚本全量编译，并行修复+对抗审查 ⑤ 冒烟测试崩溃分类修复 ⑥ 测试套件行为对齐，构建守护进程串行化昂贵重建。

选型条件，保留结构迁移（Jarred）适合逐文件对比压力测试；重新设计迁移（Mike）用对抗式审查攻击设计文档 + 可丢弃端到端试跑。

落地建议：任务队列机械化——「完成」= 输出文件已存在于磁盘；无现成测试套件时让 Claude 设计 7 场景一致性核查 + 端到端测试（Mike 连续四夜自主跑分）；开源工具包 github.com/anthropics/code-migration-kit-with-claude-code 可作起点。

避坑：压力测试产出必须全部扔掉——目的是打磨规则而非取得进展；不要盯着单个失败，注意力放在「规律」和规则手册扩充上；审查者意见不一致时交第三智能体裁决，反复出现的同类错误应改规则重生成而非逐文件打补丁。

接下来，第六部分，【跨概念对比表】Jarred 结构保留 vs Mike 重新设计。

压力测试，3 文件双智能体翻译 + 第三智能体 diff，对抗式审查设计文档 + 可丢弃端到端试跑，能否逐文件对比决定压力测试形态

编译器位置，编译留到第 4 步（cargo 分钟级），每轮循环都跑 tsc（秒级），编译成本决定融入循环还是独立阶段

验证裁判，现有 TypeScript 大型测试套件，自造 7 场景一致性核查 + 四夜 E2E，无裁判不是绊脚石，让 Claude 造一个

迭代策略，每阶段审查+关卡，结构保留，端到端跑三遍，前两次推倒重来，重设计迁移更依赖全局试跑迭代

接下来，第七部分，【决策/选型表】何时启动语言迁移。

changelog 反复内存 bug / 长期性能瓶颈，评估 AI 辅助迁移，迁移理由不再需「生死攸关」，最坏结果是删分支重来，继续忍受技术债，成本账本已变，搁置项目可能已划算

构建矩阵每次发布等 30 分钟，优先迁移构建链（Mike 案例），编译 8 分钟，得到2 秒，启动快 6 倍，可下线部署流水线，仅优化 CI 缓存，语言/工具链根因未解决

无测试套件的老旧代码库，先造裁判再迁移，无退出条件=无成功标准；Claude 可写一致性核查，直接全量翻译，90% 行为一致比不迁移更糟

预算敏感的小团队，小模型实现+大模型审查，Bun 迁移约 16.5 万美元 token；需有意识设计循环，全程 Opus/Fable，token 消耗集中在循环次数

生态萎缩的原语言，尽快启动规则手册阶段，招聘池与库生态权重上升（AI 抹平语言学习门槛），无限期维护双栈，职业风险与并行维护成本累积

接下来，第八部分，【避坑清单卡】迁移流程常见陷阱。

照本宣科（致命）：每次迁移都不一样，指南是起点，动手前须与 Claude 规划自己的方案。

差距清单先于规则手册（致命）：差距清单本质是规则覆盖不到的部分，顺序颠倒会导致审计混乱。

手动给代码打补丁对抗规则（小心）：审查者反复抓到同类错误时，应在规则手册加一条并重生成受影响文件，而非逐文件修补。

多智能体各自触发构建（小心）：构建守护进程是唯一允许重建二进制的进程，避免重复昂贵操作。

智能体过于谨慎不敢改（可忽略）：用直白强硬提示词告知编译器会在下一步兜底纠错。

原文：让审查对抗化，让验证机械化——脚本（编译器、diff、测试套件）当裁判，不要把人当质量仲裁。

接下来，第九部分，【心法/原则卡】修流程不修代码。

原则，人力前置到规则手册与压力测试，后期看着任务队列自己跑完。

为什么重要，逐文件人工审 PR 无法支撑百万行规模；机械化队列 + 对抗审查才能把偏差变成可追踪任务。

怎么落地，① 分类现有测试并改写为可移植外部断言 ② 验证裁判能抓坏代码 ③ 8 类失败模式子智能体审查规则手册 ④ 顾问模式组合不同档位模型优化 token。

适用边界，需要数万到数十万美元 token 成本（Bun 约 16.5 万刀）；生产合并前须 CI 100% 通过，合并后仍可能发现回归需修复。

成果参考：Bun 迁移后内存 6745MB，得到609MB（降 91%）、二进制体积减 19%、性能提升 2%–5%。

接下来，第十部分，总结与行动。

结论

AI 代码迁移的关键不是逐文件翻译，而是设计规则手册 + 机械化验证循环，让编译器/测试套件当裁判。

六步法：规则与差距清单 ，得到 压力试航 ，得到 全量翻译 ，得到 编译 ，得到 冒烟 ，得到 行为对齐，前置须造可移植裁判系统。

审查对抗化（多智能体互审+裁决）、验证机械化（磁盘队列可断点续跑）是 Anthropic 十条迁移的共通模式。

成本从数百万美元数年降至数万–数十万美元数周，迁移理由不再需「生死攸关」。

无现成测试套件时，一致性核查 + 自造 E2E 测试可补齐裁判缺口。

列出团队忍了很久的迁移候选库，用 Claude 评估六步流程与依赖地图复杂度。

克隆 code-migration-kit-with-claude-code，从 3 文件压力测试打磨规则手册开始。

设计任务队列：完成判定 = 磁盘输出存在，实现用小模型、审查用大模型。
