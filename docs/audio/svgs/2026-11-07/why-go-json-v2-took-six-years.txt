一句话概括。本文解决的核心问题是：一个在生态中导入量排名前五的标准库 JSON 包，为何不能「修 Bug」而必须花六年另起 v2，以及 json/v2 与 jsontext 分层、实验期到稳定期时间线对大型基础设施演进的启示。

接下来，第一部分，核心概念关系。

关系脉络如下：原型 2020，然后社区 Proposal，然后Go 1.25 实验，然后1.27 稳定

接下来，第二部分，认知纠偏。

认知纠偏

误解：JSON 很简单，重写是拖延。实际上障碍是Go 1 兼容性承诺下既有行为即契约——大小写宽松匹配、nil slice 序列化等「缺陷」已嵌入无数生产系统。

接下来，第三部分，反驳。

反驳

对立视角：「够用就行」/ 第三方 JSON 库忠实用户

六年磨一剑的标准库 v2 对已在 sonic 或 jsoniter 上押注的团队只是增加认知分裂——除非官方把生态工具链默认切到 v2，多数人仍会停留在 v1 又一个六年。

接下来，第四部分，【概念拆解卡】为何不能原地修 encoding/json。

在讲什么问题，旧版 json 的设计债能否用补丁偿还？

关键理解，问题含严格性不足、API 难扩展、流式处理弱、性能结构瓶颈；任意行为变更可能 break 依赖方。

和其他概念关系：v2 与 v1 通过共享底层实现长期共存，而非大爆炸替换。

怎么落地用：新服务优先评估 json/v2；遗留系统保持 v1 直至有明确迁移收益。

边界说明，生态第三方库、代码生成器迁移节奏未必跟得上 Go 版本。

原文依据，「有些问题不是修复几个 Bug 就能解决的，而是需要重新设计 API。」

接下来，第五部分，【方法/工具卡】json/v2 + jsontext 两层。

核心思路：把语法层（jsontext：流式读写、Token）与语义层（v2：映射 struct、选项）拆开，便于 protojson 等共用底层。

操作步骤，① 读 Go 官方博客《A new Go API for JSON》，得到 ② 在非关键服务试 import json/v2 ，得到 ③ 对照 v1 行为差异表跑回归 ，得到 ④ 渐进替换热路径或新生成代码。

选型条件，需要更严格 JSON、更好流式、或可预测序列化语义的新项目。

避坑，假设 v2 与 v1 输出字节级一致——这正是不能原地改 v1 的原因。

对比相邻方法，社区 jsoniter、sonic 等第三方——标准库 v2 目标是统一实现减少碎片。

原文引用：六年交付的不只是一个新 JSON 库，更是标准库演进方法论。

接下来，第六部分，【跨概念对比表】v1 vs v2 关切点。

兼容性，历史行为冻结，新语义可更严格，并行而非替换

架构，一体 API，语法/语义分层，易扩展、可共享

流式，有限，jsontext 强化，大 JSON / 管道友好

迁移，默认，显式 opt-in，团队需计划窗口

接下来，第七部分，【决策/选型表】何时迁移 v2。

2026 起新 Go 服务，评估 v2 默认，1.27 已稳定，盲目 v1「习惯」，错过流式与严格性

依赖宽松匹配遗留 API，暂留 v1，行为契约，强行换 v2 无测，静默产出差异

Protobuf JSON 互操作，关注共享 jsontext，Joe Tsai 动机线，各写一套 parser，重复与安全面

性能敏感网关，benchmark 后决定，结构优化在底层，假设必快 N 倍，工作负载相关

接下来，第八部分，【避坑清单卡】标准库迁移。

坑名，认为「稳定」等于「与 v1 相同」。原因：v2 故意修正语义。解法：黄金文件测试对比输出。严重程度：致命。

坑名，全公司一刀切升级 Go 版本。原因：依赖树未就绪。解法：按模块滚动，保留 v1 构建标签期。严重程度：小心。

坑名，忽视六年里的社区 Proposal 讨论。原因：重复踩已决议的设计取舍。解法：读官方时间线图与 proposal 评论。严重程度：可忽略。

接下来，第九部分，【心法/原则卡】大型基础设施演进。

原则，被海量依赖的组件，演进路径是新 API + 共享实现 + 漫长实验，不是勇敢 break。

为什么重要，Go 导入量前五的包动一根线牵动百万模块。

怎么落地，在自己维护的「准标准库」级组件上预演：v2 包名、兼容层、多年实验旗标。

适用边界，内部小库仍可快速 break；边界随下载量上升而硬化。

原文支撑：六年沉淀的是工程文化：兼容性、社区协作、分层架构一并交付。

接下来，第十部分，总结与行动。

结论

encoding/json 的历史包袱与 Go1 承诺使「修旧库」不可行，催生并行 v2。

2020–2026 时间线覆盖原型、公开讨论、Go 1.25 实验与 1.27 稳定。

jsontext 与 json/v2 分层统一底层，服务流式与 protojson 等场景。

迁移关键是行为差异测试与渐进 opt-in，而非一夜之间替换。

案例价值在于标准库级重构的节奏与治理，不止 JSON 本身。

阅读 go.dev 博客《A new Go API for JSON》与官方时间线图。

在分支上对核心 struct 跑 v1/v2 序列化 golden test。

新模块默认 Go 1.27+ 并记录选用 v2 的 API 面。

跟踪 Daniel Martí / Joe Tsai 相关 talk 了解 jsontext 细节。

把「不能改行为只能新包」原则写进自家公共库治理文档。
