一句话概括。本文解决的核心问题是：在年均不到 20 小时的 full-peak 区域故障面前，全局 2× 容灾预留如何让 400 万核算力利用率常年约 20%，以及 Uber 如何通过业务分级、fail-open 化依赖清理与受控超卖，在两年把预留打到约 1.3×、砍掉 102.5 万核且核心可用率仍稳在 99.97%。

接下来，第一部分，核心概念关系。

关系脉络如下：2× 一刀切双活，然后消灭 fail-close，然后T0～T5 四档响应，然后1.5× 超卖池

接下来，第二部分，认知纠偏。

认知纠偏

误解：「双活 / 全量 2× 容量」等于高可靠。实际上 6000+ 微服务里大量跨层 fail-close 会让牺牲低优先级服务时拖垮 T0/T1；不分级超卖等于在关键路径上赌博。

接下来，第三部分，反驳。

反驳

对立视角：SRE「最大冗余 / 全员双活」保守派

按年不到一天的 full-peak 去削减全局 2× 预留是在用统计赌博换账单——一旦遇到超长区域故障或依赖清理漏网，亚稳态级联会比多花的 CPU 昂贵得多。

接下来，第四部分，【概念拆解卡】UFA 与 full-peak 故障。

在讲什么问题，何时才需要「另一区域扛住 100% 峰值流量」？

关键理解，Uber 定义 full-peak = 迁移量超周峰值 85% 用户且区域故障超 50% 城市；四年数据年均 <20 小时。旧模型按此极端为所有服务预留 2×，利用率约 20%。

和其他概念关系：UFA（Uber Failover Architecture）= 分级故障响应 + 依赖隔离 + K8s 资源池超卖；编排靠 OMG（Outage Mitigator）。

怎么落地用：用自家故障日志算「真正需要全量峰值接力」的小时占比，再决定默认容灾倍数是 2× 还是分级后的 ~1.3×。

边界说明，分级容灾成立前提是 fail-open 与网络精准断连；未清理依赖前不能牺牲 Restore-Later / Terminate 类服务。

原文依据，「Full-peak 故障平均每年发生不到 20 小时，占全年 0.23%。」

接下来，第五部分，【方法/工具卡】四种故障响应类型。

核心思路：按业务层级 T0～T5 映射 Always-On / Active-Migrate / Restore-Later / Terminate，非核心服务故障时可被牺牲或延后恢复，核心秒级扩容不被抢占。

操作步骤，① 给每个服务定层级 ，得到 ② 映射响应类型与 RTO ，得到 ③ 划分 stateless.cpu 与 overcommit.cpu 池 ，得到 ④ 故障时 OMG 按类型驱逐、迁移、断网。

选型条件，超大规模微服务、双区域、容灾成本与利用率矛盾尖锐；小团队单区域无需整套 UFA。

避坑，Terminate 类在故障期持续不可用——只能用于 NP；不能把 T1 行程链路放进 Restore-Later。

对比相邻方法，传统 active-active 全员 2×；UFA 让低优先级「寄居」在闲置缓冲容量里日常超卖。

原文引用：T0/T1 Always-On；T2 Active-Migrate；T3～T5 Restore-Later；NP Terminate。

接下来，第六部分，【跨概念对比表】容灾模型维度。

预留倍数，≈2× 全服务，~1.3× 综合（含 1.5× 超卖池），用数据砍掉「为 0.23% 时间买单」

利用率，~20% 基线，31% 均值，P99 42%，11 个月减 102.5 万核

依赖要求，隐含「下游都得活」，4155 个 fail-close 必须清理，省钱与可靠一体两面

故障表现，理论全量接管，2026-01 17h 事件 99.97% 可用，8 分钟内突发容量就绪

组织成本，规则简单，~50 人平台团队、两年分层推进，社会技术变革 > 单点技术

接下来，第七部分，【决策/选型表】何时采用分级容灾。

万级微服务、双 Region，UFA 式分级 + 依赖门禁，RPC 跨层调用占比高，继续全员 2×，算力账单与利用率双输

单体或少服务，传统 HA + 演练，依赖图可控，上 OMG + 7 层 tier，治理 ROI 不成比例

已做超卖但未分级，先 fail-close 扫描，超卖会把隐患放大，直接砍 NP 资源，易触发亚稳态失败

强监管行程/支付，T0/T1 Always-On + Canary 断网，牺牲外围保核心，全 Terminate 低环境，合规与实验环境需求冲突

接下来，第八部分，【心法/原则卡】fail-open 与三层安全网。

原则，低优先级服务可以死，前提是上游必须 fail-open——下游挂了我能降级，而不是把错误原样抛出拖死核心。

为什么重要，一周内 RPC 约 62 万亿次，约半数为高，得到低跨层；不隔离则「腾资源」等于「捅核心」。

怎么落地，运行时依赖画像 + Go/Java 静态传播分析 + Canary 5 分钟断网回归；AI 驱动 47 条移动端 E2E 故障注入。

适用边界，静态分析拦在合入前，Canary 45 天仅 3 次新增回归——仍要保留运行时监控补漏。

原文支撑：三层网共揪出 4155 个 fail-close 违规。

接下来，第九部分，【避坑清单卡】UFA 工程陷阱。

坑名，未清依赖就超卖。原因：Restore-Later 被抢占触发链式挂。解法：依赖图先行或与 UFA 并行投人。严重程度：致命。

坑名，预发无法复现地域问题。原因：真实灰度才暴露机场周边延迟等。解法：分区域灰度 + 主动切换治灰色故障。严重程度：小心。

坑名，镜像拉取打垮仓库。原因：大规模冷启动。解法：Kraken P2P 预热数 TB 镜像，启动快 30%。严重程度：小心。

坑名，一刀切驱逐批处理。原因：与业务方未协调。解法：故障窗口暂停向批处理集群调度非关键任务。严重程度：可忽略，得到小心（团队规模相关）。

接下来，第十部分，总结与行动。

结论

数据证明 full-peak 极罕见，一刀切 2× 让机队长期低利用率。

UFA 用 T0～T5 四档响应把「牺牲非核心」产品化，并配套 OMG 编排。

fail-close 清理是超卖与分级的前提，三层分析抓出 4155 处违规。

11 个月减 102.5 万核、利用率升至 31%，核心可用率保持 99.97%。

最难的是跨 6000+ 服务、数百团队的社会技术协作而非单点算法。

统计近 3～5 年区域故障中「需全量峰值接力」的时长占比。

绘制高，得到低层级 RPC，标记 fail-close 调用对并排期修复。

为核心服务定义 Always-On 清单，其余映射 Migrate / Restore / Terminate。

在 Canary 引入「断网低 tier 5 分钟」自动回滚门禁。

阅读 NSDI 26 原文核对超卖公式与 Kraken / OMG 细节。
