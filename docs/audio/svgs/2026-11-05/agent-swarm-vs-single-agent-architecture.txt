一句话概括。本文解决的核心问题是：在上下文窗口、推理算力与 Agent 间协调成本都有限的前提下，何时应把能力留在单一执行循环里，何时值得拆成 Subagent、持久化 Agent 乃至 Swarm 式横向协作——以及如何用端到端评测在「合并」与「拆分」之间做可测量的架构决策。

接下来，第一部分，核心概念关系。

关系脉络如下：单上下文上限，然后压缩 / 外置 / Subagent，然后持久化多上下文，然后过度拆分则协调税

接下来，第二部分，认知纠偏。

认知纠偏

误解：Single Agent 与 Agent Swarm 是互斥阵营、必须站队。实际上两者讨论同一权衡的不同侧面——前者强调减少不必要的上下文边界，后者强调不要把所有工作记忆挤进一个窗口。

接下来，第三部分，反驳。

反驳

对立视角：多 Agent 平台厂商 / 「组织即架构」派

把 Subagent 全 fold 回主循环会在合规审计、职责分离和故障追责上把「一个超级上下文」变成单点黑箱——协调成本降下来，治理与可解释性可能一起崩盘。

接下来，第四部分，【概念拆解卡】上下文并行 vs 计算并行。

在讲什么问题，多 Agent 的价值是否等于「多开几个模型一起跑」？

关键理解，独立上下文可同时保留多份「工作记忆」；持久化 Agent 让已建立的代码理解、排除过的假设可被反复调用，而不只是任务结束就销毁的 Subagent。

和其他概念关系：计算并行适合互不依赖的子任务；上下文并行适合同一领域知识被多任务反复引用。

怎么落地用：识别团队是否反复为「前端/安全/数据层」重建调查上下文——若是，评估长期存活的专业 Agent 或共享记忆，而非每次 spawn 临时 Subagent。

边界说明，持久化 Agent 仍面临压缩、知识过时、状态同步；不是「永远准确的全知分身」。

原文依据，「多 Agent 不只是把计算并行化，也可以把上下文并行化。」

接下来，第五部分，【方法/工具卡】Single Agent 循环 + Skills / 渐进式披露。

核心思路：一个执行循环持续看到原始工具结果并修正计划，按需加载 Skills 与 Tools，而非每跨 Agent 边界就交接摘要。

操作步骤，① 梳理 Subagent 是否连续调用、共享同一批数据 ，得到 ② 将流程与领域规则写入 Skills，实时数据走 Tools ，得到 ③ 短说明 + 按需展开详细 Skill 正文 ，得到 ④ 保留并行工具调用与外部记忆，但不默认拆上下文。

选型条件，工作流前后步骤强依赖同一中间结论、模型已能在单循环内规划与纠错时优先单 Agent。

避坑，把「架构图画得专业」当成拆分理由；Anthropic 观察到部分多 Agent Token 为单 Agent 3～10 倍、延迟约 2 倍（场景相关，非普适定律）。

对比相邻方法，树状 Subagent 编排 vs 单循环——后者减少摘要链路上的信息损失，前者适合硬隔离权限与验证。

原文引用：「除非确实需要独立上下文，否则优先让同一个 Agent 保持对任务全过程的理解。」

接下来，第六部分，【跨概念对比表】Compaction / 外置记忆 / Subagent / 持久化 Agent。

Compaction，窗口上限，总结时不知未来何细节关键，长任务可用，但每次总结都是下注

外部记忆，细节留存，「文件在」≠ Agent 知何时读；理解不随文件迁移，需检索策略与元数据

临时 Subagent，主上下文免污染，任务结束上下文丢弃，重复调查，问题明确后再派调查员

持久化 Agent，可复用专业上下文，压缩、过时、占用与同步，Swarm 方向的核心构件

接下来，第七部分，【决策/选型表】任务特征 ，得到 架构倾向。

连续工作流、前后共享大量中间信息，单 Agent 循环，减少交接摘要损失，每步独立 Subagent，协调税 > 隔离收益

多条独立研究/验证路径，多 Agent 并行，边界清晰、只交换结论，强行单上下文塞满探索，污染主 Agent 注意力

独立权限、审批、验证隔离，专业 Subagent，安全与合规边界，为「简化架构」合并退款/高危操作，丢掉权限边界

跨分支反复需要同一专业知识，持久化 Agent / 共享状态，避免树状根节点瓶颈，纯树状逐级上报，根上下文再次成为瓶颈

接下来，第八部分，【避坑清单卡】多 Agent 工程化。

坑名，为组织图拆分 Agent。原因：每增 Agent 增提示词、上下文、接口与评测面。解法：先问「获得了单 Agent 无法经济获得的能力吗」。严重程度：致命。

坑名，把 Compaction 当无损续命。原因：间歇性故障线索可能在总结时被当噪声丢弃。解法：关键调查路径保留原始日志引用或外置索引。严重程度：小心。

坑名，架构大改无基准。原因：Agent 随机性掩盖单次侥幸成功。解法：10+ 真实任务样例、比质量/成本/延迟、一次只动一块。严重程度：致命。

接下来，第九部分，【心法/原则卡】优化信息流动，而非崇拜 Agent 数量。

原则，竞争焦点是「以更低协调成本，让正确信息在正确时间到达正确 Agent」。

为什么重要，树状编排规模变大时，专业知识困在分支、根节点协调再次吃满上下文；Mesh/Swarm 探索横向求助，但去中心化也有通信与责任模糊成本。

怎么落地，从单 Agent 起步；仅在可测量收益处引入多 Agent；合并的是不必要的上下文边界，不是权限/验证/安全边界。

适用边界，模型能力持续上升时，过于僵硬编排可能限制新模型自行规划——架构应可随评测结果 fold 与 unfold。

原文支撑：「两者并不矛盾……是构建高效 AI 系统时可以灵活组合的工程工具。」

接下来，第十部分，总结与行动。

结论

Agent 架构争论的底层是上下文容量、信息损失与协调成本的权衡，不是数量崇拜。

Compaction、外置记忆、Subagent、持久化 Agent 各解决不同瓶颈，且都有信息损失或维护代价。

Anthropic 主张在污染、真并行、专业化隔离三类场景才值得独立上下文；否则优先单循环 + Skills/Tools。

大规模系统可能需 Swarm 式共享状态与横向协作，但应与层级编排动态组合，而非二选一。

端到端评测（质量、Token、延迟、失败率）是合并/拆分的唯一可靠依据。

列出当前 Subagent 调用链：是否连续、是否共享数据——优先合并高频连续对。

建立 10+ 条真实任务基准，记录 fold 前后成功/失败翻转与 Token、耗时。

对反复需要的领域上下文，试点持久化 Agent 或共享 Git/任务状态，而非重复 spawn。

保留退款、发布、高危工具等权限 Subagent，不因「架构简化」取消边界。

阅读 Hallerite《On the Nature of the Swarm》与 Anthropic fold 文章，对照自家编排是树状、单循环还是混合。
