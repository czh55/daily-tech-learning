一句话概括。本文解决的核心问题是：MCP 协议只定义接口形态、不教如何设计好用可维护的 Server——论文基于 15 个生产与开源 Server 提炼 5 种架构模式与 4 个反模式，并用真实遥测量化「单个上下文暴露多少工具时 Agent 还能选对」。

接下来，第一部分，核心概念关系。

关系脉络如下：后端数据/动作，然后5 种模式，Gateway/Orchestrator…，然后工具描述，LLM 靠它选型，然后≤10~15 工具，准确率红线，然后Agent 正确调用

接下来，第二部分，认知纠偏。

认知纠偏

常见误解：「工具越多越好，让 Agent 自己挑」—— 生产数据显示 Haiku 在 10~15 个工具间跌破 90% 准确率；堆 20、30 个工具前应先拆 Domain Adapter 或上 scoped Proxy Aggregator，而不是静态合并全部能力。

接下来，第三部分，反驳。

反驳

对立视角：「能力最大化」派 / 主张一个 Server 暴露全部工具

10~15 个工具的红线是用 2025 Q1 特定模型和语音场景测出来的——工具描述足够好、模型足够强时，30 个工具照样能 90%+，scoped 拆分反而增加检索延迟和集成复杂度。

接下来，第四部分，【概念拆解卡】五种 MCP 架构模式速览。

在讲什么问题，协议规范出来后 Server 遍地开花，但重复踩坑：参数巨 schema、状态乱放、聚合工具名冲突——需要可复用的设计词汇。

核心机制（论文 GoF 式归纳，15 Server 语料 + 54 留出验证 κ=0.76）：

1. Resource Gateway：统一数据访问入口，Resources 读 + Tools 参数化查询，返回前净化防 Prompt Injection

2. Tool Orchestrator：多系统工作流封装成单个复合工具，编排下沉 Server，LLM 只见「一个操作」

3. Stateful Session Server：连接级会话 ID + 内存/Redis 上下文，多轮编辑/事务场景

4. Proxy Aggregator：代理 N 个上游，命名空间防冲突；scoped 变体按需暴露工具子集

5. Domain-Specific Adapter：把 CRM/金融等对人类友好、对 LLM 不友好的 API 翻译成可读工具+输入归一化+错误人话化

边界说明，Stateful 仅在「本轮依赖上轮状态」时用，且须规划会话回收防内存泄漏；Adapter 在底层 API 已对 LLM 友好时是过度设计。

接下来，第五部分，【决策/选型表】什么场景选哪种模式。

只读后端数据（DB/文档/API），Resource Gateway + 净化层，唯一访问入口、schema 变化不冲击 LLM 侧，裸返回用户生成内容，Prompt Injection 把数据当指令执行

跨系统多步动作（工单+通知+群消息），Tool Orchestrator，降 LLM 推理负担，Server 内处理部分失败，暴露每个子 API 给 LLM，要求 LLM 维护中间状态

打开，得到编辑，得到保存多轮工作流，Stateful Session Server，避免重复传大数据，支持事务语义，每轮全量传状态，上下文爆炸；协议不保证 LLM 可靠传 session ID

企业聚合多 MCP Server，scoped Proxy Aggregator，工具数逼近红线时按需检索，非静态合并，static-merge 全暴露，工具数超 15 准确率实打实下跌

Salesforce 等复杂 CRM API，Domain-Specific Adapter，描述精确时工具选择准确率显著提升，直接暴露原始 API，机器 ID、复杂认证 LLM 无法稳定使用

接下来，第六部分，【避坑清单卡】四个反模式（比模式更该先看）。

坑名，God Tool、未净化资源、同步长任务、模糊工具描述——语料中无一是任何 Server 的主导结构，却是反复出现的局部错误。

原因，把 MCP 当普通 API 设计，忽略「客户端靠读自然语言描述选 API」这一反常约束。

原文说法与解法：

• God Tool：do_anything(action, params) 让 LLM 猜 action ，得到 拆成命名精确、schema 明确的独立工具

• 未净化资源：UGC 含「忽略之前指令」直接进 Resource ，得到 所有外部内容进响应前净化/转义

• 同步长任务：视频编码等无 MCP 异步回调 ，得到 同步返回 task ID + 单独 poll_job 工具

• 模糊描述：send_message 无描述或复述名字 ，得到 写清干什么、何时用、返回什么，当 Code Review 审查

严重程度，God Tool 和模糊描述直接击穿工具选择准确率——在 10~15 红线内也救不回来。

接下来，第七部分，【方法/工具卡】工具数量红线与 scoped 聚合落地。

核心思路：ANSYR 语音 AI 平台 2025 Q1 生产遥测，按工具数分桶统计 Haiku 4.5 / Sonnet 4 选择准确率。

操作步骤，

1. 审计当前 Server（或聚合后）暴露工具数，目标控制在 10~15 个以内

2. 逼近红线时：拆多个 Domain-Specific Adapter，或 Proxy Aggregator 用 scoped 变体（retrieval-over-tools）

3. 每个工具描述写清场景与返回值——描述是核心工程产出，不是事后注释

4. 传输选型：本机 stdio vs streamable-http 差毫秒级，跨主机 RTT ~30ms 才是瓶颈——关注是否同机部署、聚合是否多一跳

5. 横切：Bearer Token 在传输层认证、结构化错误返回、initialize 带版本、每次调用记工具名/延迟/错误码

关键数字：Haiku 10 工具 91%、15 工具 87%；Sonnet 20 工具仍 ≥90%、30 工具跌破——与 RAG-MCP、LongFuncEval 趋势一致。

静态合并多个上游全部工具到单一上下文，是「把所有能力一股脑塞给 Agent」的粗暴幻想——论文用数据打破了它。

接下来，第八部分，【跨概念对比表】五种模式 vs 经典架构原型。

经典原型，Repository/REST，Facade/Mediator，Proxy/API Gateway，不是全新发明，是 LLM 约束下的再诠释

LLM 新增约束，资源命名便检索，工具集大小定准确率，须分区工具适配上下文预算，描述比 schema 更重要

主要代价，多读一次跳转，工作流变更改代码+文档，单点故障、多一跳延迟，scoped 变体还要保证筛选快且准

典型用例，Postgres/MongoDB 连接器，CI/CD、客服动作中枢，企业 MCP 网关，按读写/编排/聚合分治

接下来，第九部分，【心法/原则卡】MCP 是 API 设计，受众是读描述的大模型。

原则，MCP Server 设计本质是 API 设计，但客户端通过读自然语言描述决定调什么——描述直接决定工具能不能被正确使用。

为什么重要，类比 LSP 解耦编辑器与语言服务器；MCP 能否像 LSP 一样沉淀共享生态，取决于能否用架构模式词汇指导大家把 Server 写好。

怎么落地，工具描述像对待代码一样写、像 Code Review 一样审；聚合用 scoped 而非 static-merge；只读加净化、多步封装 Orchestrator、有状态才 Session。

适用边界，论文基于 15 Server + 特定模型遥测，不同模型拐点不同（Sonnet 容忍更高工具数）——红线是起点不是绝对真理，须结合自身模型与场景复测。

原文：「如果你还把工具描述当成写完代码后随手补的注释，你的 Server 性能上限已经被你自己锁死了。」

接下来，第十部分，总结与行动。

结论

论文从 15 个 Server 提炼 Resource Gateway、Tool Orchestrator、Stateful Session、Proxy Aggregator、Domain Adapter 五种可复用模式

四个反模式（God Tool、未净化、同步长任务、模糊描述）是反复出现的局部错误，应优先排查

生产遥测：Haiku 在 10~15 个工具间跌破 90% 准确率——单上下文工具数宜控制在此范围

聚合多 Server 时用 scoped Proxy Aggregator 按需暴露，避免 static-merge 拉高可见工具数

MCP 设计受众从「写代码的人类」变成「读描述的大模型」，工具描述是核心工程产出

清点现有 MCP Server 暴露工具数，超过 15 则规划拆分或 scoped 聚合

为每个工具写清「干什么、何时用、返回什么」，纳入 Code Review 流程

所有外部/用户生成内容进 Resource 前加 sanitize 净化层

长耗时操作改为返回 task ID + poll_job，不要同步阻塞

记录每次工具调用的工具名、输入哈希、延迟、错误码，便于排查 LLM「胡来」
