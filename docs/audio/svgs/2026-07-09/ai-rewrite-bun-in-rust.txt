欢迎收听每日技术学习语音讲解。本期主题，AI 重写 Bun 为 Rust：101 万行、11 天、64 个 Claude。标签包括Bun、Zig→Rust、Claude Agent、对抗性审查。本次讲解预计时长 约 14 到 15 分钟，共 11 个部分。好，我们开始。

一句话概括。本文解决的核心问题是：在被月下载 2200 万次、Claude Code 等工具依赖的生产级基础设施上，AI Agent 能否在 11 天内完成 53.5 万行 Zig 到 100 万行 Rust 的完整语言重写，以及需要怎样的工程方法论才能让它真正可行。

接下来，第一部分，核心概念关系。

关系脉络如下：Zig 53.5 万行，内存安全债，然后PORTING.md，模式映射，然后64×Claude，实现+审查，然后370 万次断言，零跳过，然后Rust v1.4，-20% 体积

接下来，第二部分，认知纠偏。

认知纠偏

常见误解：「给 Claude 一句『重写成 Rust』就能搞定」—— Jarred Sumner 明确说这是不负责任的做法；真正撑起质量的是实现者与对抗性审查者分离、机械翻译优先、以及把编译错误当可并行消化的任务队列。

接下来，第三部分，反驳。

反驳

对立视角：Zig 社区 / 「修 bug 清单就够了」派

16.5 万美元和 100 万行新代码只为把一类内存 bug 交给编译器——在 Zig 上补 ASAN、Fuzz 和智能指针方案，成本远低于推倒重来，且不会引入 debug_assert 语义差这类新回归。

接下来，第四部分，【概念拆解卡】为什么从 Zig 迁到 Rust。

在讲什么问题，Bun v1.3.14 修复清单几乎清一色是 use-after-free、悬空指针、内存泄漏——手动内存管理在 JS 引擎 GC 与原生代码混合场景下系统性失控。

核心机制，Rust 借用检查器把清单里绝大多数 bug 变成编译错误；Drop 机制自动做 RAII 式资源清理，替代 Zig 里容易漏写或重复写的 defer。

关键理解，选 Rust 不是因为讨厌 Zig，而是因为「事后 ASAN/Fuzz 发现」永远追不上「从源头杜绝」——C++ 有构造/析构但仍需人肉风格指南，执行力靠不住。

典型场景，node:zlib use-after-free、node:http2 哈希表 rehash 悬空指针、crypto.scrypt 泄漏、TLS 会话缓存每次泄漏约 6.5KB。

边界说明，Bun 约 20% 代码本就是 C++（JSC、uWebSockets、BoringSSL），Rust 版仍有约 4% unsafe（1.3 万处），因必须调用 C/C++ 库——不可能变成纯 safe Rust 项目。

原文：「这类问题可以一直靠一个个修撑下去，但对得起用户的方式应该是从根子上系统性地杜绝它们重复出现。」

接下来，第五部分，【决策/选型表】增量重写 vs 一次性全量重写。

53 万行、架构需保持，一次性全量机械翻译，Sumner 从 esbuild Go，得到Zig 经验：增量会留大量过渡代码，短中期极痛苦，按模块逐步替换，双语言并存期维护成本爆炸

先保功能对等，忠实 Zig 结构移植，地道 Rust 留到 v1.4 后，先吃到借用检查红利，再逐步降 unsafe，重写时顺便大重构，范围失控、测试难收敛

人力不可接受（3 人年+功能冻结），AI Agent 并行 + 人类监工，团队备选其实是「什么都不做继续修 bug 清单」，手写类 Rust 智能指针，体验差且无编译器级保证

生产依赖（2200 万月下载），零测试跳过底线 + 6 平台 CI 全绿才合并，370 万次 expect 断言，0 个跳过或删除，为赶进度 stub 掉编译不过函数，Claude 曾误理解任务，审查规则后才止住

接下来，第六部分，【方法/工具卡】实现者 + 对抗性审查者分离。

核心思路：写代码的人（Claude）想让代码尽快合并，会对自己代码的问题视而不见——审查者必须看不到实现者推理过程，且被明确告知「默认这段代码是错的」。

操作步骤，

1. 配置 1 个实现者 + 至少 2 个对抗性审查者，审查者只拿 diff

2. 准备阶段：3 小时产出 PORTING.md（Zig，得到Rust 模式映射）+ LIFETIMES.tsv（结构体生命周期标注）

3. 试运行 3 个文件验证流程，再铺开 1448 个 .zig 文件

4. 4 个独立 worktree × 16 个 Claude，峰值约 64 并行；禁止跨文件 git 命令和慢命令（cargo）

5. cargo check 约 1.6 万错误按 crate 分组：每 crate 一个实现者+两审查者+整合者小循环

审查规则：「如果你需要写一整段注释来证明这个权宜之计是合理的，那说明代码本身就是错的——去把代码修对。」

真实拦下的 bug：异步 uv_close 的 Box 提前释放（改用 Box::leak）；负数时间戳 trunc vs floor；unwrap_or 立即求值导致 CSS color-mix panic——都能编译通过，无审查必漏。

接下来，第七部分，【避坑清单卡】机械翻译的 19 个已知回归。

坑名，两门语言「长得一样、语义完全不同」的陷阱——纯人工审查也容易漏。

原因，机械翻译不是无脑复制粘贴；Zig comptime、assert 副作用、边界检查默认值与 Rust 不一致。

原文案例：

• debug_assert! 在 release 擦除副作用 ，得到 HMR 热更新失效

• bytemuck::cast_slice 遇奇数长度直接 panic ，得到 Blob.text() 崩溃

• Rust release 默认边界检查 vs Zig ReleaseFast 关闭 ，得到 缓冲区上限从 840 万骤降到 27 万

• comptime 格式化 vs Rust 运行时格式化 ，得到 终端超链接被误当颜色标记吃掉

解法，合并后 11 轮 Claude Code Security 审查 + 全解析器 7×24 Fuzzilli 模糊测试（超 1000 亿次，约 15 个自动 PR）。

严重程度，致命级若未测到生产——Prisma Compute 和 Claude Code 已跑 Rust 版验证内存与启动问题修复。

接下来，第八部分，【跨概念对比表】重写前后关键指标。

内存（Bun.build 2000 次），泄漏至约 6.7GB，稳定约 609MB，Drop 自动清理见效

Linux 二进制体积，约 88MB，约 70MB（-20%），少 comptime + LTO + ICU 精简

HTTP 吞吐（Bun.serve），16.96 万 req/s，17.77 万 req/s（+4.8%），Rust-C++ LTO 跨语言优化

Claude Code 冷启动（Linux），517ms，464ms（-10%），生产工具已切换

unsafe 占比，N/A（手动管理），约 4%（78% 仅一行），随地道化重构会继续降

接下来，第九部分，【心法/原则卡】AI 能否挑起基础设施重写。

原则，答案不是「能」或「不能」，而是方法论决定上限——人类做大型重写需要的纪律，这次由 64 个 Claude 执行，人做架构决策与流程监工。

为什么重要，16.5 万美元、11 天、0 测试删除——将成为「AI 能否重写关键基础设施」的参照系；反面是 3 人年 + 全年功能冻结。

怎么落地，一次性重写决策、机械翻译优先、对抗性审查、编译错误任务队列化、零测试跳过。

适用边界，需要 Anthropic 级模型 + Claude Code 动态工作流 + 对代码库有完整上下文的人类监工；不是「复制粘贴喂 AI」能复现的。

原文：「执行这些纪律的主力换成了 64 个同时运转的 Claude 实例，而人类工程师的角色，变成了架构决策者和流程监工。」

接下来，第十部分，总结与行动。

结论

Bun 迁 Rust 根因是 Zig 手动内存管理与 JSC 混合场景下 use-after-free/泄漏系统性爆发，Rust 把多数问题前移到编译期

工程上选一次性全量机械翻译，地道 Rust 重构放到 v1.4 之后，避免增量过渡代码泥潭

1 实现者 + 2 对抗性审查者是质量核心，三个「能编译能跑」的 bug 全靠审查拦住

64 Claude 并行 + 4 worktree，把 1.6 万编译错误和 972，得到0 测试失败当可并行任务队列消化

重写后内存收敛、体积 -20%、吞吐 +2.8%~4.8%，但机械翻译留下 19 个语义回归需持续 Fuzz 与安全审查

评估大型重写时先算「增量过渡成本」vs「一次性机械翻译 + 后续重构」

任何 AI 代码生成流程强制实现/审查角色分离，审查者默认代码有错

设定「零测试跳过」硬底线，CI 全平台全绿才允许合并

机械翻译后专门做「同语法不同语义」回归清单（assert 副作用、comptime、边界检查）

用 bun upgrade --canary 试用 Rust 版，关注 v1.4.0 正式版发布
