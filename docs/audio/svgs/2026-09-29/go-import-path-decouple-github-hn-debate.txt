一句话概括。本文解决的核心问题是：把 import 写死成 github.com 究竟是习惯还是技术债——作者摊开 HN 正反论据，说明路径同时承担模块身份与物理拉取地址，全局替换救不了不可变 tag，replace 只能止血；并给出 go-import 机制、三类 vanity 落地与存量迁移步骤。

接下来，第一部分，核心概念关系。

关系脉络如下：模块身份，Identity，然后拉取位置，Location，然后校验键，Checksum 链，然后自有域名，间接层

接下来，第二部分，认知纠偏。

认知纠偏

常见误解：「迁路径就是全局查找替换，Agent 几小时搞定」。原文强调不可变 Git tag 仍携带旧路径，会破坏 bisect 与历史构建，规模上去替换次数按依赖图爆炸。

接下来，第三部分，反驳。

反驳

对立视角：「GitHub 足够稳」实用派

对多数个人库，多一个域名和 vanity 运维点，比平台迁移的极低概率更实在——续费疏忽一次，整条 import 命名空间就交给陌生人。

接下来，第四部分，【概念拆解卡】import path 的双重属性。

在讲什么问题，同一字符串既是命名空间又是仓库 URL，把易变基础设施焊进源码。

核心机制，Go 以目录为包，工具链鼓励在源码里写完整托管地址；modules 下该字符串还驱动 go get 与校验。

关键理解，争论起点不是「GitHub 好不好」，而是名字与地址是否应分离。

典型场景，企业同时使用 GitLab、GitHub、Azure DevOps，只因迁移成本太高而三平台并存付费。

边界说明，个人练手、一次性脚本不必折腾 vanity；被他人长期依赖的库与企业内库应尽早分离。

「同一个字符串，既是名字，又是地址。」——争论的共同起点。

接下来，第五部分，【跨概念对比表】全局替换 vs replace vs vanity 域名。

历史 tag，不自动修复，需重打 tag，不改 tag 内容，改映射即可，import 不变，只有 vanity 保护下游 import 字面量

库作者下游，需全员跟进，replace 不传递给依赖方，下游无感换托管，库必须用 vanity 或改模块路径

源码字面量，可更新，仍留旧 URL，稳定为 go.corp/…，replace 是止血不是架构

供应链控制面，无，无统一入口，可指向 GOPROXY/制品库，域名是间接层期权

接下来，第六部分，【方法/工具卡】go-import 最小落地。

核心思路：对 ?go-get=1 返回带 go-import meta 的 HTML，第三段指向真实 Git 仓库。

操作步骤，① 准备域名与 TLS；② 部署返回 meta 的页面（Nginx 或托管 gvu）；③ 人类访问用 302 跳仓库（避免 301 被浏览器永久缓存）；④ 配置 go-source 供文档站；⑤ 私有模块设 GOPRIVATE=go.yourcompany.com。

选型条件，模块少可用静态 HTML；数量多要通配路由与 /v2 支持；不想运维可选 gvu 类托管 CLI。

避坑，vanity 只解析「去哪拉」，鉴权仍在 Git 服务器，服务不应保存仓库密码。

接下来，第七部分，【决策/选型表】何时用 github.com，何时用自有域名。

个人练手/一次性工具，直接用 github.com，迁移概率低、成本最低，第 0 天买企业域名流程，运维大于收益

长期维护的开源库，第 0 天 vanity，依赖方多、期权成本近零，等火了再迁，历史 tag 与下游协调爆炸

企业多团队内库，vanity + 自建 GOPROXY，统一缓存、鉴权、校验，仅靠公共代理，私有与合规无法满足

存量 github 路径，新模块用域名、旧模块渐进，旧 tag 不能原地改名，删旧仓库，破坏未升级依赖方

接下来，第八部分，【避坑清单卡】迁移与静态 vanity。

旧 tag 陷阱：改主干不等于改已发布版本。原因：tag 不可变。解法：新路径发新版本，旧路径归档只读。严重程度：致命。

301 跳转：浏览器永久记住旧目标。原因：Nginx 默认 301。解法：人类跳转用 302。严重程度：小心。

/v2 遗漏：主版本≥2 必须带后缀路径。原因：解析服务未配。解法：选型时确认主版本自动支持。严重程度：小心。

域名续费：身份解释权在域名。原因：过期可被抢注。解法：企业续费流程；个人权衡维护责任。严重程度：小心。

接下来，第九部分，【心法/原则卡】第 0 天的便宜期权。

原则，解耦成本不对称——今天半小时配置，换明天跨团队不可灰度迁移。

为什么重要，反方对「当前仓库替换简单」成立，正方对「历史与依赖图」成立，时间点不同。

怎么落地，新项目先定模块路径；存量用 go mod edit -module、批量 sed、go mod tidy、全量 test，旧 go.mod 加 Deprecated 注释。

适用边界，域名运维对个人小库是真实成本，需与「被依赖规模」权衡，并非一刀切。

接下来，第十部分，总结与行动。

结论

import path 同时是身份、拉取地址与校验键，耦合托管平台是架构层面的绑定。

全局替换忽略不可变 tag；replace 仅主模块止血，库作者无法替下游承担。

自有域名是用可控运维换不可控迁移，并可选作 GOPROXY 与供应链入口。

go-import/go-source + 302 是人类与工具链协作的最小机制。

争论本质是「第 0 天付半小时」还是「第 N 天付跨团队账单」。

盘点对外模块：被依赖且生命周期>1 年的，评估 vanity 域名。

新项目在写第一行 import 前确定模块路径，避免事后改 tag 链。

若迁移存量：归档旧仓库、Deprecated 注释、禁止删除旧路径。

团队场景检查 /v2、monorepo 子目录（Go 1.25+）是否在解析层支持。

配置 GOPRIVATE 与自建代理，不把「明天还在」当假设。
