一句话概括。本文解决的核心问题是：当企业内部已有成熟 REST/领域服务时，如何用 MCP 在不动业务核心的前提下，为 AI Host 提供可发现、可治理、可审计的工具面，并在 CLI 与 Shell 同样流行的 Agent 时代判断 MCP 的真实价值边界。

关系脉络如下：AI Host，然后MCP Client，然后MCP 适配层，然后领域服务 / 仓储

接下来，第二部分，认知纠偏。

认知纠偏

误解：上 MCP = 重写后端。原文强调在既有应用服务外加薄适配层，把 MCP 请求映射到已有能力，再把结果结构化回给模型。

接下来，第三部分，反驳。

反驳

对立视角：「给 Agent 一个 curl 脚本 + API Key 就够了」

裸 REST 让模型自拼 URL、自猜错误码，在写操作与多租户场景下几乎无法做统一授权与幂等；等到事故复盘时你会发现缺的正是 MCP 那层可描述的契约与可审计的 Tool 边界。

接下来，第四部分，【概念拆解卡】MCP 解决的不是「有没有 API」。

在讲什么问题，传统 API 为人与程序设计；Agent 需要发现能力、理解参数语义、在权限内组合多步调用。

关键理解，MCP 标准化 Host–Client–Server 交互；Server 用 Tools（动作）、Resources（可读上下文）、Prompts（任务模板）描述能力。

关系：REST 仍服务人类/UI；MCP 是 AI 消费层的「插座标准」，可与 CLI Bridge 共存（如 OpenClaw）。

落地：从 get_order 只读 Tool 起步，再扩库存、工单、写操作与租户隔离。

边界：不替代领域建模；只管协议映射、契约与安全壳。

原文依据，「API 能被程序调用，不等于 AI 应用就能可靠地使用它。」

接下来，第五部分，【跨概念对比表】CLI 工具箱 vs MCP 能力总线。

抽象层次，OS 级组合、管道，跨语言结构化 RPC，互补非替代

企业场景，难以开放裸 Shell，明确边界、可审计，生产必选 MCP 壳

参数/结果，文本流，模型自解析，JSON Schema 类型化，降低误用率

远程/多租户，SSH 耦合重，stdio / Streamable HTTP，按部署选型传输

组合方式，本地 Agent 极轻，可被 CLI Backend 经 Bridge 调用，可叠加使用

接下来，第六部分，【方法/工具卡】Go 适配层的工程习惯。

核心思路：接口隔离领域与协议；官方 SDK 承载协议，团队专注映射与治理。

步骤：① 定义领域接口（订单查询），得到 ② 实现 MCP Tool 映射 + 输入输出 struct ，得到 ③ context 贯穿超时/取消 ，得到 ④ 协议级集成测试（非只测函数），得到 ⑤ 选 stdio（本地）或 HTTP（远程）。

选型：已有 Go 单体/微服务团队优先 Go MCP SDK，复用 CI、观测与部署栈。

避坑，勿把每个 REST endpoint 机械包成 Tool——先问用户任务、副作用、权限。

对比：第一个 Tool 返回数据只证明链路通；生产从成功调用之后才开始（授权、幂等、限流）。

接下来，第七部分，【决策/选型表】Tool / Resource / Prompt。

查订单状态，Tool，明确动作、副作用可控，Resource，模型难自主触发读取节奏

业务知识库切片，Resource，只读上下文供给，巨型 Tool 描述，Discovery 成本高

标准工单话术，Prompt 模板，可复用任务框架，自由生成，一致性差

取消订单，Tool + 幂等键 + 确认，写操作需审计，裸 Tool 无授权，模型重复调用风险

接下来，第八部分，【避坑清单卡】专栏强调的 14 讲生产议题。

契约：名称/描述/Schema 影响模型误用率——需人审 + 集成测试。

身份：租户与用户上下文必须从 Host 传到 Server，禁止默认全网可见。

写操作：幂等、确认、审计三件套；重复取消/建单由协议层兜底。

可靠性：超时、取消、并发、限流、下游故障要有统一错误语义。

观测：按 Tool 维度打点，否则无法做 Agent SLO。

接下来，第九部分，【心法/原则卡】REST 已在，为何还要 MCP？。

原则，AI 更强不会自动给后端长出「可被 Agent 安全使用」的接口——工程师仍要设计知识边界与安全壳。

落地：虚构订单系统连载：查询 ，得到 多工具面 ，得到 写操作治理 ，得到 部署观测，全在同一仓库演进。

边界：本地可运行最小服务即可入门；企业 Copilot/客服再叠授权与远程 HTTP。

原文支撑：「如何把现有 Go 业务能力以标准化、可治理的方式开放给 AI Agent，仍是真实且重要的工程问题。」

接下来，第十部分，总结与行动。

结论

MCP 是 AI 消费既有后端的适配协议，不是替换 Go 业务代码。

CLI 与 MCP 分层不同，企业场景靠 MCP 提供治理；本地 Agent 可 Bridge 组合。

工程难点在契约、传输、身份、写操作幂等与协议测试，而非注册第一个 Tool。

14 讲订单系统路线覆盖从心智模型到生产交付的完整路径。

盘点一个只读查询 API，设计最小 Tool Schema 与描述（防误用）。

在 Go 项目里划出 internal/mcp 适配包，领域接口零依赖 SDK。

为写操作起草幂等键与审计字段，再暴露 Tool。

补一条 MCP 协议级集成测试（stdio 启停 + tools/list + tools/call）。
