一句话概括。本文解决的核心问题是：同一份任务交给同一个 Coding Agent，代码库「整洁度」不同会不会改变干活成本——SonarSource 用 6 组最小对照对、33 个任务、660 次试验证明：通过率几乎不变，但 token 消耗和反复读文件却实打实地不同。

接下来，第一部分，核心概念关系。

关系脉络如下：代码整洁度，SonarQube 量化，然后任务通过率，91.3% vs 92.1%，然后Token Footprint，输入 -7.1%，然后文件重复访问，-34%，然后API 账单，人类信用卡

接下来，第二部分，认知纠偏。

认知纠偏

常见误解：「AI 又不嫌代码丑，能跑通就行」——如果只盯 SWE-bench 通过率，这话成立；但 Agent 已在 12.8 万 GitHub 项目留下痕迹，单任务平均约 400 万 token，整洁度决定的是绕路和回头成本，不是能不能做完。

接下来，第三部分，反驳。

反驳

对立视角：「能跑就行」派 / 只盯 SWE-bench 通过率的评测党

通过率 91% 和 92% 几乎一样，说明屎山照样能交付——为 Lint 和重构停迭代一周，省下的 7% token 未必抵得过机会成本，尤其小团队一年 Agent 调用量可能还不到统计显著阈值。

接下来，第四部分，【概念拆解卡】最小对照对 (Minimal Pair)。

在讲什么问题，现实中找不到「除整洁度外完全相同」的两份代码库，研究者必须人工造出可对照的实验材料。

核心机制，两份代码库架构相同、依赖相同、测试行为相同，唯一差异是 SonarQube 违规数与认知复杂度；Slopify 管线做旧、Vibeclean 管线翻新，每步改完都跑测试，破坏行为的改动被拒绝。

关键理解，这样才能把 Agent 行为差异归因到「整洁度」单一变量，而不是架构漂移或测试覆盖不同。

典型场景，评估 Lint/重构对 AI 编程助手的影响；对比 Commons BCEL、Netflix Genie、CKAN 等公开库与 SonarSource 私有库。

边界说明，仅覆盖 6 组库、33 个手工任务、Claude Code 一套组合——不能外推到所有语言栈和所有 Agent 框架。

原文：「你几乎找不到两个除了整洁度之外完全一样的代码库。」

接下来，第五部分，【跨概念对比表】整洁 vs 脏乱代码上的 Agent 表现。

任务通过率，91.3%，92.1%，能不能做完，几乎无差别

输入 token，基准，多约 7.1%，脏乱代码让 Agent 往上下文塞更多无关内容

输出 token，基准，多约 8.5%，工具调用、代码、推理全线膨胀

推理字符，基准，多约 11.1%，脏乱代码上 Agent「想」得更多

文件重复访问，基准，多约 34%，改完又回头读，像「心里没底」的信号

读过文件数，略多 +3.2%，较少，干净版第一遍读更广，读完就下决心

接下来，第六部分，【决策/选型表】什么场景该优先投资代码整洁度。

跨模块功能开发（14 个任务赛道），模块边界清晰 + Lint 门禁，输入 token -10.7%，重复访问 -50.8%，收益最大，放任模块耦合增长，Agent 要在屎山里跨边界摸索，绕路成本最高

单文件「上帝方法」热点改动，消灭复杂度，而非机械拆函数，拆而不简会把逻辑摊到更多文件，导航成本可能上升，为过 Sonar 指标硬拆 10 个小函数，Genie 案例：干净版反而多用 8% 输入 token

团队日常 Agent 辅助开发，启用 SonarQube / ESLint / Ruff 等静态分析，整洁度从「给人看」变成「给 Agent 省钱」的量化机制，只靠注释堆砌可读性，注释消融实验证明：结构清晰比注释量更关键

评估 Agent 选型或模型升级，同时看通过率与 token footprint，SWE-bench 只盯 Pass rate 会漏掉账单差异，仅用 benchmark 通过率做决策，同一任务跑 10 次，最贵与最便宜可差 2.5 倍以上

接下来，第七部分，【避坑清单卡】Agent 时代的整洁度误区。

坑名，以为「拆了大函数 = 整洁 = Agent 一定更省」——翻新管线把 200 行 switch 拆成十个 helper，复杂度只是搬家。

原因，认知热点任务上 token footprint 基本不变；Agent 在干净版打开更多文件、每文件改更少行，总导航成本未必下降。

解法，重构时追问「复杂度是消灭了还是摊薄了」；跨模块场景优先清晰边界和命名，单点热点优先简化逻辑而非切块。

严重程度，小心——不会阻止任务完成，但可能让「整洁」标签反而增加 token。

统计方差陷阱：27 个非校准任务里 16 个干净版更省、11 个脏版更省；数据集层面 -7.1% 是平均趋势，单次重构结果可能完全相反。

模型泛化陷阱：实验仅用 Claude Code + Sonnet 4.6；Haiku 4.5 通过率太低无法读出 footprint 差异，结论不宜直接套到其他模型。

接下来，第八部分，【心法/原则卡】整洁代码的新记账方式。

原则，代码整洁度在 Agent 时代不过时，只是记账对象从「同事 review 体验」变成了「AI 绕路成本」。

为什么重要，22%~29% 的 GitHub 项目已有 Coding Agent 活动痕迹；整洁度几乎不影响「能不能做完」，却决定「要花多少钱、绕多少路、有没有把握」。

怎么落地，① 上 Lint/静态分析门禁；② 跨模块改动前理清边界与命名；③ 重构巨型函数时消灭复杂度；④ 用 SonarQube 等指标量化整洁度而非凭感觉。

适用边界，样本仅 6 库 33 任务；不能替代「该不该为业务速度牺牲质量」的产品决策，但提供了可量化的成本侧论据。

原文：「一个可预测、命名清晰的方法名，胜过一堆注释。」

注释消融：拉平两侧注释量后，省 token 优势反而更明显（一例从 +1.2% 变为 -18.0%），证明效应来自结构清晰而非「注释少」。

接下来，第九部分，总结与行动。

结论

SonarSource 660 次试验：整洁度几乎不影响 Agent 任务通过率，但显著影响 token 与重复读文件

输入 token -7.1%、输出 -8.5%、文件重复访问 -34%——脏乱代码让 Agent 多绕路、多回头、多「犯嘀咕」

跨模块改动收益最大；单点「上帝方法」若只拆不简，干净版未必更省

注释消融排除干扰后，结构清晰才是核心变量

研究局限：6 库、Claude 单栈、方差大——是统计趋势而非每次必省的简单等式

为常用 Agent 项目启用 SonarQube / ESLint / Ruff 等静态分析，把整洁度纳入 CI

规划跨模块功能时优先梳理模块边界与命名，这是 Agent 收益最大的场景

重构巨型函数前问一句：复杂度是消灭了还是只是切成更多块

评估 Agent 时除通过率外记录 token 与工具调用次数，别被 SWE-bench 单一指标误导

阅读 arXiv:2605.20049 原文，按自己代码库规模估算年化账单差异
