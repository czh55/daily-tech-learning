一句话概括。本文解决的核心问题是：在 AI 能批量产出 PR 时，个人如何把精力从「亲自写每一行」转到「设计厨房」——工具、流程、Agent 技能与验收标准，从而支撑极高合并吞吐而不失控。（正文抓取受掘金 WAF 限制，以下结合 API 摘要与行业同主题实践整理。）

接下来，第一部分，核心概念关系。

关系脉络如下：主厨（你），定菜单与标准，然后厨房设备，工具链 / CI，然后每位厨师 Agent，分工与培训，然后创意菜品，非流水线组装

接下来，第二部分，认知纠偏。

认知纠偏

误解：「合并 2500 PR = 更勤奋地手写和审每一单」。高吞吐来自前置的厨房设置占去大部分时间，成品是创造性产出而非简单拼装。

接下来，第三部分，反驳。

反驳

对立视角：「纯手工精品厨房」派

在竞品以 Agent 规模迭代时，主厨亲自炒每一道菜只会把瓶颈锁死在人类工时，厨房再精致也出不了馆规模。

接下来，第四部分，【概念拆解卡】主厨 vs 厨师（人机分工）。

在讲什么问题，一人团队如何在一个月内吸收海量 Agent 产出。

关键理解，主厨价值在设备（IDE、模板、仓库策略）、流程（分支、测试、合并规则）、以及对每个 Agent 的「培训」（系统提示、技能包、边界）。

和其他概念关系：与 Harness Engineering、SDD 框架、合并队列/无队列策略（参见超大规模 monorepo 实践）同谱系。

怎么落地用：先画厨房平面图再开灶——缺任一层，PR 越多越乱。

边界说明，强监管、强审计行业仍需人类逐单签字，不能照搬纯 Agent 厨房。

接下来，第五部分，【方法/工具卡】三高合并的前置投入清单。

核心思路：合并数是结果指标；输入指标是厨房是否可重复、可度量。

操作步骤，1）统一工具与仓库约定（lint、测试、目录），得到 2）为任务类型配置专用 Agent（评审、实现、修 CI），得到 3）自动化门禁（测试、diff 范围、意图说明），得到 4）主厨只处理例外与菜单级决策。

选型条件，个人或小团队 + 可接受 Agent 主导实现时。

避坑，没有流程先开多个 Agent 并行——冲突与评审债爆炸。

接下来，第六部分，【避坑清单卡】。

坑名：把「合并数」当 KPI 而忽视测试与回滚 — 吞吐虚假。

坑名：主厨下场炒菜 — 厨房无人维护，Agent 漂移。

坑名：所有菜一个厨师 — 应分技能 Agent，避免上下文混杂。

接下来，第七部分，【决策/选型表】精力分配。

启动期，工具、模板、CI、Agent 说明书，逐 PR 改代码

稳态高合并，菜单（优先级）、例外仲裁、度量，重复性实现

质量事故，改流程/门禁，而非只骂模型，单纯加人工审行数

接下来，第八部分，【心法/原则卡】创造性产品 vs 组装线。

原则，最终代码应是创造性艺术；若像流水线组装，说明厨房设计失败或任务被拆得过碎。

怎么落地，为 Agent 保留足够任务粒度与上下文；用规范驱动（Spec）约束方向而非逐行指挥。

接下来，第九部分，总结与行动。

结论

超高 PR 合并是厨房设计的结果，不是熬夜手写的结果。

工具、流程、Agent 培训三件套先于放量。

主厨角色是标准与例外，不是默认实现者。

画出当前「厨房」组件图并标出瓶颈。

为每类任务写 Agent 技能与禁区。

设合并前自动门禁，主厨只审意图与例外。

用合并数与回滚率联合度量，避免虚荣 KPI。
