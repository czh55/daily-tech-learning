一句话概括。本文解决的核心问题是：在 AI Agent 高频创建小仓库与巨型 monorepo 并发读取的双重压力下，Git 托管架构为何要从 Spokes 的三副本强一致 + 3PC 共识，转向以对象存储 WAL 为唯一真相源、本地磁盘退化为可丢弃缓存的 Continuity 范式。

接下来，第一部分，核心概念关系。

关系脉络如下：packfile 随机寻址，+ DAG 游走，然后Spokes，3 副本 + 3PC，然后Continuity / walgit，WAL + S3 + CAS，然后AI Agent 负载，海量小仓库 + CI 洪峰

接下来，第二部分，认知纠偏。

认知纠偏

常见误解：「把 packfile 存进 S3 就是 Continuity」。微软 Azure DevOps 早就在 blob 存储 packfile，但引用仍放关系型数据库；Continuity 的关键是完全基于 WAL、不依赖任何外部数据库，用 S3 CAS 取代 3PC 共识，本地仓库可随时从 WAL 物化重建。

接下来，第三部分，反驳。

反驳

对立视角：GitHub 基础设施团队 / 「Spokes 够用了」派

S3 每次读写的延迟和按请求计费，在 push 密集场景下会把成本与尾延迟直接暴露给开发者——Spokes 本地 NVMe 强一致虽重，却是经过二十年验证的确定性路径。

接下来，第四部分，【概念拆解卡】Spokes 架构——13 年行业标准及其天花板。

在讲什么问题，为什么 GitHub 2013 年推出的 Spokes 曾是最佳实践，却在 2026 年遇到扩展性瓶颈。

核心机制，不重新发明 Git，只在 packfile 层做文章；所有数据以正常 Git 仓库形式存本地 NVMe；多副本间用三阶段提交（3PC）保持强一致。一次 push 拆成 packfile（并行分发）和引用事务（3PC 同步）。

关键理解，Git 客户端对最终一致性极不友好——刚 push 完 fetch 读不到会直接懵掉，所以 Spokes 选了「重」的强一致路线。但 3PC 每一步延迟取决于最慢节点，副本越多推送吞吐反而越差（tail at scale）。

典型场景，2013 年「三副本」甜蜜点时代的企业 Git 托管，GitLab、Gitea 等本质都是 Spokes 变体。

边界说明，对付海量 AI Agent 创建的「用完即弃」小仓库时，仍要求三副本——下限太高；对付巨型 monorepo CI 并发读取时，三副本扛不住——上限太低。运维上每份拷贝都是「宠物」而非「牲口」，需巨大路由表和持续校验。

「Spokes 把仓库当宠物养，而不是牲口——每一份拷贝都金贵得不能出任何差错。」——Cursor 博客原话

相关概念：与 Continuity 的「无状态 + 对象存储真相源」形成对立；GitHub 早期 NFS/GFS/DRBD 的失败证明 packfile 随机游走在网络文件系统上是灾难。

接下来，第五部分，【概念拆解卡】Continuity——WAL + S3 + CAS 的新范式。

在讲什么问题，如何既保留「本地磁盘存真实 Git 仓库、复用上游工具链」的优点，又摆脱共识协议 + 路由表 + 宠物式运维。

核心机制，写前日志（WAL）存进 S3 兼容对象存储作为唯一真相源；本地磁盘上的仓库退化为可随时重建的热缓存。push 只有在 packfile 完整写入 S3 且引用事务通过 CAS 成功更新索引后才返回成功，保证线性化。

关键理解，没有选举、没有共识协议——所有 WAL 更新通过 S3 原子 CAS 同步，任何副本都可安全接受 push。副本间用 UDP gossip 通知「有新数据」，丢包无所谓，因为每次读都会向 S3 条件 GET 核对 etag。

典型场景，巨型 monorepo 铺开成百上千副本扛 CI 读取洪峰；AI Agent 批量创建的海量小仓库一个副本就够；长时间无流量仓库可从本地彻底 GC，下次访问再从 WAL 物化。

边界说明，压缩（repack）只在主节点做一次写回 WAL，其余副本下载已压缩 pack 用带宽换 CPU。rendezvous hashing 只是效率优化，映射过时也能在下一节点重新物化。

性能数据：100 副本压测读吞吐线性增长；S3 Standard 稳定 120 push/s；S3 Express One Zone 突破 300 push/s，瓶颈转为本地 Git 压缩速度。

接下来，第六部分，【跨概念对比表】Spokes vs Continuity vs walgit。

真相源，本地 NVMe 磁盘，S3 WAL，S3/GCS WAL（同架构）

一致性机制，三阶段提交共识，S3 CAS 原子交换，S3 CAS（同）

副本伸缩，副本越多 push 越慢，读吞吐随副本线性扩展，同 Continuity + 远程读取器优化

小仓库成本，强制三副本，一个副本 + S3 兜底，单文件二进制，零初始化

巨型仓库克隆，服务器扛全量，标准 Git 协议，bundle-uri 走 CDN 静态分发

运维复杂度，路由表 + 校验和修复，无状态，无路由表/数据库，配置指向存储桶即 serve

一句话结论，下限太高、上限太低，AI 时代负载模型答案，架构讲透后落地极快

接下来，第七部分，【方法/工具卡】walgit 快速上手路径。

核心思路：Shopify CEO Tobi Lütke 用一个周末把 Continuity 架构用 Rust 复刻为单文件开源实现，工程上更进一步。

操作步骤，

① 下载 walgit 单文件二进制，写配置指向任意 S3 或 GCS 兼容存储桶；

② 运行 walgit serve，第一次 git push 自动创建仓库，无需额外初始化；

③ 巨型 monorepo 启用 bundle-uri：每周全量 bundle + 每日增量，首次 clone 走 CDN 静态文件；

④ 小机器场景启用「远程读取器」（HTTP Range 按需读 S3）和「历史 pack」（commit/tree 本地，blob 留对象存储）。

选型条件，不想被 GitHub 绑定、又觉得自建 GitLab/Gitea 运维太重 ，得到 walgit 是「单文件 + 对象存储」轻量选项。

落地建议：内置 Git LFS、React Web UI、JSON API + SDK、Webhook 事件、保护分支策略、none/token/oidc 三种鉴权——麻雀虽小五脏俱全，可直接跑起来验证架构。

「walgit —— 一个单文件二进制 + 对象存储的 Git 服务器，没有数据库，没有主节点，没有任何真正重要的本地状态。」

避坑：不要把 walgit 当作 Cursor Origin 的替代品——它是架构验证和自建实验工具，生产级 SLA 和生态集成仍需评估。

接下来，第八部分，【决策/选型表】你的团队该继续 Spokes 还是迁移 WAL 架构。

传统团队，人类开发者有限并发，继续 Spokes / GitHub，成熟稳定，生态完整，急着迁移 Continuity，无明确痛点时不值得换架构

巨型 monorepo，CI 读取压垮三副本，Continuity / walgit，读吞吐随副本线性扩展，可铺上百副本，加 Spokes 副本，3PC 副本越多 push 越慢

AI Agent 批量创建海量小仓库，Continuity / walgit，小仓库一副本 + S3 兜底，可 GC 闲置本地缓存，Spokes 三副本，大量闲置副本占资源

不想厂商绑定，运维人力有限，walgit 自建，单文件 + 对象存储，无数据库/路由表，自建 GitLab 集群，运维成本对标 Spokes 宠物模式

首次克隆超大仓库，walgit bundle-uri，静态 bundle 走 CDN，服务器只补差异，标准 git clone，服务器扛全量传输

接下来，第九部分，【心法/原则卡】对象存储做真相源的系统设计范式。

原则，把本地磁盘降级为缓存，把对象存储提升为真相源——「什么都往 S3 里怼」从笑话变成严肃架构选择。

为什么重要，从 serverless Postgres（Neon）到 Git 托管，驱动力是云对象存储在可用性、持久性和成本上的持续进化；AI Agent 正在从根本上改变 Git 基础设施的负载模型。

怎么落地，① push 先写 WAL 到 S3 再更新引用（CAS）；② 本地仓库可随时从 WAL 物化；③ 读请求先条件 GET 核对 etag；④ 压缩只在主节点做一次。

适用边界，依赖 S3 延迟和 CAS 语义；极端低延迟场景需 S3 Express One Zone；完全离线环境不适用。

时代信号：一篇架构博客发布不到几天，资深工程师就能用 Rust 独立复刻可用开源实现——架构护城河正在被 AI 拉低的编码边际成本压缩。

接下来，第十部分，【避坑清单卡】Git 托管扩展性常见误区。

坑 1：用 NFS/GFS 共享 Git 仓库——packfile 随机游走在网络文件系统上是灾难。解法：GitHub 早期已证明此路不通。严重程度：致命。

坑 2：Spokes 副本无脑扩容——3PC 副本越多 push 吞吐越差。解法：读扩展用 Continuity 式线性副本，写扩展靠 WAL + CAS。严重程度：致命。

坑 3：AI Agent 小仓库仍维持三副本——大量闲置副本占资源。解法：一副本 + S3 兜底，闲置可 GC。严重程度：小心。

坑 4：把 packfile 存 blob 但引用放数据库——引入额外一致性复杂度。解法：完全基于 WAL，不依赖外部数据库。严重程度：小心。

坑 5：忽视 bundle-uri 对巨型仓库首次克隆的价值——服务器扛全量传输。解法：walgit 的静态 bundle + CDN 分发。严重程度：小心。

接下来，第十一部分，总结与行动。

结论与行动

Git 天生为分布式协作设计，packfile 随机寻址 + DAG 游走使集中托管扩展性极难，GitHub 在 NFS/GFS/DRBD 上交的学费证明了这一点。

Spokes（3 副本 + 3PC）统治 13 年，但 AI Agent 负载模型暴露其「下限太高、上限太低」——小仓库浪费副本，大仓库扛不住 CI 洪峰。

Continuity 用 S3 WAL + CAS 取代共识协议和数据库，本地磁盘退化为可丢弃缓存，读吞吐随副本线性扩展。

walgit 证明架构一旦讲透，一个周末即可 Rust 复刻为可用开源实现，含 bundle-uri 等工程增强。

Git 托管被 GitHub 垄断近二十年的市场，可能迎来 Cursor Origin 与开源 walgit 的新一轮洗牌。
