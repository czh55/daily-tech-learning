一句话概括。本文解决的核心问题是：MCP 协议为何在 SDK 月下载逼近 5 亿、连接器超 950 个的规模下，必须把核心从有状态双向流改成无状态 HTTP 请求/响应，以及开发者应如何迁移握手、会话、elicitation 与鉴权相关实现。

接下来，第一部分，核心概念关系。

关系脉络如下：旧：initialize 握手，Mcp-Session-Id 粘性路由，然后自描述 _meta 请求，任意 LB 轮询，然后MRTR 多轮往返，替代反向双向流，然后扩展框架，Apps · Tasks · EMA

接下来，第二部分，认知纠偏。

认知纠偏

常见误解：「无状态 = MCP 服务器不能记业务状态」——正确理解是：传输层不再藏隐式会话；跨调用状态由服务器铸造显式 handle 交给模型传递，比黑盒 Session-Id 更可观测、更可组合。

接下来，第三部分，反驳。

反驳

对立视角：资深分布式架构师 / 「会话才是正确抽象」派

把会话砍掉只是把状态管理成本转嫁给应用层和客户端 MRTR 循环——对深度依赖服务器主动 push、长链路编排的复杂 Agent，无状态 HTTP 未必比精心设计的会话层更省总复杂度。

接下来，第四部分，【概念拆解卡】有状态 MCP 的生产痛点与无状态改造目标。

在讲什么问题，早期 MCP 要求 initialize/initialized 握手 + Mcp-Session-Id 会话，服务器还能反向发起 elicitation/sampling/roots，导致负载均衡必须粘性路由、共享 Redis 会话、网关需解析 JSON 体才能鉴权限流。

核心机制，2026-07-28 把状态从传输层拿掉——每个请求自描述协议版本、客户端身份与能力（_meta），可选 server/discover 探能力，不再强制握手。

关键理解，协议火了（Tier1 SDK 月下载近 5 亿），但运维复杂度成了规模化瓶颈；这次修订是「从少年到成年」的架构还债，而非功能堆砌。

典型场景，Serverless/边缘一键扩容 MCP 服务、多实例无共享存储部署、网关按 HTTP 头做路由限流。

边界说明，需要长连接双向流的 legacy HTTP+SSE 已弃用；深度依赖会话 ID 的旧实现迁移成本最高。

「把 MCP 从一个有状态的双向协议，改造成彻底的无状态请求/响应协议。」——MCP 官方博客

接下来，第五部分，【方法/工具卡】MRTR 替代服务器反向请求。

方法名：Multi Round-Trip Requests（SEP-2322）

核心思路：服务器不再反向发起请求，而是在响应中标 resultType: input_required 并附问题；客户端收集用户输入后，带着 inputResponses 重新发起原始调用。

操作步骤，① 识别原 elicitation/sampling/roots 反向流逻辑；② 改为检测 input_required 响应；③ 收集输入后重发同 method 调用并填 inputResponses；④ 在无状态 Supabase MCP 等场景验证高风险操作前确认。

选型条件，需要用户确认、缺参补全、且服务器本身无状态运行——MRTR 是官方无状态路径，不再依赖常驻双向流。

Supabase 产品负责人：无状态 MCP 长期无法轻松接入 elicitation，MRTR 让他们能在删数据前跟用户确认。

避坑：仍假设服务器能「主动 push」到客户端——无状态核心下必须客户端驱动多轮，调度逻辑要改到客户端循环。

接下来，第六部分，【跨概念对比表】旧会话模型 vs 2026-07-28 无状态模型。

连接建立，initialize + initialized 握手，每请求 _meta 自描述，可选 discover，握手非必需，冷启动更快

负载均衡，粘性路由 + 共享会话存储，普通轮询即可，横向扩容像普通 HTTP 服务

二次确认，elicitation 等反向双向流，MRTR input_required 多轮，客户端驱动，适合 Serverless

网关鉴权，解析 JSON 才知道 method，Mcp-Method + Mcp-Name 请求头，WAF/限流可直接按头路由

业务状态，隐式 Session-Id，显式 handle 由模型传递，模型可见、可组合，非黑盒

接下来，第七部分，【决策/选型表】迁移与集成怎么排优先级。

硬编码 Mcp-Session-Id，改为自描述 _meta + 显式 handle，会话头已移除（SEP-2575/2567），继续依赖粘性路由，与无状态核心冲突，无法 Serverless 扩容

elicitation/sampling/roots，MRTR + inputResponses，反向流已不可用，自建 WebSocket 旁路，偏离标准，客户端兼容性差

资源未找到错误处理，匹配 -32602 Invalid Params，错误码对齐 JSON-RPC（SEP-2164），仍匹配 -32002，升级后逻辑失效

企业 IdP 接入，OAuth 2.0/OIDC + EMA 扩展，Issuer 校验、凭证绑定、CIMD 方向，继续依赖 DCR 为主路径，DCR 已标记弃用，未来移除

新能力试水，扩展框架（Apps/Tasks/EMA），先扩展验证再考虑并入核心，直接改核心规范，违背生命周期与一致性测试门槛

接下来，第八部分，【避坑清单卡】升级 2026-07-28 必查项。

坑名，客户端仍匹配 -32002 资源未找到

原因，错误码改为 JSON-RPC 标准 -32602。

解法，全文搜索 -32002，改为 -32602 或按 Invalid Params 语义处理。

严重程度，致命——错误分支静默失效。

坑名：新项目仍基于 Roots/Sampling/Logging——已弃用（SEP-2577），至少 12 个月缓冲但 logging/setLevel 在 2026-07-28 路径上直接被拒；日志改用 _meta 的 io.modelcontextprotocol/logLevel。

坑名：列表接口不读 ttlMs/cacheScope——浪费带宽且 prompt 缓存断线后不稳定；tools/list 等现支持客户端缓存策略。

接下来，第九部分，【心法/原则卡】扩展框架与生命周期政策。

原则，新能力先扩展、后核心；弃用至少 12 个月缓冲，一致性测试门槛（SEP-2484）是 Final 提案的前提。

为什么重要，避免每次大版本「伤筋动骨」；MCP Apps、Tasks、EMA 已在扩展框架转正。

怎么落地，跟踪扩展版本号；Claude 连接器目录提交按新文档流程；Bedrock AgentCore Gateway 等已支持 UpdateGateway 一键升级。

适用边界，仅做本地实验可滞后；生产多实例、企业鉴权、目录上架应优先对齐 2026-07-28。

接下来，第十部分，总结与行动。

结论

MCP 2026-07-28 是协议史上最大修订：无状态核心、移除握手与会话、自描述 _meta 请求。

MRTR 用 input_required + inputResponses 替代 elicitation/sampling/roots 反向流，利好无状态 Serverless 部署。

请求头路由、列表 ttlMs/cacheScope、错误码 -32602 等「边角」改动对网关与客户端缓存落地很关键。

扩展框架收纳 MCP Apps、Tasks、EMA；OAuth 加固并弃用 DCR 转向 CIMD；Roots/Sampling/Logging 弃用但有缓冲期。

Claude 率先适配，生态伙伴反馈聚焦降复杂度、可扩容、易接入。

审计代码中 Mcp-Session-Id、initialize 握手与 -32002 硬编码。

将 elicitation 等反向逻辑改为 MRTR 客户端多轮循环。

网关配置 Mcp-Method/Mcp-Name 头路由与限流规则。

评估 OAuth Issuer 校验与 CIMD 迁移路径，停止以 DCR 为长期方案。

计划提交 Claude 连接器目录时对照 2026-07-28 官方提交流程与 SDK 分级测试。
