一句话概括。本文解决的核心问题是：公司内部跑了五年的私有 Go module 方案为何在白盒交付时全线失效——真正的痛点不在 GOPROXY 怎么配，而在 import path 这条「承诺」一旦跨出组织边界就必须整套重建。

接下来，第一部分，核心概念关系。

关系脉络如下：网络边界，GOPROXY/VCS 不可达，然后信任边界，凭证不能外泄，然后组织边界，vanity path 失效，然后import path 翻译层，必须重建

接下来，第二部分，认知纠偏。

认知纠偏

常见误解：「私有 module 拉取是内部基础设施问题，配好 GOPROXY 就一劳永逸」——五年稳定运行只证明边界内成立；代码一旦白盒交付，拉代码的人和存代码的服务器不再共享同一网络与信任域。

接下来，第三部分，反驳。

反驳

对立视角：「全用 go mod replace 直连内部仓」实用派

replace 只能救本地编译，团队协作和 CI 各写各的 replace 路径，版本锁不住——你省下的 vanity 层，最后会变成 N 份不可合并的 go.mod 补丁。

接下来，第四部分，【概念拆解卡】Vanity Import Path 与「翻译层」。

在讲什么问题，小厂希望 import path 干净（mycompany.com/go/common），但代码实际在内网 Git 上，go get 如何找到真实仓库？

核心机制，govanityurls 把 vanity path 翻译成真实 VCS 地址；内部 GOPROXY 统一代理公共与私有 module；开发者只改 GOPROXY，拉取过程透明。

关键理解，import path 不是字符串装饰，而是「只在特定网络边界内才成立的承诺」——域名解析、go-get meta、代理路由缺一不可。

典型场景，小厂没有 git.company.com 式内网 VCS 域名，却想用语义化私有路径复用公共代码。

边界说明，方案默认拉代码者与 VCS 在同一信任域；跨组织交付时 vanity 服务部署在己方，对方网络里 path 即死链。

原文：「这个 Go module 的 import path 本身，是一个只在我们自己的网络边界里才成立的承诺。」

接下来，第五部分，【方法/工具卡】内部方案 vs 跨边界重建。

核心思路：边界内用 govanityurls + Nginx + GOPROXY；边界被打破时在目标组织内重建简化版映射与拉取链路。

操作步骤（跨边界交付）：1. 在客户环境申请域名或内网 DNS ，得到 2. 配置 vanity 映射指向授权仓库 ，得到 3. 设置 GOPROXY 或 GOPRIVATE ，得到 4. 单独开通仓库权限（不交内部 VCS 凭证），得到 5. 验证 go mod tidy / go build。

选型条件，白盒源码交付、客户自编译维护；SaaS 黑盒调用 API 则不走此路径。

原文：「整个过程和五年前第一次搭建时几乎一样繁琐，唯一的区别是，这次要在一个我们不熟悉、不受控的环境里，重新做一遍。」

落地：作者将五年重复操作封装为 gvu（gomodvanityurls）CLI，一行命令完成 vanity 映射与私有 module 分发配置。

避坑：不要把内部 VCS 凭证交给客户——等于开放全部私有代码；应在客户侧独立部署翻译层与最小权限仓库。

接下来，第六部分，【决策/选型表】私有 module 方案怎么选。

大厂内网统一 VCS，import path 直指 git.company.com，go get 原生工作，无需翻译，vanity + 外网域名，多一层无意义映射

小厂边界内复用，govanityurls + 内部 GOPROXY，语义化 path + 透明拉取，仅 go mod replace，可应急但难规模化治理

白盒交付给客户，客户环境重建映射 + 最小权限仓，不泄露己方信任域，复用己方 GOPROXY，客户网络不可达

频繁新增私有仓，CLI（gvu）自动化 vanity 配置，避免手写 vanity.yml 运维抗拒，纯 Web 管理后台，与开发者心智模型脱节

接下来，第七部分，【跨概念对比表】边界内稳定 vs 跨边界交付。

GOPROXY 可达性，全员指向内部代理，客户机/CI 访问不到，代理假设失效

凭证策略，内网 SSH/Token 统一管，不能给全量 VCS 权限，信任边界割裂

vanity 服务，部署在己方，全员可用，客户 DNS 解析不到己方，path 变死链

运维动作，改 vanity.yml、调 Nginx，在陌生环境重做全套，重复劳动暴露本质

接下来，第八部分，【避坑清单卡】私有 module 五年踩坑史。

坑名，以为「内部跑通 = 问题已解决」，忽视跨边界场景。

原因，五年优化都在同一边界内打磨体验，从未质疑「拉代码的人与存代码的服务器同域」这一隐含前提。

解法，设计交付模式时提前问：代码会不会离开组织？会则预埋客户侧映射方案。

严重程度，致命（客户 go mod tidy 直接 lookup 失败）。

坑名：每次新增私有仓手动改 vanity.yml——开发者天然抗拒运维琐事，配置腐化后更难跨边界复制。

坑名：Gerrit 迁 GitLab 时 SSH 算法不匹配——翻译层背后仓库换了，映射与密钥要同步，否则边界内也会炸。

接下来，第九部分，【心法/原则卡】CLI 重新成为控制面。

原则，散落在 vanity.yml、Nginx、GOPROXY 里的动作，本质上应该是一个命令的事。

为什么重要，Web UI 图形化运维动作，但开发者高频操作终收敛为一行命令（gh repo create、wrangler deploy）；AI 时代 CLI 更是事实控制面。

怎么落地，跨边界重建时用 gvu 等工具替代手工三板斧；内部新增私有仓也避免纯手动改配置。

适用边界，面向开发者的基础设施；纯业务人员配置场景仍可能需要 UI。

原文：「命令行不再只是极客的偏好，它正在重新成为很多产品事实上的控制面，AI 时代尤甚。」

接下来，第十部分，总结与行动。

结论

私有 module 五年稳定，证明的是边界内方案成熟，不是跨组织交付已解决。

白盒交付同时击穿网络、信任、组织三层边界，import path 翻译层必须就地重建。

Go 用 import path 做域名解析，把「私有代码分发」问题暴露得格外鲜明，但本质适用于所有跨信任边界的代码交付。

重复的手工配置应收敛为 CLI 控制面——gvu 是作者对五年同一问题不同场景的封装。

真正痛点永远出现在边界被打破的那一刻，而非 GOPROXY 配没配好。

盘点现有私有 module：import path 承诺在哪些网络/组织边界内才成立？

若有白盒或跨客户交付，提前设计客户侧 vanity + 最小权限仓，而非临时救火。

新增私有依赖时避免纯手写 vanity.yml，用自动化工具保持可复制性。

交付前在「干净环境」跑一遍 go mod tidy && go build，模拟客户第一天。

评估 gvu 等 CLI 是否能把 Nginx/GOPROXY/vanity 三板斧收成一行命令。
