一句话概括。本文解决的核心问题是：面对亿级去重、流式频次与 P99 分位数等场景，何时用 Bloom Filter、HyperLogLog、Count-Min Sketch、T-Digest 与 Top-K Sketch 等 Sketch 以固定 KB～MB 内存换取有界误差，而不是让 map 与全量延迟数组撑爆内存与 GC。

接下来，第一部分，核心概念关系。

关系脉络如下：成员可能存在?，然后Bloom，然后多少不同键?，然后HLL，然后频次?，然后CMS，然后P99 延迟?，然后T-Digest，然后Top-K 热点?，然后Top-K

接下来，第二部分，认知纠偏。

认知纠偏

误解：概率结构等于「随机不准」。作者强调误差来自可证明的哈希与 sketch 模型；固定种子下结果可复现，业务需先接受假阳性或单向高估等明确误差类型。

接下来，第三部分，反驳。

反驳

对立视角：「精确 map 更简单、可调试、不会误导 SLO」

在十亿级流式场景里，精确结构带来的 OOM、Full GC 与跨区 Merge 成本往往先击穿 SLO，而用有界误差的 Sketch 做预筛与聚合才是可控工程——真正风险是未声明误差就当作精确数下单。

接下来，第四部分，【概念拆解卡】概率性数据结构 / Sketch。

在讲什么：不保存全量原始数据，只保留回答特定查询所需的紧凑摘要。

关键理解，用可声明的误差模型换内存；传统 Set 答「在或不在」，Bloom 答「一定不在或可能在」。

关系：与精确 map 对立；与 LSM、缓存、流式引擎中的预过滤层互补。

落地：先写清业务容忍的 FP 率、基数误差或分位数偏差，再选结构与参数。

边界：财务、库存等必须精确到个位时不能用近似替代。

原文：「我们能否不保存完整数据，只保留足以回答特定问题的信息？」

接下来，第五部分，【跨概念对比表】三种误差模型。

假阳性，不存在却判「可能存在」，Bloom Filter，可多做一次 DB/磁盘查询，不能当「一定在」

假阴性，存在却判不存在，经典 Bloom 无，误判清零比特会导致 FN，故不支持删

估算误差，数值接近真值，HLL、CMS、T-Digest，CMS 单向偏高：估算 ≥ 真实

接下来，第六部分，【方法/工具卡】Bloom Filter（成员查询）。

机制：k 个哈希置位 m 比特；任一位为 0 则必不存在，全 1 则可能存在。

步骤：① 预估 n 与目标误判率 p ，得到 ② m ≈ -n·ln(p)/(ln2)² ，得到 ③ go get github.com/nalgeon/unsure/bloom ，得到 ④ 缓存/LSM 前短路无效 I/O。

依据：百万 URL、1% FP 约 1.2MB；VictoriaLogs 用其跳无关日志块。

避坑，超设计 n 误判升；不支持删；要删用 Counting Bloom 或静态用 Binary Fuse。

接下来，第七部分，【方法/工具卡】HyperLogLog（基数 UV）。

机制：哈希前导零 + 多寄存器；内存由精度 p 定，与元素个数无关。

落地：unsure/hll；Merge 后全局 UV 可在分片聚合（DataFusion approx_distinct）。

边界：不能枚举具体元素；标准误差约 1.04/√m。

原文案例：「SELECT approx_distinct(user_id) FROM access_logs」

接下来，第八部分，【方法/工具卡】Count-Min Sketch + Top-K。

CMS：d×w 矩阵多哈希，查询取行最小值；保证以 1-δ 概率：真实 ≤ 估算 ≤ 真实 + ε·N。

注意：误差相对总流量 N，低频键相对误差可能很大。

Top-K：HeavyKeeper 衰减 + 最小堆，适合流量倾斜；频次仍为估算。

落地：countmin.New(0.001, 0.01)；API/IP 分钟级窗口可用分片 Sketch 到期丢弃。

接下来，第九部分，【方法/工具卡】T-Digest（P95/P99）。

机制：带权质心压缩分布，尾部用小质心保极端分位。

落地：unsure/tdigest Add + Quantile(0.99)；多机 Merge 得全局近似分位。

边界：近似非随机化概率保证；合并过多可能略损尾部精度。

接下来，第十部分，【决策/选型表】问题 ，得到 结构。

元素可能存在，Bloom / Binary Fuse（静态），无删、超容误判升，精确 membership 证明

不同元素个数，HyperLogLog，不能查单键，精确 COUNT DISTINCT 报表

流式频次，Count-Min Sketch，不能枚举全部键，低频键高精度计费

P99 延迟，T-Digest，合并降精度，保存每条原始 trace

热门 Top-K，Top-K / HeavyKeeper，近似排名，均匀分布下的精确排序

接下来，第十一部分，【避坑清单卡】生产接入 Checklist。

财务级精确：订单金额、库存禁止为省内存上 Sketch。

容量规划：Bloom/CMS 参数绑定预估规模，耗尽要有扩容或重建策略。

时间窗：多数 Sketch 不支持删；按分钟分片，过期丢旧摘要。

分布式合并：HLL/T-Digest Merge 需统一精度参数，注意误差累积。

对抗输入：可控哈希输入需安全哈希、容量上限，防冲突攻击。

基准：unsure 公布的是特定硬件数据；上线前对自己的分布做 Benchmark。

接下来，第十二部分，【心法/原则卡】先问是否必须保存全量。

原则，并非所有问题都要 map[string]uint64；明确可接受误差后，几 KB Sketch 可能足够。

反面：1 亿 UV 用 map[string]struct{} 带来指针、桶与 GC 的隐形放大。

落地：列表五种武器 + unsure 子包 bloom/countmin/hll/tdigest/topk；关注 Blocked Bloom 的 cache-line 友好布局。

边界：中小数据仍用 map 最简单可靠。

接下来，第十三部分，总结与行动。

结论

五大 Sketch 分别覆盖成员、基数、频次、分位数与热点五类查询。

假阳性、假阴性与单向估算误差须在需求阶段写进 SLA。

unsure 提供 Go 实操入口，并强调缓存行级布局等工程优化。

VictoriaLogs、DataFusion、监控栈证明这是基建而非常识题。

时间窗、合并、对抗输入与 Benchmark 决定能否上生产。

审计服务里不断增长的 map，标注是否可改为 Bloom/HLL/CMS。

为缓存穿透路径试装 Bloom 短路，测量减少的 DB 命中。

在分析 SQL 中对非财务指标试用 approx_distinct。

监控 P99 用 T-Digest 替代全量延迟切片存储。

用 go test bench 对比 unsure 与当前 map 方案的内存与 QPS。
