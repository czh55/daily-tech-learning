一句话概括。本文解决的核心问题是：在 Go 1 兼容性承诺锁死 v1 默认行为的前提下，官方如何用独立 v2 包与 jsontext 双包架构既修复大小写不敏感、重复键等历史债，又让存量代码零改动继续跑在「换芯不换 API」的 encoding/json 上。

接下来，第一部分，核心概念关系。

关系脉络如下：v1 文档化行为，14 年不变，然后sonic/go-json，兼容复刻，然后jsontext，纯语法，然后json/v2，语义映射，然后encoding/json，DefaultOptionsV1

接下来，第二部分，认知纠偏。

认知纠偏

常见误解：「Go 1.27 终于修了 json 的 Bug」。大小写不敏感匹配等在 v1 路径上仍由 DefaultOptionsV1 刻意保留；v2 才是大小写敏感、重复键报错、非法 UTF-8 拦截的新语义，迁移需显式换 import 与 Options。

接下来，第三部分，反驳。

反驳

对立视角：「永远不换标准库」的维护者 · 够用就行派

再叠一个 v2 包只会让团队永远维护三套语义（v1、v2、sonic），十四年修不动的根因是承诺本身——与其学 16 条差异，不如继续 import 第三方并锁定版本。

接下来，第四部分，【概念拆解卡】jsontext 与 json/v2 解耦。

在讲什么问题，v1 把语法解析与 Go 类型映射缠在一起，嵌套 UnmarshalJSON 导致整段 JSON 被解析两次甚至指数级放大（Kubernetes OpenAPI 案例）。

核心机制，encoding/json/jsontext 只管分词、流式与规范校验；encoding/json/v2 管结构体标签、Options 与类型映射。重复键、非法 UTF-8 在语法层即失败，错误前缀 jsontext:。

关键理解，拆分首要动机是 protojson 式「严苛规范 + 真流式」，性能是架构红利而非唯一目标。

典型场景，自定义高性能管道只复用 jsontext；业务 API 用 v2.Marshal/Unmarshal 并配置 Options。

边界说明，jsontext 倾向 aliasing 与极致吞吐，官方明确「不是给大众随处滥用」；大众默认仍走 v1 或谨慎配置的 v2。

原文：将语法与语义清晰拆解并不是后来为了优化性能而做的事后剥离，而是在最初的 API 提交中就已被深度锚定。

接下来，第五部分，【方法/工具卡】迁移与尝鲜路径。

标签：标准库升级 · 渐进迁移 · 构建期开关

操作步骤，1) Go 1.25+ 用 GOEXPERIMENT=jsonv2 本地试编译 ，得到 2) Go 1.27 直接 import "encoding/json/v2" ，得到 3) 对照 16 项行为差异清单做回归（重复键、字段名大小写、EOF 校验等），得到 4) 对 time.Duration 在 v2 中显式配置时间格式，勿假设纳秒整数默认 ，得到 5) 存量服务继续 encoding/json 则自动享受 v2 底座性能，语义仍 v1。

选型条件，新服务或安全敏感 JSON 解析选 v2；强依赖 v1 怪异行为（大小写模糊匹配）的遗留系统暂缓换 import。

落地：勿对 v2 错误信息做字符串正则匹配——源码在 cannot 与 unable to 间蓄意随机化，防范海勒姆定律。

接下来，第六部分，【跨概念对比表】v1 默认 vs v2 语义。

字段名匹配，大小写不敏感，大小写敏感，安全与可预测性向 v2 倾斜

重复键，静默取后者，语法层报错，v2 更早失败

time.Duration，纳秒整数，无默认格式则 Marshal 报错，强迫显式格式选择

Decode 流，易忽略 EOF，UnmarshalRead 读到 EOF，减少半包 JSON 漏检

实现层，Go 1.27 起基于 v2+DefaultOptionsV1，原生新实现，同底座、不同选项

接下来，第七部分，【避坑清单卡】第三方库与兼容陷阱。

坑 1 — 以为 drop-in 更快就更「正确」：go-json/sonic 为 100% 复刻 v1 缺陷，go-json 在字段≥17 时曾漏掉大小写不敏感（位图优化路径）。严重程度：致命（静默语义漂移）。

坑 2 — 依赖错误文案断言：v2 随机化报错措辞，测试若匹配固定字符串会 flaky。解法：断言错误类型/结构化字段。

坑 3 — v2 直接 Marshal Duration：Go 1.27 v2 无 format 标签（发布前撤回），原生 Duration 需自定义类型或 Options。严重程度：小心（迁移卡点）。

坑 4 — 忽视 CL 224079 教训：即便官方补丁只慢 1%，仍因破坏存量行为被拒——评估「修 Bug」前先查是否文档化行为。

接下来，第八部分，【决策/选型表】JSON 方案怎么选。

存量 Go 服务零改动，继续 encoding/json，1.27 底层已换 v2 引擎，强行改 v2 import，16 项语义差需全量回归

新 API / 严格 JSON，json/v2 + 明确 Options，重复键与 UTF-8 早失败，v1 默认，历史宽松行为

极致吞吐、可控内存，jsontext + 自写映射，语法层流式与 aliasing，手写 bytes 切分，规范与安全难保证

要最快且保持 v1 语义，sonic/go-json（知悉风险），社区优化，标准库 v2 语义，目标不同：兼容 vs 正确

接下来，第九部分，【心法/原则卡】兼容承诺高于「显然更好」。

原则，文档写明的「糟糕默认」在 Go 1 承诺下不是可悄悄修的 Bug，只能新包新语义或 v2 底座 + 兼容标志托举 v1。

为什么重要，第三方为性能背负复刻 v1 缺陷的包袱，说明「不换 API 的修复」在生态层已证明成本极高。

怎么落地，新代码默认 v2；遗留用 v1；读 #71497 行为差异表；性能对比用自家 payload 基准，勿迷信单一数字。

适用边界，跨语言 JSON 若依赖 v1 大小写模糊匹配，换 v2 会破坏对接方——需协议层显式约定字段名。

接下来，第十部分，总结与行动。

结论

encoding/json 的已知缺陷因 Go 1 兼容性文档化而无法在 v1 API 内根治，CL 224079 等修复尝试因 1% 性能与行为破坏被拒。

Joe Tsai 主导的 v2 以 jsontext（语法）+ json/v2（语义）双包落地，Go 1.27 转正；v1 整包重构为 v2 + DefaultOptionsV1，实现零 API 换芯。

第三方高性能库为无缝替换被迫复刻 v1 缺陷，甚至引出生产 Bug；官方选择不合并 unsafe 方案，以调查数据优先可靠与安全。

v2 用随机化错误文案抵制字符串依赖；time.Duration 与 format 标签妥协使 v2 原生 Duration 需显式配置。

对照官方 v1/v2 行为差异 Playground 示例，标记自己代码是否依赖大小写不敏感或重复键。

新项目试点 encoding/json/v2，为 Duration 等类型提前定序列化格式。

审查测试里对 json 错误信息的字符串匹配，改为稳定断言方式。

若使用 go-json/sonic，关注字段数边界与版本发布说明中的兼容性修复。
