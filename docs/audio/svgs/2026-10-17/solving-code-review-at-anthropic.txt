欢迎收听每日技术学习语音讲解。本期主题，Claude Code 团队如何做代码审查。标签包括Agent 规模工程、分级防御、审查收敛、You Land It。本次讲解预计时长 约 10 到 11 分钟，共 12 个部分。好，我们开始。

一句话概括。本文解决的核心问题是：当约 90% 代码由 Agent 编写、PR 吞吐翻倍时，如何用「持续审查 + 风险分级 + 机器读 diff」把人类注意力留给架构与意图，同时让回滚率下降超 40%。

接下来，第一部分，核心概念关系。

关系脉络如下：本地验证，+Skills，然后多 Agent，投票审查，然后安全，阻断，然后低/中/高，人工档，然后Merge Queue，+Flag，然后事故，得到Eval

接下来，第二部分，认知纠偏。

认知纠偏

误解：Agent 时代可以取消 Code Review。Anthropic 并未取消审查，而是把「是否有人读过」换成「哪道检查最能拦截该变更的风险」，并把审查前移到打字时的拼写检查阶段。

接下来，第三部分，反驳。

反驳

对立视角：「速度至上、零人工合并」激进派

把阅读 diff 全交给机器，等于把「我们是否该做」与隐性架构债一起自动化——合并翻倍时你省的是眼疲劳，丢的是产品灵魂与跨团队否决权。

接下来，第四部分，【概念拆解卡】审查目的的两条腿。

在讲什么问题，日合并从数千到数万后，逐行人肉审查失效，但质量不能丢。

关键理解，职责一是发布前发现问题；二是团队共享上下文。本文主攻前者，后者用 Claude 切片解读 + 透明频道协作替代死磕 diff。

怎么落地用：为每条变更问「风险是什么？哪道自动化/人工检查最合适？」而非「谁还没点批准」。

边界说明，外部提交仍保留人工「我们真的要做吗」闸门，机器不能替代产品判断。

原文依据，「是否有人读过」只是粗糙代理指标，核心是可拦截的风险与检查匹配。

接下来，第五部分，【方法/工具卡】提 PR 前的验证闭环。

核心思路：绝大多数审查在 PR 创建前完成；Claude 必须展示可运行验证结果，不能只说「已完成」。

操作步骤，1）配置测试/构建/截图对比 ，得到 2）子 Agent 在干净上下文审 diff ，得到 3）可选 Skills：找 Bug、精简 diff、E2E、UI 设计准则 ，得到 4）再开 PR。

选型条件，Boris Cherny 估计「能验证自己工作」可把交付质量提升 2–3 倍。

避坑，审查器反复报同类问题时，应改 Skill、加 Lint 或更新规范，而不是让人重复关评论。

CLAUDE.md 保持简短并索引其他文档；REVIEW.md 由 Code Owner 写清「失败长什么样」、限制 nit 数量、要求带行号证据。

接下来，第六部分，【方法/工具卡】PR 级 AI 审查与共识过滤。

核心思路：每个 PR 先经 Claude 结合仓库意图审 diff；多 Agent 并行找 Bug，独立验证 Agent 投票后才发布意见。

操作步骤，设置 Quick/Standard/Deep ，得到 过滤纯风格/nit ，得到 行内评论按 Important/Nit/Pre-existing 分级 ，得到 每条必须修复或解释关闭 ，得到 Agent 可夜间自动修一轮。

对比相邻方法，本地 /code-review 轻量；Team/Enterprise 的 Code Review 功能更重，内部 PR 有实质意见比例从 16% 升到 54%。

避坑，Agent 作者看到 nit 会老实改代码触发新轮次——噪音成本远高于人类忽略一条评论。

接下来，第七部分，【决策/选型表】三档风险与人工批准。

怎么落地，Agent PR 的指导人列为必需审查人，责任等同手写代码。

低，文档、文案、内部功能、Flag 后增量，自动化全绿即可，分类器读 diff 定级，非提交人自报

中，常规产品、缓存/自动更新/系统提示词，1 人，受信任作者可走轻通道

高，核心路径、CI 工作流等敏感区，2 人，Agent 批准≠人类批准；新 commit 作废旧批准

接下来，第八部分，【跨概念对比表】传统终点审查 vs 持续审查。

发生时机，写完才等人看，提交前已多轮机器审，审查像拼写检查

人类角色，读每一行 diff，架构、品味、高危区、验证据，注意力上收

失败信号，评论数，回滚率+事故率+人工等待时长，省时间不能转嫁到救火

上下文学习，读队友 PR，让 Claude 生成模块解读/Artifact，深度讲解 > 改文案 diff

接下来，第九部分，【避坑清单卡】Agent 审查无限拉扯。

坑名，作者 Agent 与审查 Agent 夜间来回 50+ 轮，人类早上才叫停。

原因，默认多轮重审；约 59% 意见在第一轮就存在，后续在挖陈年旧账；Agent 对 nit 也会改代码。

解法，三轮封顶并要求重新审视方案；之后只审增量 diff；要求一次性修同类问题；禁止重复已发意见；用「轮数」与「召回率」一起度量。

严重程度，对 Agent 主导仓库：致命（吞吐与士气）。

接下来，第十部分，【心法/原则卡】You Land It, You Own It。

原则，合入者负责跟进问题，但靠小粒度、可回滚、Flag、免责复盘文化兜底，而非人肉逐行防错。

怎么落地，合并队列重跑 main 上检查；内部狗粮 + latest/stable 通道；事故转 Eval 每日跑审查器回归。

适用边界，计费、发布、安装脚本等始终人类双签；低风险自动化合并边界随信任前移。

接下来，第十一部分，总结与行动。

结论

审查指标应从「有人读过」转为「风险与检查匹配」，并前移到 PR 之前。

人类稀缺资源应花在方向、高危代码、架构模式与验证凭据上。

AI 审查需共识过滤 + 分级 + 轮数封顶，否则 Agent 噪音会自我放大。

低/中/高风险分级 + 合并队列 + Flag 是规模下的默认组合。

事故 Eval 与回滚率是审查策略的真实记分牌。

写简短 CLAUDE.md 并为关键模块补 REVIEW.md（失败定义 + 证据要求）。

在单仓库试点 AI 审查，调几周后再推广；合并前 unresolved 讨论清零。

定义三档风险并由分类器读 diff，禁止 Agent 批准顶替人类名额。

为 Agent 工作流设审查轮数上限与增量-only 重审规则。

把历史事故 PR 收成 Eval，模型/提示词升级后全量回归。
