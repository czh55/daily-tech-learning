接下来，第一部分，核心概念关系。

关系脉络如下：① 具身大模型，VLA/世界模型，然后② 仿真/训练，Isaac·Gazebo，然后③ OM1，Agent Runtime，然后④ ROS2/Zenoh，中间件，然后⑤ 本体 HAL，步态·舵机

接下来，第二部分，认知纠偏。

认知纠偏

常见误解：装上 OM1 机器人就会走路。官方明确 OM1 不替代底层 HAL——没有运动控制与标定，仍需 RL、仿真或自研 VLA；OM1 是在已有执行能力上叠加多模态 AI 编排，不是具身智能模型本身。

接下来，第三部分，反驳。

反驳

对立视角：ROS2 资深集成商 · 「中间件已够」派

再叠一层 NLDB 和多 LLM 只会把 1Hz 认知环上的延迟与故障面放大，工业现场要的是确定性 DDS 与硬实时控制，不是把传感器编成段落给云端大模型读。

接下来，第四部分，【概念拆解卡】自然语言数据总线 NLDB。

在讲什么问题，多传感器与多 LLM 之间用什么中间表示通信，才能让人类可读、LLM 可推理、又能在约 1Hz 融合节奏下跑通行为。

核心机制，视觉/语音/电量等先经 captioning 转成自然语言片段，由 State Fuser 压成情境描述，再喂给决策 LLM；论文论证即使总线约 40 bits/s 仍可得可用行为。

关键理解，反直觉地用「人话」而非张量做总线，换来可调试、可审计的「内心独白」，代价是信息压缩与延迟需与 Fast Action LLM 分层配合。

典型场景，家庭/社会场景下需要理解意图的多机人形或服务机器人上层认知环。

边界说明，50–500Hz 步态稳定控制仍在独立控制回路，OM1 主循环通常 1Hz 级，管的是注意力与工作记忆而非电机闭环。

原文：最基础的系统由四个 LLM 通过自然语言总线通信，即使数据融合周期只有 1Hz，依然能在多种任务上跑出不错的机器人行为。

接下来，第五部分，【跨概念对比表】OM1 vs LeRobot vs ROS2。

核心职责，AI 运行时 + 硬件抽象，教机器人学技能，机器人通信与执行基建，分工而非替代

是否训练模型，否，调度编排，是，策略/模仿学习，否，OM1 站在已具备智能之上

跨硬件承诺，JSON5 换插件，偏训练管线，节点与话题标准，OM1 类比 Android 应用层

实现语言，Go（Python 已 deprecated），Python 生态，C++/多语言，OM1 选 Go 为边缘运行时

接下来，第六部分，【方法/工具卡】Gazebo 仿真跑通 Unitree Go2。

标签：零硬件入门 · ROS2 Humble · Zenoh 桥

操作步骤，1) Ubuntu 22.04 装 ROS2 Humble 与 CycloneDDS 相关包 ，得到 2) git clone OpenMind/OM1-sim，rosdep install，colcon build，uv 装 Python 侧 ，得到 3) ros2 launch go2_gazebo_sim go2_launch.py ，得到 4) zenoh-bridge-ros2dds 连配置 ，得到 5) 设置 OM_API_KEY，CONFIG=unitree_go2_autonomy USE_SIM=true make dev ，得到 6) 用 teleop_twist_keyboard 验证链路。

选型条件，无实体狗、要先验证 NLDB，得到LLM，得到动作；有 NVIDIA GPU 可换 Isaac Sim 官方文档路线。

落地：OM1 不知道控制的是真机还是仿真——这正是 hardware agnostic 设计要验证的点。

避坑：官方支持 Gazebo/Isaac Sim，无原生 MuJoCo 集成；别期待 OM1 单独承担 MuJoCo 式 RL 训练场景。

接下来，第七部分，【避坑清单卡】安卓类比与工程现实。

坑 1 — 把 OM1 当 VLA：不会凭空学会走路。解法：先建好 HAL/控制栈再叠 OM1。严重程度：致命。

坑 2 — 忽视形态差异：四足与人形运动学是两物种，HAL 能屏蔽多少要看落地而非架构图。严重程度：小心。

坑 3 — 仍用 Python 主线：新开发已全面 Go，Python 版本 deprecated。严重程度：小心（维护与部署）。

坑 4 — 单 LLM 扛全链路：典型需 Fast Action（约 300ms）、Core（约 2s）、Mentor 复盘分工，并受 system_governance 约束。

接下来，第八部分，【决策/选型表】何时引入 OM1。

已有 ROS2/Zenoh 与 HAL，评估 OM1 作上层 Agent，解耦模型与机身，用 OM1 替代运动控制，职责越界

从零训练行走策略，LeRobot + 仿真训练，OM1 不教技能，只装 OM1，无执行基础

边缘 Jetson 部署，Go 单二进制 OM1，低延迟、小内存，继续 Python 运行时，官方已弃维护

多机协作愿景，关注 FABRIC 协议演进，超越单机 Android 类比，仅当手机 OS 理解路线，路线含 App Store/Web3 层

接下来，第九部分，总结与行动。

结论

OM1 是模块化 AI Runtime/HAL，站在栈第③层，与 LeRobot（学技能）、ROS2（执行通信）互补。

NLDB + State Fuser + 多 LLM 角色分工构成核心流水线；JSON5 多模式配置实现跨机身复用 Agent 逻辑。

Python，得到Go 重写面向边缘延迟、并发与单二进制部署；主循环约 1Hz，与底层高频控制分离。

OpenMind 路线从 Runtime 延伸到 Robot App Store 与 FABRIC，「安卓」类比在形态差异与 Web3 治理上存在边界。

对照自家机器人是否已有 HAL，再评估 OM1 是否只补认知编排层。

用 OM1-sim + Gazebo Go2 跑通 Zenoh 桥与 USE_SIM=true 开发链路。

阅读 JSON5 中 modes/transition_rules，设计可切换人格状态而非单 prompt 硬编码。

规划 Fast/Core/Mentor 三类 LLM 的部署位置与 API Key（OpenMind Portal）。
