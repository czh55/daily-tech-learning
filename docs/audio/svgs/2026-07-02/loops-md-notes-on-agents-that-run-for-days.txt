欢迎收听每日技术学习语音讲解。本期主题，Andrej Karpathy 解析 Loop Engineering：构建「数日级」长程 Agent 的 9 条黄金法则。标签包括Loop Engineering、Agent Harness、Karpathy、长程 Agent。本次讲解预计时长 约 12 到 13 分钟，共 10 个部分。好，我们开始。

一句话概括。本文解决的核心问题是：当 Agent 任务复杂度提升、运行时间拉长到数天级别时，为什么单纯调 Prompt 会失效，以及如何用「循环工程」——把控制流、状态持久化与多角色分离设计为一等公民——让 Agent 稳定交付可用产品。

接下来，第一部分，核心概念关系。

关系脉络如下：Prompt 时代，一次性写完即弃，然后Loop 一等公民，Gather，得到Reason，得到Act，得到Verify，然后三角色分离，Planner/Generator/Evaluator，然后磁盘状态，contract.md 等，然后瓶颈迁移，Coding，得到Planning，得到Taste

接下来，第二部分，认知纠偏。

认知纠偏

常见误解：「模型不够聪明才导致 Agent 失败」—— Karpathy 指出瓶颈早已不在模型智商，而在 Harness 设计太差；模型能写代码、能审查，却无法自行决定何时停、何时推倒重来、结果写到哪里。

接下来，第三部分，反驳。

反驳

对立视角：「Prompt 极简主义」派 / 快速 Demo 倡导者

三角色、磁盘合同、27 条断言是过度工程——多数产品一周上线、用户只在乎功能有没有，为「数日级 Agent」设计的 Harness 会把简单任务拖成运维负担。

接下来，第四部分，【概念拆解卡】Loop Engineering vs Prompt Engineering。

在讲什么问题，为什么凌晨三点还在调 System Prompt 的开发者仍停留在「提示词时代」？

核心机制，Prompt 是写完一次就扔的静态指令；Loop 是你睡觉时仍在后台运行的系统——收集、推理、行动、验证、重复（Gather, Reason, Act, Verify, Repeat）。

关键理解，当模型已能无人监督遵循复杂流程，Prompt 的杠杆效应见顶；拉开差距的是 Procedure（流程），不是措辞。

典型场景，任务需运行数小时到数天、需断点恢复、需多轮生成-评估博弈时，必须写循环而非写 Prompt。

边界说明，简单单次问答、短链路 Demo 仍可用 Prompt；长程、有状态、需验收的生产系统必须用 Loop。

原文：「如果你发现自己凌晨三点还在反复调试某一个 Prompt，那你还停留在提示词时代。请关掉那个 Playground 标签页，开始写循环吧。」

接下来，第五部分，【方法/工具卡】三角色分离 + 磁盘状态 + 合同协商。

核心思路：把「既当裁判又当选手」的自我评分彻底拆开，用磁盘文件固定真相，用可测试断言合同约束验收。

操作步骤，

1. 三角色三窗口：Planner 写 Spec 不碰代码；Generator 写代码不自评；Evaluator 从第一秒就假设「代码肯定有 Bug」。

2. 先协商合同：Generator 提出「如何算完成」，Evaluator 反驳，通过磁盘 Markdown 拉锯至 27 条左右可测试断言（10 条太少易放水）。

3. 状态写磁盘：维护 feature_list.json、progress.md、contract.md、log.md（追加格式 ## [YYYY-MM-DD] op | title）。

4. 允许推倒重来：新一代模型在死胡同时会删库重来——有干净 Evaluator + 磁盘合同时，第 11 次迭代可交付完好版本。

选型条件，需要可审计、可恢复、防上下文腐化时用磁盘；纯聊天式短会话仍可用内存上下文。

落地检验：若无法用三个文件向模型描述清楚当前状态，说明系统状态设计过于复杂。

避坑：角色混用导致模型谄媚，循环悄无声息收敛出 Slop；上下文窗口会压缩、退化、撒谎，磁盘文件不会。

接下来，第六部分，【决策/选型表】何时人类介入 vs 让循环自治。

构建失败（编译报错），让循环自行重试/推倒重来，Build Failures 不需要人类插手，人工每次修编译错误，打断循环自愈，无法暴露 Harness 缺陷

合同本身定错，人类介入修订 contract.md，验收标准错误会导致全链路跑偏，继续让 Generator 硬改，在错误目标上优化只会更快产出垃圾

主观体验验收，Evaluator 四维度加权打分，设计/原创性/工艺/功能性可量化，纯靠 Generator 自评，模型向错误品味指标收敛

调试循环行为，读 Trace 用 grep 定位分歧点，与读 stack trace 同一块肌肉，盲目做下一次实验，仅凭玄学 Vibe 调优

新模型发布，对照删减 Harness 冗余逻辑，Harness 为弥补模型缺陷而存在，只加不减的 Harness，说明已看不懂也不再阅读自己的控制代码

接下来，第七部分，【避坑清单卡】长程 Agent 常见失效模式。

坑名，上下文腐化 + 自我谄媚——运行数小时后 Agent 把一小时前的话藏在自生成摘要后面。

原因，状态塞进 Context Window 而非磁盘；Generator 与 Evaluator 角色未分离。

解法，Write to Disk, Not to Context；崩溃后仅靠三个文件即可断点续跑。

严重程度，致命——「Demo 很惊艳，落地就抓狂」的主因。

原文：「LLM 的上下文窗口是会撒谎的。它们会发生信息压缩、会随着对话变长而退化。」

老模型陷阱：给坏代码层层打补丁成考古遗迹；新模型 + 干净 Evaluator 会果断删库重来——不要打断重启行为。

接下来，第八部分，【心法/原则卡】瓶颈永远在移动。

原则，设计循环的唯一目的，是让下一个瓶颈清晰暴露——你永远没有「大功告成」的那天。

为什么重要，Coding 不再是瓶颈 ，得到 Planning 成瓶颈 ，得到 Verification 自动化后 ，得到 Taste 成瓶颈；每次迁移都需重构更轻的 Harness。

原文支撑：「如果你的系统运行得无比顺滑、毫无阻碍，那只能说明你观察得还不够仔细。」

怎么落地，给主观体验建四维度评分 + 好/坏参考站校准；读完整 Transcript 而非盲试；新模型发布时删掉模型已能自主搞定的逻辑。

适用边界，品味指标需小心制定——模型不会凭空创造品味，只会向你描述的指标收敛。

接下来，第九部分，总结与行动。

结论

Agent 落地失败根因多在 Harness 而非模型智商——控制流、状态持久化、多角色博弈是一等公民。

标准循环五动词：Gather ，得到 Reason ，得到 Act ，得到 Verify ，得到 Repeat；Karpathy 9 条法则皆其注脚。

Planner / Generator / Evaluator 必须分离，合同前置为可测试断言，状态落盘而非塞进上下文。

允许循环推倒重来；构建失败不必人工介入，合同定错才需人类。

瓶颈从 Coding 迁移到 Planning、Verification、Taste——Harness 应随模型进化只减不加。

为当前 Agent 项目建立 feature_list.json、progress.md、contract.md、log.md 四文件状态协议。

拆出独立 Evaluator 上下文，系统提示首句写入「这代码肯定有 Bug，你的任务是找证据」。

下次 Agent 跑偏时，把完整 Transcript 重定向到文件，grep 定位「判断开始分歧」的瞬间再改 Prompt。

在写第一行代码前，让 Generator 与 Evaluator 就「完成定义」在磁盘上拉锯至至少 20 条断言。

新模型发布后对照审视 Harness，删除模型已能自主完成的控制逻辑。

总结：

行动清单：

关键认知转变：从「Prompt 工程师」进化为「系统级循环工程师」——技术形式在变，工程本质未变：管理复杂性，消除不确定性；下次 Agent 频频跑偏时，停下调 Prompt 的手，审视支撑它的那条循环。
