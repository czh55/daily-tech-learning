一句话概括。本文解决的核心问题是：在不能停工补文档的 React 老项目上，如何不拼装 Spec Kit+Superpowers 两套工具，而是取宪法思维、铁律纪律与 Delta Spec，叠成 Spec / Skill / Harness 三层与 WORKFLOW.md 裁剪规则，让增量需求约 50 分钟跑通且 review 在合入前拦住规范与实现缺口。

接下来，第一部分，核心概念关系。

关系脉络如下：Harness，CLAUDE.md + 组件分层表，然后Skill 层，8 Skill + 硬门控，然后Spec 层，Delta + 单目录收拢

接下来，第二部分，认知纠偏。

认知纠偏

误解：「把三个开源框架拼一起就行」。作者实测 Spec Kit+Superpowers 九步协同成立，但流程耗时翻倍 + 中间规范要手工粘贴，只适合超大规模团队；棕地小改动（50 行）走完全阶段门控 ROI 极差。

接下来，第三部分，反驳。

反驳

对立视角：流程极简派 / 「AI 自觉就够」

八 Skill、YAML 追踪和组件四层表是另一套官僚软件工厂——团队真正需要的是删流程写代码，不是把 Superpowers 的 MUST 抄进更多 Markdown。

接下来，第四部分，【跨概念对比表】三框架：拿走什么、丢掉什么。

Spec Kit，宪法式可验证约束，阶段门控、按功能分片规范，改动小则流程倒挂；棕地无 Delta

Superpowers，MUST 铁律、反合理化闭环，14 Skill 全链、纯 brainstorming，Token 与子代理成本高；无规范累积；方向易偏

OpenSpec，Delta Spec、单目录收拢，无纪律的 apply，企业场景不能靠 AI 自觉

接下来，第五部分，【概念拆解卡】brainstorming vs grill-me 方向校准。

在讲什么问题，为何扔掉 Superpowers 的 brainstorming，改用 Matt Pocock 式 grill-me 做 product Skill。

关键理解，brainstorming 适合绿地、模糊想法；grill-me 假设已有主干（PRD + 十万行代码），一次一问、长 design tree，细节密度高。

怎么落地用：企业棕地用「六维评审 + 逐层审问」产出 product.md，下游 api/ui/page 不再补方向性细节。

边界说明，只有念头、无文档时 grill-me 会把人问崩——别在探索期硬用。

作者：TDD 再好，做出来的东西跟需求对不上也白搭。

接下来，第六部分，【方法/工具卡】WORKFLOW 三种模式。

full：新功能/跨模块 ，得到 完整 8 Skill 链 + .spec.yaml 追踪。

light：小改动、纯 review/补测 ，得到 只跑必要 Skill，不建 YAML、不归档。

bugfix：Jira ，得到 根因 ，得到 最小修复，独立链路，不进 spec 进度。

操作步骤，在 spec/WORKFLOW.md 写清 Skill 依赖（api/ui 并行 ，得到 page ，得到 test/qa ，得到 review）；换项目时 CLAUDE.md 重写，WORKFLOW 可迁移。

组件 L0–L3 对照表：禁止直接用 antd 原生（L0），优先 L1 封装；review 发现漏登记则回流 CLAUDE.md，四个月表从十余行长到四十余行，误用降八成。

接下来，第七部分，【方法/工具卡】用户角色筛选案例（Delta ，得到 Skill ，得到 review）。

Spec 层：只写 ADDED/MODIFIED（角色下拉、接口 role 参数、URL 同步）进 spec/changes/user-role-filter/。

Skill 层：api/ui 读 CLAUDE.md；接口不清标 [待确认] 停等人；page 组装后 test；每步更新 .spec.yaml。

Harness 层：review 三步（意图/质量/边界）；发现应使用 RoleSelect 而非原生 Select ，得到 补宪法；发现漏 URL 同步 ，得到 标 [需修复] 退回 page。

结果：全程约 50 分钟，合入前拦 2 个问题，归档到 archive/日期-id/。

接下来，第八部分，【避坑清单卡】自建 Harness 常见坑。

小改动仍跑 full 八链：固定流程成本吃掉收益——用 light/bugfix——严重程度：小心。

铁律写成「请尽量」：RLHF 乐观偏见下无效——改成执行步骤硬门控——严重程度：致命。

只维护 CLAUDE.md 无 WORKFLOW：方法论与项目事实混淆——换库即失忆——严重程度：小心。

期待 OpenSpec apply 自证质量：必须叠 review+TDD 纪律——严重程度：致命。

接下来，第九部分，【决策/选型表】何时用哪套方法论。

十万行棕地、有 PRD，本文三层 + grill-me，增量 Spec + 规范回流，Spec Kit 全阶段门控，1.5h 流程 vs 50 行改动

个人绿地原型，Superpowers brainstorming，低启动成本，八 Skill 全链，Token 与子代理过重

超大规模、能扛双倍流程，Spec Kit+Superpowers 组合，语义/物理两层隔离成立，十人团队硬套，胶水层人力填缝

仅要 Delta 文档，OpenSpec 底座，40 分钟级增量，单独 OpenSpec apply，无企业级纪律

接下来，第十部分，总结与行动。

结论

三框架精髓可融为一层系统，消除「规范↔执行」手工胶水。

棕地核心：Delta Spec 只写变化 + 铁律 Skill + CLAUDE.md 可验证宪法与组件分层表。

方向校准用 grill-me 式审问，而非绿地 brainstorming；流程用 full/light/bugfix 裁剪。

review 双向回流：规范缺口进 CLAUDE.md，实现缺口退回上游 Skill。

在 spec/WORKFLOW.md 画出 Skill 链与三种模式触发条件。

把「禁止 L0 原生组件」写成可 review 抓取的规则，并建 L1–L3 初表。

选一个真实小需求跑通 Delta ，得到 api/ui/page ，得到 review，记录 .spec.yaml。

对比单次改动耗时，决定默认 light 还是 full。
