一句话概括。本文解决的核心问题是：如何在 Hermes Agent 中构建可串联、可门控、可零 Token 运行的定时自动化流水线——用 context_from 链接多阶段任务、用 wakeAgent 实现高频轮询零成本跳过、用 no-agent 模式处理纯脚本看门狗。

关系脉络如下：Cron 调度，然后wakeAgent 门控，然后Agent / no-agent，然后context_from 链，然后多平台投递

接下来，第二部分，认知纠偏。

认知纠偏

常见误解：「Cron 任务各自独立，串联只能靠手动读文件」—— Hermes 的 context_from 会在下游任务触发时自动注入上游最近一次成功输出，无需硬编码路径；wakeAgent 门控让 99% 无变更的 tick 零 LLM 调用。

接下来，第三部分，反驳。

反驳

对立视角：n8n / Temporal 工作流工程师

把流水线塞进 Cron 加 JSON 门控是在用聊天机器人调度器硬扛编排——没有可视化 DAG、没有幂等重试与死信队列，context_from 链条一长就沦为不可观测的黑盒，生产级自动化应交给专业工作流引擎而非 Hermes 定时任务。

接下来，第四部分，【概念拆解卡】Hermes Cron 三大机制。

在讲什么问题，Cron 任务默认隔离无记忆，高频轮询烧钱，纯监控不需要 AI——三大痛点如何一次解决。

核心机制，① context_from：任务 B 触发时自动读取任务 A 最近成功输出作为提示词前缀，实现采集，得到筛选，得到发布流水线；② wakeAgent 门控：预检查脚本在 Agent 启动前输出 JSON 决定跳过或唤醒，零 Token 静默；③ no-agent 模式：调度器直接运行脚本，有输出才投递，零 LLM 调用。

关键理解，三种机制共用同一调度器、生命周期管理与投递路由，不需要为不同模式维护不同工具链。

典型场景，每日 AI 新闻三级流水线、SSL 证书 14 天到期告警、竞品仓库变更自动分析、内存/磁盘看门狗。

边界说明，context_from 链条建议 3-5 级以内；上游未执行过时下游无额外上下文但正常运行；需要语义理解/总结/分析的任务不能用 no-agent。

相关概念：与 n8n 等可视化工作流互补——Hermes Cron 深度集成 Agent 推理与消息平台投递，适合已部署 Hermes 的 AI 原生运营场景。

接下来，第五部分，【方法/工具卡】context_from 三级流水线实战。

标签：任务链 · 多阶段自动化

核心思路：用名称引用串联隔离会话，上游输出自动成为下游上下文前缀。

操作步骤，① 7:00 创建「AI News Collector」采集 HN 前 10 条 AI/ML 新闻；② 7:30 创建「AI News Triage」设 context_from="AI News Collector"，评分筛选 ≥7 分条目；③ 8:00 创建「AI News Brief」设 context_from="AI News Triage"，生成推文草稿，无合格新闻以 [SILENT] 开头抑制投递。

选型条件，需要「采集，得到处理，得到发布」多阶段且每阶段逻辑不同、需 AI 推理时选用 Agent + context_from。

落地：多任务扇入用 context_from=["task-a","task-b"] 列表，输出按顺序拼接。

避坑：context_from 读取的是上游最近一次成功输出，不会等待同一 tick 内正在运行的上游——调度时间必须错开（如 7:00/7:30/8:00）。

接下来，第六部分，【方法/工具卡】wakeAgent 零成本门控。

标签：高频轮询 · Token 节约

核心思路：预检查脚本 stdout 最后一行输出 JSON，{"wakeAgent": false} 跳过 Agent，{"wakeAgent": true, "context": {...}} 唤醒并传数据。

操作步骤，① 编写门控脚本到 ~/.hermes/scripts/（文件变更检测、外部标志位 touch、SQLite 新行数检查三食谱）；② Cron 任务配置预运行脚本；③ 脚本判断无新状态时输出 wakeAgent:false，有变化时更新状态并 wakeAgent:true。

对比相邻方法，无门控每 5 分钟轮询月调 8640 次 Agent；有门控日均 2 次真实变更约 60 次，减少 99.3% 调用。

门控脚本开销通常在 10ms 以内完成，wakeAgent 缺省默认为 true。

接下来，第七部分，【跨概念对比表】Agent 模式 vs no-agent 模式。

LLM 调用，每次 tick 可能推理，零 Token、零模型消费，脚本能算清结果就用 no-agent

适用任务，语义理解、总结、分析，阈值告警、健康检查、SSL 监控，判断标准是输出是否需要推理

输出规则，Agent 响应投递，exit 0 + 非空 stdout 投递，空 stdout 静默，非零退出码始终投递错误告警

调度管理，同一调度器，暂停/恢复/列表/日志/投递通用，无需维护两套工具链

接下来，第八部分，【决策/选型表】Cron 自动化方案选型。

每日新闻采集，得到筛选，得到发布，三级 context_from + [SILENT]，各阶段需不同 AI 推理，链式传上下文，单任务塞全部逻辑，提示词臃肿、难以调试

一次性提醒，相对延迟 30m/2h/1d，简单直接，Cron 五段式，过度配置

接下来，第九部分，【避坑清单卡】Cron 自动化常见陷阱。

坑名，通知轰炸——定时任务每隔几小时推送「一切正常」。

原因，未使用 [SILENT] 抑制或无门控导致空 tick 也投递。

原文说法：「每隔几小时收到一条一切正常的消息，很快就会把通知渠道变成噪声源。」

解法，提示词末尾要求无事项时以 [SILENT] 开头回复；no-agent 模式空 stdout 自动静默；wakeAgent:false 跳过 Agent。

严重程度，小心——用户很快屏蔽通知渠道，真正告警也被忽略。

另一坑：门控脚本放错路径或含 ../ 遍历——Hermes 只接受 ~/.hermes/scripts/ 下脚本且拒绝路径遍历，严重程度：致命（任务静默失败）。

接下来，第十部分，总结与行动。

结论

Hermes Cron 支持斜杠命令、CLI、自然语言三种等价创建方式，调度格式覆盖相对延迟、间隔、五段 Cron、ISO 时间戳。

context_from 用名称引用串联隔离会话，实现采集，得到筛选，得到发布三级流水线，多任务扇入用列表拼接。

wakeAgent 门控让高频轮询 99% 无变更 tick 零 LLM 调用，月成本可减少 99.3%。

no-agent 模式用纯脚本处理阈值告警类任务，与 Agent 任务共用调度器与投递路由。

[SILENT] 前缀抑制空通知，避免通知渠道变成噪声源。

用 hermes cron create "0 9 * * *" 创建第一个每日定时任务，--deliver telegram 验证投递。

搭建三级 AI 新闻流水线：Collector(7:00) ，得到 Triage(7:30, context_from) ，得到 Brief(8:00, context_from + [SILENT])。

为高频监控任务编写 wakeAgent 门控脚本到 ~/.hermes/scripts/ 并 chmod +x。

将内存/磁盘/SSL 类看门狗迁移到 --no-agent 模式，验证空 stdout 静默与非零退出码告警。

用 hermes cron list 审计全部任务，暂停不再需要的无门控高频 Agent 轮询。
