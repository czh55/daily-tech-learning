一句话概括。本文解决的核心问题是：团队或个人在拉取私有 Go 模块时，如何一次性理清凭据配置、四个环境变量职责边界，以及按场景选择「直连托管平台」还是「自定义 import path + vanity 解析层」的落地方案。

接下来，第一部分，核心概念关系。

关系脉络如下：凭据层，.netrc / git insteadOf，然后GOPRIVATE，划定私有前缀，然后拉取路径，直连 vs Vanity，然后go-import，映射真实仓库，然后go get，git 直连拉取

接下来，第二部分，认知纠偏。

认知纠偏

常见误解：「配好 GOPRIVATE 就能拉私有模块」—— 实际上 GOPRIVATE 只告诉 Go 跳过公共代理和校验库，凭据（token/SSH）和 import path 解析（vanity）仍是独立的两层问题，缺任何一层都会 401 或 404。

接下来，第三部分，反驳。

反驳

对立视角：「YAGNI 派」/ 反对 vanity 层的极简开发者

绝大多数团队永远不需要 vanity——github.com/org/repo 够用一辈子，为「好看的 import path」多维护一层解析服务，是把五年后可能发生的迁移焦虑提前兑现成今天的运维税。

接下来，第四部分，【概念拆解卡】四个环境变量的职责边界。

在讲什么问题，为什么私有模块报错时总在 GOPRIVATE、GOPROXY、GOSUMDB、GOVCS 之间来回试？

核心机制，GOPRIVATE 划定「哪些是私有的」，得到 跳过 proxy 和 sumdb；GOPROXY 控制公共模块怎么拉和缓存；GOSUMDB 控制是否向 sum.golang.org 校验（私有模块必须关）；GOVCS 控制私有域名允许用 git/hg 等工具拉取。

关键理解，四者不是互斥替代关系，而是「私有划定 + 公共拉取 + 公共校验 + VCS 白名单」的分工组合。

典型场景，export GOPRIVATE=github.com/yourname/*,go.mycompany.com/* 配合 export GOVCS=go.mycompany.com:git。

边界说明，只配 GOPRIVATE 不管凭据 ，得到 401；私有模块不关 GOSUMDB ，得到 校验失败；自建域名不在 GOVCS 白名单 ，得到 1.16+ 默认拒绝拉取。

原文：「GOPRIVATE 划定哪些是私有的，GOPROXY/GOSUMDB 决定公共部分怎么拉、怎么校验，GOVCS 决定私有部分允许用什么工具拉。」

接下来，第五部分，【方法/工具卡】凭据配置两种主流方式。

核心思路：Go 通过 git 拉私有仓库，凭据最终要落到 git 能识别的认证机制上。

操作步骤，

1. ~/.netrc：machine github.com + login + password(token)，git 和 go 都会读

2. git insteadOf（更推荐）：git config --global url."https://oauth2:${GITHUB_TOKEN}@github.com/".insteadOf "https://github.com/"

3. SSH 重写：git config --global url."ssh://git@github.com/".insteadOf "https://github.com/"

4. CI 环境：token 放平台 Secret，禁止明文写进仓库脚本

组织场景：用机器账号(bot)生成令牌、按仓库限权、统一放 CI Secret，避免人员变动导致流水线突然失效。

避坑：凭据散落 .netrc、git config、CI 环境变量各处，换机器就要重配一遍，还容易把明文 token 提交进仓库。

接下来，第六部分，【方法/工具卡】Vanity Import URL 三种落地方式。

核心思路：Go 请求 https://example.me/go/pkg?go-get=1，期望 HTML 含 go-import meta 标签指向真实 git 仓库。

操作步骤，

1. 静态 HTML + GitHub Pages/Cloudflare Pages：零成本，每新增 module 手动加页面

2. 自建 govanityurls + Nginx：YAML 映射自动生成页面，需维护 TLS 和可用性

3. gvu 托管：gvu add example.me/go/pkg https://github.com/user/repo.git，免运维

边界说明，vanity 解析层和代码托管可以完全独立——不同域名、不同机器；自建 Git Server 时 go-import 指向内网 git 地址即可。

原文 meta 示例：<meta name="go-import" content="example.me/go/privatemodule git https://github.com/tonybai/privatemodule">

接下来，第七部分，【决策/选型表】个人 vs 组织场景怎么选。

只想 go get 拉到，不在乎 import path，托管平台私有仓库 + GOPRIVATE + git insteadOf，零额外基础设施，上 vanity 层，过度工程

个人要自定义域名 import path，仓库少，得到静态页；不想运维，得到gvu，按维护意愿选成本，一上来自建高可用，个人场景过度

组织要 go.mycompany.com 语义，小规模，得到自建 govanityurls；要免运维，得到gvu，为未来仓库迁移留余地，每个 repo 手改 import，迁移成本指数增长

组织规模大、CI 高可用，托管 vanity（gvu）或自建+高可用，vanity 挂了全公司 CI 停，单点 VPS 无备份，可用性风险被低估

白盒交付给客户，专门方案（客户网络访问不到你内网），原有方案在对方环境直接失效，照搬内部配置，需重新搭一套

接下来，第八部分，【避坑清单卡】五大常见痛点与解法。

坑名，凭据散落、import path 绑死平台、vanity 运维成本高、组织新增映射琐事、跨组织交付失效。

原因，把「能拉代码」和「好看的 import path」「高可用 vanity」「客户环境」混为一谈，没有分层设计。

解法，① 统一 git insteadOf + CI Secret ② 需要品牌语义才上 vanity ③ 评估自建 vs 托管的运维成本 ④ 组织用 bot 账号和限权 token ⑤ 白盒交付单独设计方案。

严重程度，组织场景 vanity 单点故障为致命级——Tony Bai 五年自建方案稳定但「每新增仓库改配置重载 Nginx」的隐性成本会随团队放大。

接下来，第九部分，【跨概念对比表】三种 Vanity 方案对比。

运维成本，极低，高（TLS/可用性），极低，仓库数决定选型

可控性，中，完全自主，依赖第三方，要自主选自建

扩展性，差（手动加页），好（YAML 映射），好（一条命令），仓库多了别用手写

高可用，看托管平台，需自己保障，天然多副本，组织 CI 优先托管

新增模块，手动 HTML，改 YAML + 重载，gvu add 一条命令，频率越高越要自动化

接下来，第十部分，总结与行动。

结论

私有模块拉取 = 凭据层 + 环境变量层 +（可选）vanity 解析层，三层独立排查

GOPRIVATE 划定私有前缀；私有模块须关 GOSUMDB；GOVCS 放行私有域名 VCS

凭据推荐 git insteadOf + CI Secret，组织用 bot 账号和限权 token

不在乎 import path ，得到 直连托管平台；要自定义 ，得到 静态页 / 自建 / gvu 三选一

组织高可用场景优先考虑免运维 vanity 或自建+冗余，vanity 故障=全公司 CI 停

检查本机 GOPRIVATE、GOSUMDB、GOVCS 是否覆盖你的私有前缀

配置 git config url.insteadOf 或 SSH 重写，CI 侧 token 进 Secret

若需自定义 import path，评估仓库数量后选静态页 / govanityurls / gvu

用 go get -x 跑一次，顺着报错判断是凭据、环境变量还是 vanity 问题

组织场景文档化 bot 账号、令牌轮换和新增 module 的标准流程
