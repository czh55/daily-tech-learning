一句话概括。本文解决的核心问题是：如何把 Claude Code 从「一锤子买卖」的一次性 Prompt 调用，升级为可跨会话断点续传、有强验证与失败退路的「睡后运行」自动化循环系统。

接下来，第一部分，核心概念关系。

关系脉络如下：触发器，Cron/手动/CI，然后上下文，读 TASK/PROGRESS，然后行动，写 outputs/，然后验证，独立监工，然后状态更新，PROGRESS.md，然后决策，继续/停止/升级

接下来，第二部分，认知纠偏。

认知纠偏

常见误解：「循环 = 重复问 Claude 同一个问题」或「/loop 命令本身就是魔法」—— 循环是可复用的工作流结构，/loop 只是定时器，真正生命力来自 4 文件结构、SOP、强验证与状态持久化。

接下来，第三部分，反驳。

反驳

对立视角：「YAGNI 极简派」/ 反对过度流程的敏捷倡导者

四个 Markdown 加双会话验证是官僚化——多数团队真正需要的是能跑的脚本和 Cron，不是给 AI 写 SOP 手册，文件越多维护成本越高、循环本身就成了新债务。

接下来，第四部分，【概念拆解卡】Loop vs 一次性 Prompt。

在讲什么问题，为什么高频重复工作（日报、CI 排查、进度监控）不能用「每天重新润色 Prompt」解决？

核心机制，Claude 会话是临时性的；循环在聊天窗口外持久化状态，让模型读取上次发生的事并在断点处接棒。模型负责推理，循环提供运转框架。

关键理解，漏掉验证 ，得到 盲目自信容忍垃圾产出；漏掉状态 ，得到 每次从零开始；漏掉决策 ，得到 沦为不知何时停下的死循环。

典型场景，每日项目审查、CI 失败排查、GitHub Issue 梳理、文档缺陷自查、周度回顾沉淀。

边界说明，一次性简单任务仍可用 One-shot；需跨天/跨会话记忆、有明确终止条件的重复工作才值得建 Loop。

原文：「没有循环，每一次运行都是从零开始；而有了循环，Claude 能够读取上一次发生的事，并在上一次停下的地方完美接棒。」

接下来，第五部分，【方法/工具卡】极简 4 文件系统搭建。

核心思路：无需数据库和后台，用 4 个 Markdown 文件定义目标、SOP、记忆与产出。

操作步骤，

1. 创建目录结构：my-loop/TASK.md、LOOP_INSTRUCTIONS.md、PROGRESS.md、outputs/

2. TASK.md：写高层次目标、预期输出、Scope 与禁止行为（Do Not 规则）

3. PROGRESS.md：维护当前状态、上次运行记录、Open Items、Blockers、Needs Human Review、Next Run Should

4. LOOP_INSTRUCTIONS.md：启动准备 ，得到 标准操作流程 ，得到 安全红线 ，得到 异常失败策略（Failure Policy）

5. 手动跑通 3-5 次模拟变更，确认断点续传后再部署 /loop 24h

PROGRESS.md 铁律：决策依赖的信息保留在 PROGRESS；仅留档备份的记录移到 outputs/history/。永远膨胀的状态文件等同于无用。

避坑：第一版循环必须有明确「禁止行为」——不是不信任 Claude，而是合格工程师的职业素养。

接下来，第六部分，【方法/工具卡】强验证与 Worker/Verifier 分离。

核心思路：循环停下来不是因为模型「觉得写完了」，而是硬性约束条件通过了校验。

操作步骤，

1. Worker 会话：按 LOOP_INSTRUCTIONS 执行并更新 outputs/ 与 PROGRESS.md

2. Verifier 会话（独立）：对照验证清单逐项体检，严禁修改任何文件

3. 验证报告须含 5 项：通过项、失败项、被改文件列表、是否可安全接收、需人工确认的疑点

4. 弱验证（「看起来行不行」），得到 强验证（「7 条指标全部 PASS 才标记 Accepted」）

原文：「干活的与监工的，必须彻底分离。」

避坑：Claude 自信汇报完成、报告缺章节、PROGRESS 敷衍涂改、悄悄改了源码——这些致命失误往往在系统跑崩后才被发现。

接下来，第七部分，【决策/选型表】/loop vs /goal 与权限阶梯。

每日监控、日报生成，/loop 24h，基于时间触发，到期再跑，/goal，目标触发适合「不达标不停」场景

修复 Bug 直到测试全过，/goal 条件表达式，基于状态/目标触发，不达目标不停，固定间隔 /loop，时间到了但目标未达成会空转

第一个循环系统，权限阶梯 L1-L2（只读/outputs 草稿），即使 L1-L2 也有巨大价值：汇总信息无需碰重要文件，一上来开放 Slack/合并 Master，幻觉一旦发生是毁灭性车祸

本地循环稳定后，逐步加 GitHub/Slack（先只读再草拟），每增一工具扩大破坏半径，须详尽 Tool Permissions Policy，未列出的工具擅自使用，后台做出意料之外的事

测试节奏观察，/loop 15m，短间隔便于盯过程，未手动验证就部署自动调度，五大死穴之首

接下来，第八部分，【避坑清单卡】摧毁循环系统的 5 大致命死穴。

坑名，手动测试未通过就部署自动调度，或无状态/无验证/无失败策略。

原因，把「觉得更强大」当终止条件——无客观 Checklist、无状态记录、无验证机制。

解法，① 手动跑通 3-5 次 ② 配置 PROGRESS.md ③ 引入独立 Verifier ④ 写 Failure Policy ⑤ 从 L1-L2 权限起步，证明稳定后再升级。

严重程度，致命——过早接入太多工具会使出错时破坏半径指数级扩大。

原文反面教材：「每天持续优化产品战略文档，直到觉得它变得更强大。」—— 要么一事无成，要么把不想改的文件改得面目全非。

优秀循环特征：明确定时计划、严格限制范围、可预测输出文件、绝对安全权限边界——差距不在模型智商，而在系统设计。

接下来，第九部分，【跨概念对比表】引入循环前后的世界线。

记忆，会话结束上下文清空，PROGRESS.md 跨会话传递，状态在聊天窗外

行为控制，每次重新润色 Prompt，LOOP_INSTRUCTIONS 如法律控死行为，审输出不审 Prompt

质量保障，肉眼跟踪文件变化，独立 Verifier + 硬性 Checklist，瓶颈转向审查验证

自动化，人工重复体力劳动，读取，得到执行，得到验证，得到更新，得到停止闭环，睡后仍在运转

权限，无边界或全开，6 级权限阶梯渐进放权，成熟工程化体现

接下来，第十部分，总结与行动。

结论

循环 ≠ 重复 Prompt，而是触发器，得到上下文，得到行动，得到验证，得到状态，得到决策的六要素闭环

4 文件系统（TASK / INSTRUCTIONS / PROGRESS / outputs）零架构成本即可落地

PROGRESS.md 是控制面板不是档案馆；Worker 与 Verifier 必须分离

权限从 L1-L2 起步，手动验证 3-5 次后再 /loop 自动调度

系统瓶颈从「如何生成」转向「如何审查验证」—— 你设计的是无需肉身盯防的自动化系统

在项目目录创建 4 文件结构，复制文中 TASK / PROGRESS / LOOP_INSTRUCTIONS 模板

用 Claude Code 手动触发一次每日审查循环，检查 outputs 与 PROGRESS 更新

模拟 3 次项目变更后重跑，确认断点续传

开独立 Verifier 会话做强验证，对照 7 条硬性指标
